Write acceptance criteria

Acceptance criteria are what "done" means. In spry they are not a nice-to-have at the bottom of a ticket: tests are named after them, QA checks them by hand, and a story is done only when every one is proven. Write them well and the rest of the process mostly runs itself.

The one decision you can't hand to the agent

A story goes ready only on a person's yes, because its criteria decide what gets built and what counts as finished. It's one of the three things a person always decides — see Where a person decides.

Where they live

Criteria live only in stories, in a table numbered AC-1, AC-2, and so on. Everywhere else they are cited by story and number: S-2/AC-1. Here is a story from the worked example:

ACGivenWhenThen
AC-1a member with 3 books on loanthe librarian scans their library cardthe desk shows "Limit reached: 3 books on loan" and Lend cannot be pressed (F-1/R-1)
AC-2a member with an overdue bookthe librarian scans their library cardthe desk shows "Return overdue book first:" and the overdue book's title, and Lend cannot be pressed (F-1/R-4)

Given is the starting situation, When is what the person does, and Then is what they see.

The rules for a good criterion

Observable by a person using the product

Written at audience 3 — something a person would see on a screen, a receipt, an email. Not a table, a function or a status code.

Not this

  • The loans table gets a row with due_on set

This

  • The receipt shows the title, the member's name and a due date 14 days from today

One behaviour each

If Then joins two outcomes with "and", ask whether they could fail separately. If they could, they are two criteria. (Showing a refusal message and disabling the button is one behaviour — the refusal. Lending a book and printing the right due date are two.)

Not this

  • the book is lent and the receipt shows the due date and the member is emailed

This

  • AC-1 — the desk shows "Lent to" and the member's name
  • AC-2 — the receipt shows a due date 14 days from today

Specific enough to fail

Every criterion becomes a test name and a manual check. A Then that can't be wrong — "it works", "the page loads correctly", "an error is shown" — can't be proven either. Name the exact message, number or state.

Not this

  • an appropriate error is shown

This

  • the desk shows "Already on loan to" and the member's name, and Lend cannot be pressed

Cite the feature's rules, don't restate them

A feature holds numbered business rules (R-1, R-2…). A criterion that depends on one cites it — (F-1/R-2) — rather than copying the rule. If the loan length changes, it changes in one place.

Use the glossary's words

If the glossary says lend, a criterion never says check out. spry check fails on a banned synonym. QA will look for the words in the criterion on the screen, so they must match.

Six at most

A story with more than six criteria is usually two stories. spry offers to split it before going on.

Numbers are forever

  • Never renumber. Tests, QA logs and slices point at S-1/AC-2. If numbers shifted, they would silently point at the wrong thing.
  • Dropping a criterion strikes it through — ~~AC-2~~ — rather than deleting it. The number is never reused.
  • A new criterion takes the next number, even if it belongs logically between two others.

How a criterion gets proven

A criterion is proven in one of two ways.

By a test whose name cites it

The citation goes in the string that names the test — the title, a docstring, or a parametrize id:

it("S-2/AC-1 refuses a member with 3 books on loan", () => { … });
it("S-2/AC-2 refuses a member with an overdue book", () => { … });
  • A citation in a comment or in code proves nothing, and spry check warns about it. Names are what test runners report, so names are what count.
  • A skipped or to-do test proves nothing — it.skip, test.todo, xit, @pytest.mark.skip.

By a QA check

Some criteria are best checked by a person — a printed receipt, a layout on a real device. A pass as the latest row for that criterion in the story's checks.md proves it. See Checks for QA.

A person who saw it broken wins

If the latest QA row for a criterion is fail, the criterion is not proven — even if a test passes. In the worked example, story S-1 has all its slices merged, but QA saw the due date print a day early in the evening, so S-1 shows "not proven" until bug B-1 is fixed and QA logs a new pass for AC-2.

Changing criteria after slicing

Editing a story after work has started is allowed — sometimes you learn something. But changing a criterion under its tests is also the quiet way to make failing work "pass", so spry watches for it:

  • A warning on the pull request when a branch changes the text of a criterion that a test already cites, or that the story's QA scenarios or check-log rows relied on and the branch left as they were. Re-read those scenarios in the same pull request.
  • A block at merge when the same branch changes a criterion and code. The merge waits until the slice carries criteria_approved_by: with the name of the story's owner. The agent shows them the old and new text, and only their yes — in their words — puts that line in. The agent's own judgement never does.

A quick checklist

  • Could someone using the product see whether it's true?
  • Is it one behaviour?
  • Could a test of it fail?
  • Does it name exact messages and numbers?
  • Does it cite the feature rule instead of restating it?
  • Does it use the glossary's words?
  • Are there six or fewer in this story?
