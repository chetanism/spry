Work as a team

spry runs the same for one person or ten — a team is a section of the config, not a separate setup. This page covers what changes when there are several people, and several agent sessions, working on one repository at once.

Roles and members

The team is listed in spry/spry.config.json. In the worked example, three people:

"team": {
  "members": [
    {"name": "Asha",  "github": "asha-k",   "roles": ["product"]},
    {"name": "Ravi",  "github": "ravi-dev", "roles": ["developer"]},
    {"name": "Meera", "github": "meera-qa", "roles": ["qa"]}
  ],
  "review": {
    "spry/plan/**/README.md":   ["product"],
    "spry/plan/**/checks.md":   ["qa"],
    "spry/plan/**/SL-*.md":     ["developer"],
    "src/**":                   ["developer"]
  }
}
  • Empty members means solo: no person is asked to review, approval is skipped at merge, and the plan is committed straight to the main branch — but a fresh agent still reviews every plan item and slice.
  • Roles decide who an item goes to. Product writes and reviews milestones down to stories; developers slice and build; QA writes and runs the checks.
  • Plan items go through pull requests when a team is configured and the path falls under a review rule — instead of being committed to the main branch.

Review routing and CODEOWNERS

GitHub's CODEOWNERS file is generated from team.review, so GitHub asks the right people to review each pull request:

$ python3 spry/tool/spry.py codeowners
# Generated by `spry.py codeowners` from team.review in spry/spry.config.json.
# Change that, not this file. Later lines win, as GitHub reads them.
/spry/plan/**/README.md @asha-k
/spry/plan/**/checks.md @meera-qa
/spry/plan/**/SL-*.md @ravi-dev
/src/** @ravi-dev

A fresh-eyes review still runs first; when it finishes, it names who else must read the PR — the roles team.review gives for its paths.

IDs and slice claims

Two sessions creating a story at the same moment could both take S-7. Two people could both start on SL-4. The mint setting says where an ID is taken and a slice is claimed:

mint: local defaultmint: main
CounterThe next number in your working treeThe main branch on the remote — the push is the lock
Two sessions, one numberPossible. check --base names it before the merge, and the later branch renamesCan't happen. A refused push fetches and tries again, up to five times
Claiming a sliceMakes the branch locallyWrites branch: on the slice on the main branch, and refuses when someone holds it, naming their branch
NeedsNothingA main branch that accepts a direct commit of documents

With mint: main, spry.py new writes the new item in a temporary checkout of the main branch, commits docs(plan): new S-7 …, pushes it, and merges that commit into your branch — so the ID is final the moment you have it. Offline, or if the push is refused for any other reason, it stops and writes nothing; it never falls back to a local number.

$ python3 spry/tool/spry.py claim SL-4 --owner Ravi   # take it before writing the work order
$ python3 spry/tool/spry.py release SL-4             # give it back: planned again, branch empty

With mint: main, the backlog lists a claimed slice under In progress for everyone, so nobody else picks it up; with mint: local, only your own clone sees the claim until you push the branch.

Setting it up

Setup always commits with mint: local, because mint: main needs spry to already be on the main branch. If you chose main in the interview, switch it once setup is merged.

Slices side by side

Slices of stories that touch different files can be built at the same time, each in its own git worktree and its own agent session:

  1. Check they don't collide.

    spry.py related on each work order, and the conflict check, show no shared file.

  2. Claim without switching, and add a worktree. 
    $ python3 spry/tool/spry.py claim SL-4 --no-switch
$ git worktree add ../shelf-sl-4 sl-4-due-date-in-library-time-zone
  3. Start a session there.

    Each worktree has its own gate stamp — its record of the last green run (.spry/green) — so one gate never vouches for the other.

  4. Merge one at a time.

    The second rebases if the first touched anything it touches — /spry:merge checks this.

The backlog helps here: a slice is listed as ready only when the slices it needs are closed, so a pair that can't be built side by side never shows up as two ready rows.

GitHub issues per slice

People outside the repository often follow issues, not files. Turn on slices.issue and every slice gets one:

  • Created at open, from the work order as agreed. Its body is frozen and says so — the slice file goes on changing, and the difference is the record.
  • At close, the close summary is posted as a comment.
  • The merge commit's Closes #n closes it.
  • spry check refuses an open slice without one.

Picking the next slice

/spry:slice-open with no ID reads Ready to build from the backlog. slices.pick decides how it offers them:

SettingBehaviourSuits
offer defaultThe first row, recommended, plus the next twoTeams happy to follow plan order
askThe first four rows, none recommendedTeams where outside things — a design, another team's date — often decide

Keeping everyone's view current

The backlog, coverage and done pages on the main branch are written by CI after each merge. On a branch they show the main branch as of CI's last run. For pages that match your own working tree:

$ python3 spry/tool/spry.py view    # writes them to .spry/view/
$ python3 spry/tool/spry.py hooks   # once per clone: refresh after each checkout or pull
$ python3 spry/tool/spry.py serve   # or browse them, and the whole plan, in a browser
