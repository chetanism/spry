Work as a team

spry runs the same for one person or ten — a team is a section of the config, not a separate setup. This page covers what changes when there are several people, and several agent sessions, working on one repository at once.

Roles and members

The team is listed in spry/spry.config.json. In the worked example, three people:

"team": {
  "members": [
    {"name": "Asha",  "github": "asha-k",   "roles": ["product"]},
    {"name": "Ravi",  "github": "ravi-dev", "roles": ["developer"]},
    {"name": "Meera", "github": "meera-qa", "roles": ["qa"]}
  ],
  "review": {
    "spry/plan/**/README.md":   ["product"],
    "spry/plan/**/checks.md":   ["qa"],
    "spry/plan/**/SL-*.md":     ["developer"],
    "src/**":                   ["developer"]
  }
}
  • Empty members means solo: no person is asked to review, approval is skipped at merge, and the plan is committed straight to the main branch — but a fresh agent still reviews every plan item and slice.
  • Roles decide who an item goes to. Product writes and reviews milestones down to stories; developers slice and build; QA writes and runs the checks.
  • Plan items go through pull requests when a team is configured and the path falls under a review rule — instead of being committed to the main branch.

Review routing and CODEOWNERS

GitHub's CODEOWNERS file is generated from team.review, so GitHub asks the right people to review each pull request:

$ python3 spry/tool/spry.py codeowners
# Generated by `spry.py codeowners` from team.review in spry/spry.config.json.
# Change that, not this file. Later lines win, as GitHub reads them.
/spry/plan/**/README.md @asha-k
/spry/plan/**/checks.md @meera-qa
/spry/plan/**/SL-*.md @ravi-dev
/src/** @ravi-dev

A fresh-eyes review still runs first; when it finishes, it names who else must read the PR — the roles team.review gives for its paths.

IDs and slice claims

Two sessions creating a story at the same moment could both take S-7. Two people could both start on SL-4. The mint setting says where an ID is taken and a slice is claimed:

mint: local defaultmint: main
CounterThe next number in your working treeThe main branch on the remote — the push is the lock
Two sessions, one numberPossible. check --base names it before the merge, and the later branch renamesCan't happen. A refused push fetches and tries again, up to five times
Claiming a sliceMakes the branch locallyWrites branch: and owner: on the slice on the main branch, and refuses when someone holds it, naming their branch
NeedsNothingA main branch that accepts a direct commit of documents

With mint: main, spry.py new takes the next number from the main branch on the remote, commits docs(plan): new S-7 … there without checking anything out, pushes it, and merges that commit into your branch — so the ID is final the moment you have it. Several items in one new share one commit and one push. Offline, or if the push is refused for any other reason, it stops and writes nothing; it never falls back to a local number.

$ python3 spry/tool/spry.py claim SL-4 --owner Ravi   # take it before writing the work order
$ python3 spry/tool/spry.py release SL-4             # give it back: planned again, branch empty

With mint: main, the backlog lists a claimed slice under In progress for everyone, so nobody else picks it up; with mint: local, only your own clone sees the claim until you push the branch.

Setting it up

Setup always commits with mint: local, because mint: main needs spry to already be on the main branch. If you chose main in the interview, switch it once setup is merged.

Slices side by side

Slices of stories that touch different files can be built at the same time, each in its own git worktree and its own agent session:

  1. Check they don't collide.

    spry.py related on each work order, and the conflict check, show no shared file.

  2. Claim without switching, and add a worktree — or, with a worktrees block, let /spry:worktree do it (below). 
    $ python3 spry/tool/spry.py claim SL-4 --no-switch
$ git worktree add ../shelf-sl-4 sl-4-due-date-in-library-time-zone
  3. Start a session there.

    Each worktree has its own gate stamp — its record of the last green run (.spry/green) — so one gate never vouches for the other.

  4. Merge one at a time.

    The second rebases if the first touched anything it touches — /spry:merge checks this.

The backlog helps here: a slice is listed as ready only when the slices it needs are closed, so a pair that can't be built side by side never shows up as two ready rows.

Worktrees

With two to four sessions running, you need to know where each worktree lives, which one is free, which database and ports each one uses, and which branch each rests on between slices. Add a worktrees block to the config and spry keeps track of all of that:

"worktrees": {
  "dir": ".claude/worktrees",
  "home_branch": "alt{index}",
  "max": 4,
  "setup": "tooling/worktree-setup.sh",
  "share": [".env.example"]
}
  • Your script isolates; spry hands out. spry.py worktree new makes a worktree on its home branch (alt1, alt2, …) at the main branch's head and runs setup there, with SPRY_WORKTREE (its index) and SPRY_WORKTREE_NAME set. The script creates the worktree's database, picks its ports and writes its .env. Falsify's slots run the same script, with SPRY_FALSIFY_SLOT set as well, so a slot never shares a database with the tree it runs from.
  • One session per worktree. In a new session, /spry:worktree claims one: by index, by name, or the lowest free one. A worktree another live session holds is never offered. A claim ends with its session (a /clear keeps it), and a claim whose session is gone, or has been silent for 12 hours, can be taken. The main checkout is never claimed: sessions that only plan share it.
  • Home between slices. After a merge, /spry:merge puts the worktree back on its home branch at the main branch's head. It can't check out the main branch itself, because the main checkout holds it.
  • Leftovers. spry.py worktree prune removes the scratch trees an interrupted falsify run left behind, and forgets worktrees you deleted by hand.

Watch them work

While a slice builds, its session can go quiet for half an hour. To see what each one is doing, run spry.py watch in a terminal of its own:

$ python3 spry/tool/spry.py watch
shelf1 #1 · sl-4-due-date                 │ shelf2 #2 · sl-6-renewals
claimed by pid 4121 · 42m                 │ claimed by pid 4388 · 18m
S-2 › SL-4 Due date · step 2 of 3 · Page  │ B-3 › SL-6 Renewals · open
14:02 step 1 of 3 committed (3f9c1a)      │ 14:20 gate red: lint
14:31 gate --fast green                   │ quiet for 22m

The tool writes those lines itself: each step's commit, each gate, falsify run and merge check, and each return home. They cost no tokens, and no session has to remember to write them. A worktree that has gone quiet past progress.quiet minutes is marked. Set progress.transcripts to "claude-code" and each panel also says what its session is doing now: working, running a command, waiting on a subagent, or waiting on you — and how long since it was last cleared.

Requests in GitHub issues

People outside the team — support, sales, a clinic manager — don't read the plan. They can ask for work where they already are: a GitHub issue. Anyone who cares can join the discussion there. When it is agreed, a developer or product owner asks spry to plan it, and from then on the issue shows where the work stands.

  1. Someone asks. Two plain-words forms, Ask for something new and Report a problem, go in .github/ISSUE_TEMPLATE/ at setup. They ask what is needed, who for, and an example — and warn against pasting anyone's private details.

  2. People discuss it in the issue's comments until it is agreed.

  3. spry plans it: /spry:story #42, /spry:bug #42, /spry:feature #42 — any planning skill takes an issue. It reads the issue and every comment as the starting draft, asks only what the discussion left open, leaves out anything private, writes the item and links it: issues: [42]. One issue can become several items; if part of it waits, the issue is told.

  4. The issue follows the work. One label at a time, and a short comment naming the items when it changes:

    LabelMeans
    spry:acceptedTaken into the plan; the details are being agreed.
    spry:readyPlanned and ready to be built.
    spry:in-progressBeing built.
    spry:doneBuilt and merged — ready to test once deployed.
    spry:declinedThe plan dropped it; the item says why.

  5. QA closes it after testing. spry never closes an issue. If testing finds a problem, /spry:bug #42 records it against the same issue, which goes back to in progress.

The labels are worked out from the plan, like every other status, by spry issues --sync. It only changes what is out of step, so it runs wherever it is cheap: CI on the main branch, after every /spry:merge, or on a schedule — a merge made some other way still reaches its issue. spry issues on its own shows each issue's stage. After the item is written, the plan is the record: a change asked for on the issue goes through the item's owner.

spry knows when work is merged, not when it is deployed. A project whose deploy script knows what it shipped can post on those issues itself — spry issues --json lists each one's items and stage.

Picking the next slice

/spry:slice-open with no ID reads Ready to build from the backlog. slices.pick decides how it offers them:

SettingBehaviourSuits
offer defaultThe first row, recommended, plus the next twoTeams happy to follow plan order
askThe first four rows, none recommendedTeams where outside things — a design, another team's date — often decide

Keeping everyone's view current

The backlog, coverage and done pages on the main branch are written by CI after each merge. On a branch they show the main branch as of CI's last run. For pages that match your own working tree:

$ python3 spry/tool/spry.py view    # writes them to .spry/view/
$ python3 spry/tool/spry.py hooks   # once per clone: refresh after each checkout or pull
$ python3 spry/tool/spry.py serve   # or browse them, and the whole plan, in a browser

Who built what

A slice's owner is the person who built it. /spry:slice-open sets it when the slice opens, from the person git says is at the clone — their name in team.members — and /spry:merge won't merge a slice without one. That makes a report of one person's work a plain read of the plan:

/spry:work-report Ravi last week

Each story, task and bug Ravi worked on gets two or three lines on what Ravi's slices did — written from their close summaries — then the slices by ID and title, then what Ravi is building now. Slices someone else closed under the same story are counted, not credited. The tool behind it is spry.py work Ravi --since 2026-10-19.

Slices from before owners were set

/spry:update to 0.29.0 fills them once from each pull request's author (spry.py owners --from-prs), shows you what it will write first, and lists what it couldn't fill.
