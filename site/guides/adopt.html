Adopt an existing codebase

Most teams don't start fresh. /spry:adopt puts spry around a codebase that already exists — it reads the code before asking anything, plans from the next piece of work rather than reconstructing the past, and never blocks a line of existing code.

What adopt promises

  • Nothing existing can fail it. spry check only reads spry/ and test names. Your current code, tests and CI keep working exactly as before.
  • No backwards planning. What is already built is described once, in spry/knowledge/codebase.md. The plan starts with what you will build next.
  • Existing tests are untouched. Only new tests cite acceptance criteria.
  • Nothing you have is deleted. Instructions, decision records and workflows are merged or moved; anything spry would replace is listed as a question, not removed.
> /spry:adopt members should be able to see their own loans online

The argument is optional: if you give one, it is the next piece of work and seeds the roadmap.

Step by step

  1. spry is copied in. The process files and the tool go into spry/process/ and spry/tool/, and a config file is started.
  2. The survey. Before any question, the agent reads the repository and writes what it finds into spry/knowledge/codebase.md, reporting each area as it goes:
    • stack, package manager, test runner, the commands that run the tests, and how long a full run takes;
    • the main areas of the code, one line each;
    • existing documents — README, docs/, decision records, CLAUDE.md or AGENTS.md;
    • external services, from dependency manifests and configuration;
    • domain words that recur in type and table names — candidates for the glossary.
    It only runs commands that read. It asks before running your test suite, which may be slow or need services.
  3. The interview — the same topics as a new project, but every question offers the surveyed answer for you to confirm. You correct; you rarely type from scratch.
  4. Existing material is folded in — see below.
  5. The rest is written and checked, exactly as for /spry:init, and you are asked before the commit.

What happens to what you already have

You haveWhat adopt does
A CLAUDE.md or AGENTS.mdMerges it into the new AGENTS.md. Lines that are not a pointer, a rule an agent breaks by default, or a rule no tool can check (AGENTS.md's admission test) move to spry/knowledge/conventions/ — never deleted.
Decision recordsOne question for all of them: move each to spry/knowledge/decisions/ as D-1, D-2… in their present order, text kept. You list any to drop.
CI workflowsspry's jobs are added beside them. A workflow that only checks something spry now does is listed as a question to remove — never removed by itself.
Your own agent skills or commandsOne with the same name or job as a spry skill is listed as a question to remove — two versions side by side means an agent may run the old one. The rest stay, and are recorded as local process changes.
TestsUntouched.
The first plan is small on purpose

After adopting, expect a roadmap whose near milestones (one to three) are about your next work, and a good codebase.md. That's the right start. The plan grows as you work, one level at a time — see Plan the work.

Coming from writ

If the project ran writ, spry's predecessor — you'll see a folder (usually canon/) holding BRD.md, ID-REGISTRY.md and a slice queue — adopt follows a longer path, in two halves:

  1. writ's own agent writes a mapping file first, canon/to-spry.md: the plan as a tree of titles, every traceable writ ID and what it becomes, what is done, and where each document goes. Nothing is investigated twice.
  2. A person reviews and approves it. Adopt stops until the file says Status: approved <date> by <name>.
  3. No work in flight. A half-built writ slice has no home in spry, so finish or park it first.
  4. Adopt builds the plan from the file on a branch, one commit per step, ending in one pull request. Each story already built gets one closed Built under writ slice, test citations are rewritten to spry's form, and — in the last commit, only after you have compared spry status with writ's last ledger and said yes — the writ folder is retired. Its records of what happened are kept under spry/history/.

The full mapping is in Coming from writ.

If it stops part-way

As with a new project, setup is finished only when spry/README.md exists. Run /spry:adopt again and it continues from the first unanswered topic; the survey already in codebase.md is not repeated.
