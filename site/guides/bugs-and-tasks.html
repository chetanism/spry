Bugs and tasks

Not all work is a story. A bug is something not working as the plan says; a task is technical work no story asks for — set-up, upgrades, refactors, infrastructure. Both hang off the plan tree where they belong, get built in slices like everything else, and neither counts toward its parent's progress.

Recording a bug

> /spry:bug F-1 the due date on evening receipts is a day early
  1. Find the parent. From the argument, or the agent asks which screen or story it's about.
  2. Duplicates first. The open bugs under the same feature are read before anything is written.
  3. The interview — what happens, what should happen, steps, where it was seen, who is affected.
  4. Reproduced by the reporter or the agent before it goes ready.
  5. Your yes, then spry check and a commit. spry offers /spry:slice <ID>.

The bug from the worked example:

severity: major
breaks: [S-1/AC-2]

## What happens
- A receipt printed after about 18:30 shows a due date one day earlier than 14 days from today.

## What should happen
- The due date is always 14 days from the day of the loan (F-1/R-2, S-1 AC-2).

## Steps to reproduce
1. After 18:30, lend book 9780141439518 to library card 1001.
2. Read the due date on the receipt → it is 13 days from today.

## Where
- Build a1c9e02, Riverside desk computer, Chrome.

## Impact
- Every loan made in the evening — about a quarter of all loans. Members may return books a day early or be told they are overdue when they are not.

Severity

  • blocker stops a release.
  • major a criterion or a feature rule fails.
  • minor anything else.

A bug that breaks a criterion

Name it in breaks: [S-1/AC-2]. If QA saw it on a build, they also add a fail row to the story's check log — that's what un-proves the criterion, so the story stops showing as done until the fix lands and QA logs a new pass for that criterion. See Checks for QA.

A bug's slices and their tests

A bug has no acceptance criteria of its own, so its tests name the bug instead: for example, a test called "B-1 prints the due date in the library's time zone". When the slice is closed, the tests proven to catch its safeguards are the ones that name B-1. See Falsify.

A bug can need more than one slice. B-1 has two: one to fix the calculation, and one to correct the due dates on loans already made — which waits for the first.

Recording a task

> /spry:task M-1 set up CI
Is it really a task?

If a user would notice the result, it's a story, and spry offers /spry:story instead. Tasks are for work whose value is to the team: the result shows up in a command that passes or a number that drops, not on a screen.

The worked example's task:

## Why
- No slice can prove its acceptance criteria until tests run on every pull request.

## What changes
- A pull request runs affected tests, spry check and the type check, in parallel.
- main runs every test, then spry index; a nightly job runs every test again.

## Done when
- A pull request with a failing test cannot show green.
- Affected tests on a typical pull request finish in under 3 minutes.

Done when is checkable: a command that passes, a number reached, a thing removed.

A task's slices and their tests

A task has no acceptance criteria either, so a test written for it names the task: "T-1 refuses a pull request whose tests failed". Often a task's safeguard is guarded by a test that was there before the task and names nothing; then its falsify control names that test file instead — "expect": ["tests/ci/gate.test.ts"]. See Falsify.

Why they don't count toward progress

A milestone's progress is about outcomes for the people it serves — epics, features and stories done. Counting bugs and tasks would let a milestone look further along because there was more to fix. They still show everywhere you'd look: in their parent's page, on the backlog — where, within a milestone, bugs come first, then tasks, then stories — and as "1 open bug" next to their parent's progress.
