Checks for QA

Tests prove a lot, but not everything — a printed receipt, a real device, the evening shift. /spry:test-scenarios writes the steps a tester follows by hand for each acceptance criterion, and the check log records what they saw. A passing check proves a criterion; a failing one un-proves it, test or no test.

When to write them

Once a story is ready — before it is built or while it is being built. Scenarios that can't run yet are written now and marked not ready, so they run the week they can.

> /spry:test-scenarios S-1

Without an ID, spry lists ready stories with no checks file and asks which one. The conversation is pitched at audience 4 on spry's 1–10 scale of how technical to be (Written for its reader) — screens, fields and messages, nothing internal.

The principle: a tester has what a user has

For most products that means a browser and an account — no terminal, no database, no server. A scenario never asks a tester to "insert a row" or "set the clock". Anything the product itself can't set up goes under Before you start, addressed to whoever prepares the environment.

How the session goes

  1. The agent reads the story, its feature's rules, and the story's notes for test data.
  2. The list first, steps later. You see one line per scenario — its criterion, type and whether it's ready — and cut it down with the agent before any steps are written. A session nobody finishes is not coverage.
  3. Before you start is written: what is needed and who provides it — accounts and what each may do, data that must exist, equipment, a second browser. A tester who learns three scenarios in that they needed a second account has lost the session.
  4. The scenarios, at least one per criterion, each with numbered steps.
  5. Read back with QA, adjusted, and committed as docs(qa): scenarios for S-<n>.

Anatomy of a scenario

From the worked example's checks.md:

### AC-3 · Book already on loan

**Type** negative · **Where** the desk · **Ready** yes

1. Signed in at the desk as the librarian, lend Ravi (card 1005) Persuasion (9780141439686)
   → "Lent to Ravi".
2. Scan Mei's card, 1006, and try to lend Mei Persuasion → "Already on loan to Ravi",
   and the book cannot be lent.
3. Scan Mei's card again → still "0 books on loan"; scanning Persuasion still shows it
   on loan to Ravi.
  • Heading — the criterion it checks, then a short name. One scenario may check several: ### AC-1, AC-3 · …. spry check fails on a scenario for a criterion the story doesn't have.
  • Type — happy path, negative, permission, another organisation, repeat, at once or boundary. The ways somebody gets it wrong are most of what a session is for. If a story's criteria only describe happy paths, the agent asks the owner for the missing criterion rather than guessing one.
  • Where — the part of the product, as a person would say it. Never a link or a route.
  • Ready — yes, or no and what it waits for.
  • Steps — what to do → what you should see, with the exact data to use.

Writing good steps

Not this

  • Press the Lend button
  • → it works
  • Assume a member already has three loans

This

  • Lend the book to Kiran
  • → "Lent to Kiran"; Kiran now shows "1 book on loan"
  • Start from a state the tester can reach, with its data named
  • Say what to achieve, not what to press. "Lend the book to Kiran" survives a redesign; "press Lend" is wrong the week the button moves.
  • What you should see must be something you could be wrong about. For a refusal, name what must not happen too — a refusal that half-saved the record is a bug. That's step 3 above.
  • Each scenario stands on its own. Scenarios that change data use their own, so they run in any order.
  • Boundaries only when the criterion has one. "3 books" → also try 2 and 4.

Logging a check

Each time a tester runs a criterion, they append one row to the Check log — the table at the end of the story's checks.md — and commit it (or ask the agent to add the row for them). Rows are never edited.

| Date       | AC   | Build   | By    | Result | Notes                                        |
|------------|------|---------|-------|--------|----------------------------------------------|
| 2026-10-04 | AC-2 | a1c9e02 | Meera | pass   | printed at 11:20                             |
| 2026-10-06 | AC-2 | a1c9e02 | Meera | fail   | printed at 19:05, due date one day early → B-1 |
  • Build is what was tested — a version, a commit, a deploy.
  • A fail names the scenario and what happened. A result nobody can act on is not a run.
  • The latest row decides. A pass proves the criterion when no test does. A fail un-proves it even if a test passes — a person saw it broken. Record a bug with /spry:bug and put its ID in the notes.
See it in the worked example

Meera's evening fail above is why story S-1 shows "not proven" even though its slice is merged and its tests pass. Bug B-1 names the criterion it breaks. When B-1 is fixed and AC-2 passes again, S-1 is done. See A worked example.

When a criterion is reworded

If a pull request changes a criterion's wording, spry check --base (which compares the branch with where it started; CI runs it on every pull request) names each scenario and check-log row that relied on the old wording and that the branch left as it was. Re-read them in the same pull request: a scenario updated to fit drops off the list, and a new run of the criterion logged since the branch started clears them all. A warning that stays is accepted by a person at merge.
