Test beyond the slice

A slice runs only the tests its change affects. Four skills cover the rest: the whole suite, an exploratory walk over the real product, a security audit and a pre-launch review. All four report and never fix — a finding becomes a bug or task that you approve.

/spry:test-all

Every test, on purpose, timed part by part.

/spry:explore

A seeded, replayable walk over a real, isolated instance.

/spry:security-audit

Access, input, data, secrets — against your rules.

/spry:prelaunch

A go / no-go before a release.

The whole suite — /spry:test-all

When: when you ask, or after a change to dependencies or to build or test configuration — where the affected-only run (the tests touching what the slice changed) can't tell what is affected. Never as a routine step of a slice or a merge: CI runs the full suite on the main branch and nightly.

  1. It says what will run — which parts, whether local services come up, and whether uncommitted changes are in the tree.
  2. Cheapest first, each part timed. spry check first, then each part from tests.parts (unit, integration…). Local services (a database, queues) are started only if they're down, and stopped only if this run started them — always then, even after a failure. Data is never removed.
  3. It keeps going after a failure, so one run names every broken thing.
  4. It reports.
test-all — 4m 12s
check        ok        2s
unit         ok       41s
integration  FAILED 3m 20s  2 of 164
  - src/loans/lend.test.ts › S-1/AC-3 refuses a book already on loan: expected AlreadyOnLoan
slowest
  38s  src/desk/LendPanel.test.ts
  • A failure is named, with whether it looks like this branch or something older.
  • Slow — a part over 60 seconds, or one file over a quarter of its part — is a finding.
  • Flaky — fails, then passes when that file alone is re-run once — is a finding, never a pass.
Never to get green

It never edits code or tests, and never skips, retries or quarantines a test to make the run pass.

Exploratory testing — /spry:explore

A good tester does three things a test suite doesn't: combines steps nobody wrote down together, runs them in orders nobody planned, and notices. /spry:explore does that against a real, running copy of the product — seeded (every random choice comes from one number, the seed), so any run can be replayed exactly.

The rules

  • Always an isolated instance — a second copy of the product on its own ports and data, never the one you're developing in. Every shell first loads the file named in explore.env in the config.
  • Report only. It edits nothing in the repository. The transcript lives in .spry/explore/<seed>/.
  • Predict before running. Every step writes down the expected outcome and the criterion it comes from (S-4/AC-2) first. A step with no prediction is not a test.

What you're asked

  1. Area — the whole product, or a milestone, epic or feature.
  2. Depth:
DepthStepsDoes
Sanity~15The main path plus four or five operators — is it broken right now?
Regular recommended~50Operators across the area's criteria, evidence read back
Deep~150Every criterion in the area once, plus interrupt and concurrency
Adversarial~300Hostile, until it finds something or the budget ends
  1. Seed — a new one, or paste one to replay.

The starting data needs two of everything that has a boundary — two organisations, two users with different roles — or the walk never tests isolation and passes for the worst reason.

The walk

Each step draws an operator and a target from the seed, predicts, runs, judges and records. The oracles — what each prediction is judged against — are the area's acceptance criteria plus the security and performance rules — kept true by spry check, so they can be trusted as written.

#OperatorWhat must hold
1Duplicate — the same action twiceOne effect, or a clear refusal of the second
2Concurrent — two actors, same target, at onceOne wins; no lost write, no half state
3Reorder — a later step before an earlier oneRefused, or the same end state
4Delay — wait past an expiry, a cut-off, a slotThe time rule applies at the moment of acting
5Skip — leave out a step the flow assumesRefused with a message naming what is missing
6Substitute — another user's, organisation's or item's IDRefused; nothing about the other is revealed
7Boundary — the limit, one below, one aboveExactly the criterion's line
8Malform — wrong type, empty, oversized, odd charactersRefused at the edge, cleanly, nothing stored
9Interrupt — stop mid-actionAll or nothing; a retry completes it once
10Change underneath — edit or delete what a flow is usingThe flow notices; no stale write
11Repeat until the limit — a rate or quotaThe limit holds and says so; recovery works
12Clock — midnight, month end, time zones, daylight savingDates land on the right day
13Cross-boundary — act from one tenant or role on anotherRefused; even a suggestion is a leak
14Read the evidence — logs, audit rows, queues, emailsEach record exists, is right, leaks nothing

Operator 12 is the kind of walk that catches a bug like B-1 in the worked example — a receipt printed after 18:30 showing a due date a day early. (There, QA found it by hand.)

Before anything is reported

It assumes the walk is wrong first. On a mismatch it re-reads the criterion, reproduces on fresh data with the shortest sequence, then classifies:

ClassMeansReported?
defectThe code disagrees with a clear criterionYes — offers /spry:bug
gapThe code is defensible and no criterion decides itYes — asks who decides
walk errorThe walk misread a criterion, the data, or an intended refusalTranscript only
expectedDocumented behaviour that only looks wrongTranscript only

Every finding carries seed:counter — that pair is the whole reproduction. A finding worth re-checking later is offered as a QA scenario via /spry:test-scenarios.

First run

The explore settings — how to start, stop and seed the isolated instance — can stay unfilled at setup. The first /spry:explore stops and fills them in with a developer.

Security audit — /spry:security-audit

Scope: the whole product, a milestone, an area or a branch's diff. The report lives in spry/knowledge/audits/, and the previous audit's open findings are re-checked first. It reads the code, not only the documents:

AreaLooks for
AccessEvery route, query and screen that returns data: who may call it, checked server-side
Sign-in and sessionsExpiry, reset flows, rate limits, what a stolen session reaches
InputValidation at the edge; injection through queries, shell, templates, file paths
Personal dataWhat is stored, logged, sent to third parties; the project's numbered security rules (SEC-1, SEC-2…)
SecretsIn code, history, logs, client bundles; how they reach production
DependenciesThe stack's audit command; unmaintained packages
External servicesWhat is sent to them, and what is trusted from them

Every security rule gets a line: held (where it's enforced) or broken (a finding).

Pre-launch review — /spry:prelaunch

A go / no-go before the first release, or a major one:

  • every story of the milestone done, none unproven;
  • no open blocker bug, and every open major one accepted by name;
  • a security audit of this scope within the last milestone, its findings closed or accepted;
  • every rule marked as checked by hand, checked on this build;
  • production configuration and secrets set; nothing development-only switched on;
  • migrations run forward cleanly; a backup exists and a restore has been tried;
  • someone is told when it fails — logs, alerts and error reports reach a person;
  • spry/ and other non-product files are not in the build;
  • the constraints still hold: dates, legal, privacy notices.

The verdict is go, go with conditions (listed) or no-go (the blockers). It never deploys.

After either review

You're asked which findings become bugs or tasks and which are accepted, and by whom. Each finding's action column then holds an ID or accepted — <name>.
