Record what you learn

An agent forgets everything when the session ends. A decision made in a chat, a convention explained once, a quirk of an outside service found the hard way — all gone by tomorrow, unless they're written where the next session will look. /spry:record puts each one in the right file, findable from an index.

> /spry:record decision store the due date on the loan

One thing per run. If the kind isn't obvious from what you say, the agent asks.

Search first

Before writing anything, the agent searches the existing knowledge. If an entry already covers the same thing, it extends that one rather than adding a second — two entries about one thing soon disagree.

Decisions

A decision records the options not taken and why. That's the part people need most and remember least. From the worked example:

summary: the due date is saved when a book is lent, never worked out again later
decided_by: [Ravi, Asha]
affects: [F-1, S-1, S-2]

## Context
- F-1/R-2 sets a loan at 14 days; Asha expects the length to change (holiday periods).
- If the due date is worked out from the loan date, changing the rule would move every
  existing due date.

## Decision
- loans.due_on is set once, when the book is lent, and never recalculated.

## Rejected
- Compute lent_on + loan_days on read — changes past loans when the rule changes.
- Store the loan length on each loan — same result with more arithmetic in every query.

## Consequences
- Changing the loan length affects only new loans.
- Overdue means due_on < today, nothing else (S-2).
  • affects matters. When anyone plans or changes F-1, S-1 or S-2, the conflict check reads this decision automatically.
  • Decisions are never edited to say something new. To change one, write a new decision; the old one's state becomes superseded by D-<n>.
  • summary is the line the index shows — so it should state the fact, not "about due dates".

Conventions

One rule per bullet, each with its reason after a dash:

- Return Result<T, E>; never throw for a rule the desk shows to a librarian — the desk must
  show every refusal, and a thrown error loses its type.
- Take today: LocalDate as a parameter; never read the clock inside domain code — tests and
  B-1 need control over the date.
…

The reason is what lets someone tell, later, whether the rule still applies.

External behaviour

What a service's documentation says and what it does are often different. Each file records what was seen, when, the evidence, how confident you are, and whether it was observed or documented. When the two disagree, observed wins — and the file says so.

title: Open Library — lookups are rate-limited without a User-Agent
summary: about 100 lookups per 5 minutes, then HTTP 429
source: observed
confidence: medium
…
## Behaviour
- GET https://openlibrary.org/isbn/<isbn>.json without a User-Agent header: HTTP 429 after about 100 requests in 5 minutes.
- With a User-Agent naming the app and a contact email: no 429 seen in 1,000 requests.
- The documentation asks for a User-Agent but states no limit.

Should it go in AGENTS.md too?

AGENTS.md is read by every agent on every task, so every line in it costs something. A line earns its place only if it's a pointer, a rule an agent breaks by default, or a rule no tool can check. The agent offers a Must not line only when an agent would break the rule by default and no tool can check it — for example, "Never compute a due date from the loan date — read loans.due_on (D-1)." If the file is at its line budget, it offers what to move out instead. More in Knowledge and size.

When to reach for it

  • At the end of a slice — closing lists follow-ups, and a decision found while building is one of them.
  • After an argument that got settled.
  • The second time you explain the same thing to an agent.
  • When an outside service surprises you.

The new entry's line in the index appears when CI regenerates the indexes on the main branch.
