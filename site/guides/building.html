Build a slice

/spry:slice-open is where code starts — but not before a written plan. The agent writes a work order first, checks it against everything else in flight, opens a draft pull request with it, and then builds. It only stops to ask when the plan does something hard to undo. To plan and build in separate sessions — say, on different models — use /spry:slice-plan and /spry:slice-build.

Pick a slice

> /spry:slice-open SL-2
# or, with no ID, pick from the backlog's "Ready to build"
> /spry:slice-open

With no ID, the agent reads the first rows of Ready to build (spry.py backlog --section ready --rows 4 --plain) and asks which to open. By default it recommends the first row and offers the next two. A project can set slices.pick: ask in its config instead: then it lists the first four and recommends none, because what else bears on the choice — a design not settled, an outside team's date — is the person's call. See Work as a team.

What happens

  1. Claim it.

    spry.py claim SL-2 runs before anything else, so nobody spends an hour on a work order someone else is writing. It creates and switches to the branch sl-2-refuse-over-limit. With mint: main set (IDs and claims taken on the main branch), the claim is pushed to the main branch, and refused if someone already holds the slice. Not going ahead after all? spry.py release SL-2 gives it back.

  2. Read.

    spry.py brief SL-2 --as slice-open first: one call for the slice, the criteria it covers, its story and feature, what the conflict check starts from, and the procedure itself. If the session is already past slices.fresh_context — it built and merged the last slice, say — it stops and asks you to /clear and run /spry:slice-open SL-2 again. Then every knowledge file the change could touch — conventions, decisions, how external services behave, security and performance rules — and the code.

  3. Write the work order.

    Every section of the slice file's Work order, before any code. What goes in each is below.

  4. Conflict check.

    Against the story, its siblings, decisions — and every open slice, including which files each one touches. Findings and how each was resolved are written into the work order. See The conflict check.

  5. Design review — when the project turned it on, and always under /spry:slice-plan.

    A new agent reads the work order and looks for choices that would be hard to undo. See The design review below.

  6. Show the summary and the plan.

    The agent asks for approval only when the plan does something hard to undo, departs from the story, or the design review found a Blocker. Otherwise it goes straight on.

  7. Open the pull request.

    The slice goes open, with you as its owner; the work order is the branch's first commit, before any code. It's pushed, and a draft pull request titled SL-2 Refuse a loan over the limit is opened, its body generated from the slice file. One command does all of it — spry.py publish SL-2 open — and it changes nothing if check refuses the work order.

  8. Build.

    In the same session, unless you said to open only — one step at a time, each committed by spry.py step SL-2 --commit after its fast checks, never by hand. When every step is committed, the agent stops and asks you to /clear and run /spry:slice-close SL-2, so the close starts in a fresh session instead of re-reading the whole build on every request. The slice file and the commits carry everything it needs.

Plan and build in separate sessions

Writing the plan and closing the slice take the most judgement. Building to a concrete plan takes the least. Two skills split /spry:slice-open in half, so each half can run in its own session, on the model you pick with /model:

/spry:slice-planlarger model→ /spry:slice-buildsmaller model→ /spry:slice-closelarger model→ /spry:mergesmaller model, your yes
  • /spry:slice-plan does steps 1–7 above and stops before any code. The design review always runs here, whatever the config says, because whoever builds the plan will not know why it says what it does. Each file's plan is written concretely enough for a smaller model to follow.
  • /spry:slice-build switches to the slice's branch and builds what the work order says. When the plan turns out wrong or short, it stops and asks instead of guessing. When everything is built and committed, nothing pushed, it stops for a fresh close.
  • Run /clear between them. spry never picks the model for you.

Run a slice unattended

Typing /clear and the next skill is easy to skip, and a session that carries the plan into the build, or the build into the close, pays to read all of it again on every request. One command does the hand-over for you:

$ python3 spry/tool/spry.py run SL-2
→ plan · /spry:slice-plan SL-2 · a fresh session · planned
✓ plan session · 6m10, 41 turns
→ build · /spry:slice-build SL-2 · a fresh session · 0 of 2 steps
✓ build session · 14m02, 87 turns
→ close · /spry:slice-close SL-2 · a fresh session · not reviewed, 0 falsify rows
? close · 9m40, 52 turns
! the close session needs you

ASK
1. Post the review and fix its 2 findings?
   …

answer it: spry.py run SL-2 --answer "<your answer>"
  • Each skill gets a session of its own, started headless. Between them the tool reads the slice file and the branch's commits to see what comes next; it never takes a session's word for it.
  • It stops whenever a session asks. The three decisions that are yours stay yours: a plan that does something hard to undo, a question the work order cannot answer, the review's findings. Answer with --answer and the same session carries on, then the run does.
  • It never merges. The run ends at a pull request ready for review and tells you to run /spry:merge. The merge hook refuses a merge from any session the run started.
  • You give it its permissions. Nobody is there to approve a command, so a session can only run what you have allowed — in .claude/settings.json, or in run.args. spry adds none. A session refused a call stops the run and names the command.
  • Start small. Try it on a slice of one step, with run.review left at ask. Set run.review to b once you trust the review's fixes; a clean slice then runs from planned to ready without stopping.

Summary2–4 bullets anyone on the team can read: what will be done, and what a person will see

Must notThe decisions and rules this change could break, linked, each with one line on how

Here is SL-2 from the worked example — an open slice, work order only:

### Summary

- The desk refuses a loan when the member already has 3 books, or has an overdue one.
- The refusal shows on the desk as soon as the library card is scanned, before any book.

### Covers

- [S-2](README.md) AC-1, AC-2

### Steps

#### Step 1 · Refuse a loan over the limit

Covers: AC-1, AC-2

- `src/loans/eligibility.ts` — `canBorrow(memberId, today): Result<void, AtLimit | Overdue>`; reads `loans.due_on` (D-1)
- `src/loans/lend.ts` — call `canBorrow` before inserting; same errors
- `src/desk/LendPanel.tsx` — show the refusal after the card scan; disable **Lend**
- `src/loans/eligibility.test.ts` — unit tests below
- `db/seed.ts` — members `1003` (3 loans) and `1004` (one overdue)

### Must not

- [D-1](../../../../../knowledge/decisions/D-1-store-the-due-date.md) — overdue means `due_on < today`, from the stored date.
- [PERF-1](../../../../../knowledge/performance.md) — card scan to screen under 1 s: one query for both checks.

### Tests

- "S-2/AC-1 refuses a member with 3 books on loan"
- "S-2/AC-2 refuses a member with an overdue book"

### Demo

```bash
pnpm db:reset && pnpm db:seed && pnpm dev
open http://localhost:3000/desk   # card 1003 → "Limit reached"; card 1004 → "Return overdue book first"
```

### Conflict check

- Checked 2026-10-07 against: S-2, S-1, SL-1, D-1, security, performance, open slices (none)
- Overlap: SL-1's `lend.ts` already returns `LendError` → `AtLimit` and `Overdue` added to that union, not a new type
- Dependency: B-1 changes how "today" is worked out → `today` is a parameter here, so B-1's fix applies to both
Why a test's name carries the criterion

A criterion counts as proven when a test whose name contains S-2/AC-1 exists — in its title, docstring or parametrize id. A citation in a comment or in code proves nothing, and a skipped test proves nothing either. That is how spry knows a story is really done without anyone typing it. More in Status is derived.

When the agent stops to ask

A person decides three things: the criteria, the merge, and anything hard to undo. While building, only the third comes up:

  • a database migration;
  • a public API or event shape;
  • a new dependency;
  • deleting data or files;
  • breaking a Must not rule.

Everything else runs as one piece of work, because the checks stand in for a person watching. See Where a person decides.

Light slices

Every reading costs about the same whatever the size of the slice, so a small slice pays the most for them. Across 195 slices in two projects, one under 300 changed lines cost three times as much per line as one of 1,300–2,500 — and on those small slices the design review and the review at close each found a Blocker once in twenty.

You can mark work as light. A light slice has no design review, and one reviewer reads its whole diff at close, not one for each step and one for the seams. Nothing else changes: the agent still stops to ask before anything hard to undo, every criterion still needs its test, falsify and the gate still run, and you still merge.

  • You ask for it. Put rigor: 0 in the front-matter of a story, feature or epic, and every slice under it is at level 0. rigor: 1 on an item below takes it back out. "rigor": 0 in the config covers the whole project. The agent never sets it.
  • The tool checks the slice fits. Light holds while the slice changes at most 300 lines of code (slices.light.max_lines) and touches no migration or SQL file (slices.light.never — add your own: auth, billing, a public API).
  • A slice that outgrows it is reviewed in full at close, and merge-check warns that nobody read its design before the code.
  • See whether it is safe. spry pace has a By level table: light slices against the others of the same size — what they cost, what the review found, and the bugs filed later. Start with one epic of small work, and widen it when that table gives no reason not to.

The design review

The agent itself judges whether a choice is hard to undo, and nobody checks that judgement. The review at close comes too late for it: by then the code exists, and that review asks whether the code matches the work order, not whether the work order was right. A project can set slices.design_review to true in its config to have the work order read before anything is built. It is off by default for /spry:slice-open; /spry:slice-plan always runs it.

  • Who reads it. One new agent, which did not write the work order and is not told the reasoning behind it. It gets the slice, its story and feature, AGENTS.md, and the lists of decisions and conventions. It changes nothing.
  • What it looks for.
    • A choice the plan makes without asking that would be hard to undo: a data model, the shape of an API, where one module ends, who owns a record, what happens on failure.
    • Something the plan assumes that no story, feature or decision says.
    • An option that is harder to build and better for the product.
    • In a slice built in steps, what one step needs from an earlier one.
  • What it reports. Each finding is a Blocker, a Should or a Nit, and names the line of the work order it rests on. The agent opening the slice checks each one and drops what does not hold.
  • What happens next. A Blocker becomes a question to you, before any code. A Should the agent accepts changes the work order there and then.

The result is kept as the last section of the work order:

### Design review

- 1 Blocker, 4 Should — 1 asked
- Blocker: the limit is stored per branch, not per member — asked; per member

With the switch on, merge-check warns when a slice has no such section, or when it records more Blockers than questions asked. It is a warning for you to accept at the merge, never a block. spry pace SL-2 prints the counts beside the slice's time.

What it costs

One agent and about five minutes a slice. In the project it came from, the reviews of three slices found 11 Blockers: each was a hard-to-undo choice the plan had treated as an easy one. Small slices on settled ground gain little from it.

If the session ends mid-slice

Nothing is lost. The work order, the branch and the draft pull request are all in git, so any agent — in a new session, or a different tool — reads the slice file and carries on: /spry:slice-build SL-2 picks up the build, /spry:slice-close SL-2 the close.
