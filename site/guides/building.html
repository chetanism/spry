Build a slice

/spry:slice-open is where code starts — but not before a written plan. The agent writes a work order first, checks it against everything else in flight, opens a draft pull request with it, and then builds. It only stops to ask when the plan does something hard to undo.

Pick a slice

> /spry:slice-open SL-2
# or, with no ID, pick from the backlog's "Ready to build"
> /spry:slice-open

With no ID, the agent reads Ready to build from the backlog and asks which to open. By default it recommends the first row and offers the next two. A project can set slices.pick: ask in its config instead: then it lists the first four and recommends none, because what else bears on the choice — a design not settled, an outside team's date — is the person's call. See Work as a team.

What happens

  1. Claim it.

    spry.py claim SL-2 runs before anything else, so nobody spends an hour on a work order someone else is writing. It creates and switches to the branch sl-2-refuse-over-limit. With mint: main set (IDs and claims taken on the main branch), the claim is pushed to the main branch, and refused if someone already holds the slice. Not going ahead after all? spry.py release SL-2 gives it back.

  2. Read.

    The story and its feature, every knowledge file the change could touch — conventions, decisions, how external services behave, security and performance rules — and the code.

  3. Write the work order.

    Every section of the slice file's Work order, before any code. What goes in each is below.

  4. Conflict check.

    Against the story, its siblings, decisions — and every open slice, including which files each one touches. Findings and how each was resolved are written into the work order. See The conflict check.

  5. Show the summary and the plan.

    The agent asks for approval only when the plan does something hard to undo or departs from the story. Otherwise it goes straight on.

  6. Open the pull request.

    The slice goes open, with you as its owner; the work order is the branch's first commit, before any code. It's pushed, and a draft pull request titled SL-2 Refuse a loan over the limit is opened, its body generated from the slice file. With slices.issue on, a GitHub issue is created first from the work order.

  7. Build.

    In the same session, unless you said to open only. Then the agent goes on to close the slice.

The work order

SectionWhat it holds
Summary2–4 bullets anyone on the team can read: what will be done, and what a person will see
CoversThe criteria this slice proves, as links — never restated
PlanOne bullet per file and what changes in it
Must notThe decisions and rules this change could break, linked, each with one line on how
TestsAt least one per criterion, each name containing the criterion, like S-2/AC-1
DemoSteps anyone can copy and paste to see it working — no values to fill in by hand
Conflict checkWhat it was checked against, each finding, and its resolution

Here is SL-2 from the worked example — an open slice, work order only:

### Summary

- The desk refuses a loan when the member already has 3 books, or has an overdue one.
- The refusal shows on the desk as soon as the library card is scanned, before any book.

### Covers

- [S-2](README.md) AC-1, AC-2

### Plan

- `src/loans/eligibility.ts` — `canBorrow(memberId, today): Result<void, AtLimit | Overdue>`; reads `loans.due_on` (D-1)
- `src/loans/lend.ts` — call `canBorrow` before inserting; same errors
- `src/desk/LendPanel.tsx` — show the refusal after the card scan; disable **Lend**
- `src/loans/eligibility.test.ts` — unit tests below
- `db/seed.ts` — members `1003` (3 loans) and `1004` (one overdue)

### Must not

- [D-1](../../../../../knowledge/decisions/D-1-store-the-due-date.md) — overdue means `due_on < today`, from the stored date.
- [PERF-1](../../../../../knowledge/performance.md) — card scan to screen under 1 s: one query for both checks.

### Tests

- "S-2/AC-1 refuses a member with 3 books on loan"
- "S-2/AC-2 refuses a member with an overdue book"

### Demo

```bash
pnpm db:reset && pnpm db:seed && pnpm dev
open http://localhost:3000/desk   # card 1003 → "Limit reached"; card 1004 → "Return overdue book first"
```

### Conflict check

- Checked 2026-10-07 against: S-2, S-1, SL-1, D-1, security, performance, open slices (none)
- Overlap: SL-1's `lend.ts` already returns `LendError` → `AtLimit` and `Overdue` added to that union, not a new type
- Dependency: B-1 changes how "today" is worked out → `today` is a parameter here, so B-1's fix applies to both
Why a test's name carries the criterion

A criterion counts as proven when a test whose name contains S-2/AC-1 exists — in its title, docstring or parametrize id. A citation in a comment or in code proves nothing, and a skipped test proves nothing either. That is how spry knows a story is really done without anyone typing it. More in Status is derived.

When the agent stops to ask

A person decides three things: the criteria, the merge, and anything hard to undo. While building, only the third comes up:

  • a database migration;
  • a public API or event shape;
  • a new dependency;
  • deleting data or files;
  • breaking a Must not rule.

Everything else runs as one piece of work, because the checks stand in for a person watching. See Where a person decides.

While building

DoWhy
Check each change with spry.py gate --fastRuns spry check and the fast checks (format, lint, types — cheapest first). No tests, so it takes seconds
Run spry.py gate (with affected tests) only when a test's answer is what you needIt adds the affected tests — minutes on a big project — and it runs once more at close anyway
Never run the full suiteCI runs it on the main branch and nightly; /spry:test-all runs it when someone asks
Push only at closeEach push runs CI again
Never run spry.py index on a branchThe progress pages are written only on the main branch, so branches never conflict over them. For fresh pages locally, use spry.py view
Never edit the work order to match the codeThe close summary says what differed. The difference is the record
 
$ python3 spry/tool/spry.py gate --fast   # after each change
$ python3 spry/tool/spry.py gate          # when you need the tests' answer

A departure from the plan is noted for the close summary's What changed. A new rule learned along the way goes into the project's knowledge later, with /spry:record.

If the session ends mid-slice

Nothing is lost. The work order, the branch and the draft pull request are all in git, so any agent — in a new session, or a different tool — reads the slice file and carries on.
