Keep spry yours

No process fits every team on day one. spry's process is copied into your project so you can change it — and every change is recorded, so a later update keeps it instead of overwriting it. These five skills cover living with spry over time.

SkillUse it when
/spry:process-changePart of the process doesn't fit your team
/spry:updatespry has gained something since you set it up
/spry:contributeYour project built something other projects would use
/spry:compactspry check says a file is over its line budget
/spry:toneReplies are too technical, or not technical enough, for you

Change the process — /spry:process-change

Say the change in a sentence — "QA approves every story, not product" — and the problem it answers. The agent then makes it complete:

  1. Finds every file it touches — process files, templates, the config, AGENTS.md, the CI workflow, your own skill copies — by searching for the words the change alters, not just the obvious file.
  2. Shows the list, one line per file and what changes. Applies it only on your yes, all in one change.
  3. Records it as a row in spry/knowledge/process-changes.md: date, change, kind local, files, why. That row is what lets an update keep it.
  4. Commits chore(process): … — through a pull request on a team — and offers /spry:contribute if other projects would want it too.

Documents already written to an older template change only if you ask.

The tool is never edited locally

spry/tool/spry.py is replaced whole on every update. A change that needs the tool is contributed instead, and worked around in the process text meanwhile.

Take updates — /spry:update

Updates are offered entry by entry, adapted, never transplanted. spry keeps a changelog of every change a project may want (CH-1, CH-2…), and your config remembers the last one you considered (spry_baseline).

  1. The newest spry first.

    An installed plugin is fixed at its version, so the agent updates the plugin before reading anything. Afterwards, run /reload-plugins so the other skills use the new copy too.

  2. Where you stand.

    Your baseline, your own process changes, and which files differ from spry's.

  3. Each new entry, checked before you're asked:
    FindingMeans
    cleanThe files differ only by spry's change
    local changeYou changed a file it touches — a merge is needed
    already hereYou already do this
    conflictsIt contradicts a local change — you decide which wins
  4. One ask per entry not already here: take as is, take adapted (it says how), or skip (it says what you lose). You can answer for a group: "skip everything about CI".
  5. Port what you chose, in your own paths, commands, IDs and words. Templates update, but existing documents change only if the entry says to migrate them.
  6. Verify and record: check and index, baseline moved forward, one row per entry — taken, adapted or skipped, with why. Committed after asking.
> /spry:update

Give back — /spry:contribute

When your project has built something — a process change, a skill, a stack profile — it can offer it back. The agent judges each candidate honestly: would another project use it unchanged in shape? Is it already in spry? What evidence is there — how long it's been used, what it caught? Product rules and domain words are not contributions.

  • Everything private is stripped first. The draft is rewritten in generic terms, then spry.py scrub lists every product name, person, handle, glossary term, email and URL still in it, until nothing is left that isn't deliberate.
  • It's filed as a GitHub issue — never a pull request — and only after you've read the whole thing and said yes. Nothing leaves your machine before that.
  • A row of kind offered, with the issue link, goes into process-changes.md.

Trim what grows — /spry:compact

Files grow with every slice, record and interview; nothing else takes lines out. AGENTS.md, knowledge files, plan READMEs and slice files each have a line budget (AGENTS.md: 150 lines by default), and spry check says when one is over. Compact brings it back under by moving whole sections to the files that own them — it moves text, it doesn't edit it.

What the section isGoes to
Why one option was chosenA decision record, and the line points at it
How code is written hereThe area's conventions file
How a service really behavesThat service's external-behaviour file
A security or performance rulesecurity.md or performance.md
A procedure with stepsThe process file that runs it
What a feature or story requiresThat plan item
What you used to do and stoppedDeleted — git keeps it, and a stale rule reads as live
  • It shows the moves first — one line per section and where it goes — and moves nothing until you say yes.
  • No fact is lost, and a one-line pointer is left where each section was.
  • AGENTS.md keeps only pointers, rules an agent breaks by default, and rules no tool can check. Its admission test, Project, Must not and Where things are sections never leave.
  • One commit per destination, on a branch — and on a team, a PR whose body tables every move and the line counts before and after.
  • What it won't touch — a section with no honest home, a line it doubts — is reported for you to decide.

Why budgets exist at all: Knowledge and size.

See where the time goes — spry pace

A slice takes longer than it should, and it's rarely the agent's writing. spry pace splits each slice's time into what filled it, so you can see which part of the process, the config or the tests to change.

$ python3 spry/tool/spry.py pace                       # the page: .spry/view/pace.md
$ python3 spry/tool/spry.py pace SL-42                 # one slice in detail
$ python3 spry/tool/spry.py pace --compare 2026-10-20  # before and after a day, a CH-n or a commit

Each second goes into one of these:

  • the agent, thinking and writing
  • checks: the gate, falsify, and tests or fast checks the agent ran itself
  • other tools: spry, git, gh, the local services, polling loops
  • waiting on you, or a question it asked you
  • you, busy in another session
  • waiting on a background task, another session, or a scheduled wake-up

A gap longer than pace.away (30 minutes) counts as away and is left out.

The page also shows:

  • each slice and its phases (open, build, close, review, fixes, merge)
  • how long each gate step took
  • the slowest single calls
  • flags for what stands out
  • Did a change help? Every row in process-changes.md and every commit to the config marks a point. The page sets the slices after each point against as many before it.
  • Nothing to switch on. The gate, check, falsify and merge-check each add a line to a step log. Claude Code's own session logs are read only when you ask, so nothing runs while you work.
  • Yours only. Everything stays in .spry/ in your clone and is never committed. A passing merge-check keeps the slice's numbers there, after Claude Code deletes old session logs.
  • spry serve shows the page under Pace.

Set your tone — /spry:tone

Every document has an audience level from 1 (no technical knowledge) to 10 (an engineer in this codebase), and the agent's replies follow the document it's working on. A product owner writing a story gets plain words; a developer closing a slice gets paths and commands. Override it for yourself:

> /spry:tone 3      # plain words, no paths or code
> /spry:tone 8      # paths, types, commands
> /spry:tone reset  # follow each document again
> /spry:tone        # say the current tone and where it comes from

The setting is yours only — stored in .spry/tone, which is never committed. More in Written for its reader.
