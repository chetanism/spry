Set up a new project

/spry:init turns a paragraph about what you want to build into a working spry project: a roadmap, the first milestones, the rules your product must follow, the words your team uses, and CI (the automatic checks GitHub runs on every push) that checks it all. It is one interview, run once, and it can stop and pick up again at any point.

New code or existing code?

Use /spry:init when the project has little or no code yet. If there is already a codebase, use /spry:adopt instead — it reads the code first, so you confirm answers rather than type them.

Before you start

  • spry is installed — see Installation.
  • You are in the project's repository, connected to GitHub (a git remote). Setup reads the repository's default branch — the main line others merge into — from it rather than assuming main. New words are in the glossary.
  • Have a description ready — what you are building, for whom, and why now. A paragraph is enough; a pasted document or a file path works too. Everything after is drafted from it.
  • Setup is an interview of ten topics, a few questions at a time. If you are interrupted, nothing is lost — see If it stops part-way.
> /spry:init Shelf replaces the paper lending register at small community libraries…

How the interview works

spry never hands you a blank form. For each topic it drafts an answer from what it already knows and asks you to confirm or correct it. The rules it follows, in every interview:

  • At most three questions per reply, numbered, with lettered options and one marked (recommended) — so "2b" is a complete answer.
  • Coarse to fine. The outline of a topic is agreed before its details.
  • Written down at once. Each answer goes into a file as soon as you give it, never held in the chat. A later session — or another agent — resumes by reading the files.
  • "I don't know yet" is fine. It is recorded under Open questions with who answers and by when, and the interview moves on. Nothing is invented to fill a gap.
  • "You decide" is fine too. spry takes its recommended option and records it as an assumption, so you can revisit it.

Until the stack topic the tone is plain — written for someone with no technical background. The stack topic is for a developer; if none is present, it is skipped and noted as an open question.

Topic b is the one that makes spry fit a team rather than a single person. If you are on your own, leave the team empty — no person is asked to review and approval is skipped at merge, but a fresh agent still reviews every plan item and slice (/spry:review). You can add people later. See Work as a team.

Why security and performance come up so early

Every later plan item and every slice is checked against these rules before it is ready. A rule like "a library card number never appears in a log" written now is one an agent cannot quietly break in month three.

What gets written

When the interview ends, your repository holds:

AGENTS.md                  # what every agent reads first — kept under 150 lines
CLAUDE.md                  # one line: @AGENTS.md
.github/workflows/spry.yml # CI: spry check, fast checks, tests
.github/CODEOWNERS         # who reviews what (skipped when solo)
spry/
  README.md                # the entry point for people — written last
  spry.config.json         # levels, IDs, team, test commands, budgets
  BACKLOG.md  COVERAGE.md  DONE.md   # progress pages, filled in by CI
  plan/README.md           # the roadmap
  plan/M-1-…/README.md     # first milestone, as a draft
  knowledge/               # glossary, security, performance, constraints, …
  process/                 # spry's rules, copied in
  tool/spry.py             # the tool, copied in

A few things worth knowing about these files:

  • The process and the tool are copied into your project, not linked. Every agent and CI run uses the same copy, with no plugin needed. /spry:update brings in later improvements.
  • spry/ is kept out of your deploy — setup adds it to .dockerignore or your stack's build ignore.
  • .spry/ is git-ignored. It holds personal and cached things: the search index, your tone setting, the last green test run.
  • Existing CI is never replaced. spry's jobs are added beside it.

Here is what the roadmap looks like in the worked example:

# Roadmap

## Where we are going

- Shelf replaces the paper lending register at small community libraries.
- First for one library — Riverside Reading Room — then for any library that signs up.
- Success: the desk lends books and records returns without paper, and members see their own loans.

## Later

- M-2 Members see their loans online
- M-3 Any library can sign up

Finishing

  1. Checks run once. spry check and spry index run, and anything they report is fixed. From then on, CI on the main branch keeps the progress pages current.
  2. You see a summary, grouped as plan · knowledge · process · CI, in plain words.
  3. You are asked before anything is committed. The commit is chore(spry): set up spry. If you chose to take IDs on the main branch (topic b), the setup commit still says mint: local; switch it to main once setup is on the main branch.
  4. Optional: git hooks (small scripts git runs after a checkout or pull). spry offers spry.py hooks, run once per clone. After a checkout or pull that changed the plan or a test, it refreshes your local copy of the backlog, coverage and done pages.
  5. Next step: /spry:milestone M-1 to define the first milestone properly. See Plan the work.

If it stops part-way

Setup counts as finished only when spry/README.md exists — it is written last on purpose. If a session ends before that, run /spry:init again: it reads the config and whatever was written, and continues from the first topic with no answer. Nothing you answered is asked twice.

If spry/README.md already exists, /spry:init stops and offers /spry:status instead — it never sets a project up twice.

Things that commonly go wrong

  • Trying to plan everything up front. Name all your milestones, but describe only the next one to three. spry is incremental by design — later milestones are a line each until you get to them.
  • Skipping the glossary. If your team says "patron" and "member" for the same person, an agent will too, and two words soon become two concepts. Pick one, ban the other. spry check then fails on a banned word anywhere in the plan.
  • No developer for the stack topic. That's fine for now — the topic is recorded as an open question. But slices can't run tests until it is filled in.
