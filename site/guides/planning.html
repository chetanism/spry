Plan the work

Planning in spry is a short conversation per item, written for the person who will read it. You define one level at a time — a milestone, then an epic, then a feature, then its stories — and never more than you need right now. No big requirements document up front.

The four planning skills

All four run the same procedure; each one only knows its own level.

SkillSettlesLeaves for laterWritten for
/spry:milestoneWhy, a done when a person can check, what is in and out of scope, constraintsits epicseveryone, including people who never read code audience 2
/spry:epicWhy, who it is for, done when, in and out of scopeits featureseveryone audience 2
/spry:featureSummary, who uses it, how it works step by step, numbered rules, out of scopeits storiesproduct, QA, designers, developers audience 3
/spry:storyOne story per file, each with acceptance criteria as Given / When / Thenits slicesproduct and QA first, developers second audience 3

The audience number (1 = no technical knowledge, 10 = an engineer in this codebase) sets how the document is written and how the agent talks to you while writing it. At 2 or 3 there are no file paths, no code and no bare IDs — "S-2 Loan limit", never just "S-2". More in Written for its reader.

A small project can drop a level

Levels are chosen during setup. Many small projects skip epics and put features straight under milestones.

A planning session, step by step

> /spry:feature E-1
  1. Find the parent. Every level except a milestone needs one — given as the argument, or the agent lists the candidates with their titles and asks. If the parent is still a draft, it says so and asks whether to go on, since its scope may still move.
  2. Read before asking. The parent and everything above it, every sibling at this level, the glossary, the knowledge files the project always checks (by default the security and performance rules and the decisions index), and — for a story — the feature's numbered rules.
  3. Create the draft. The tool picks the next ID, the right folder and the template. The document exists before the first question, so every answer is written into it straight away.
  4. The interview, one section at a time in the template's order: at most three questions per reply, each with a drafted answer to confirm. It stops when every required section has content a reader could act on; empty optional sections are deleted rather than left as "TBD".
  5. The conflict check. The draft is compared with everything it could clash with — duplicates, overlaps, contradictions, things it depends on, glossary clashes. See The conflict check.
  6. Your yes. You see a short summary and are asked to mark it ready. Only then does it change state, pass spry check, and get committed as docs(plan): <ID> <title>.
  7. A fresh review, offered. One line offering /spry:review <ID> — a new agent that didn't write the item reads it against its parent. Solo, it's the only second pair of eyes you have. See Reviews with fresh eyes.

On a team, when the item's folder is under a review rule in the config, step 6 opens a pull request for the people who review plan documents instead of committing straight to the main branch.

What a finished item looks like

Here is part of a feature from the worked example. Notice what is not written in it: no stories (the stories table below it is generated), no code, no database tables — just enough for product, QA and design to agree on.

## Summary

- A librarian lends a book to a member by scanning the member's library card and the book.

…

## How it works

1. The librarian scans the member's library card → the desk shows the member's name and current loans.
2. The librarian scans the book → the desk shows the title.
3. The librarian presses Lend → the desk confirms and prints a receipt with the due date.

## Rules

- R-1 A member may have at most 3 books on loan at once.
- R-2 A loan lasts 14 days; the due date is printed on the receipt.
- R-3 A book can be on loan to only one member at a time.
- R-4 A member with an overdue book cannot borrow another until it is returned.

…

## Conflict check

- Checked 2026-09-30 against: E-1, F-2, glossary, security, performance, D-1
- Term: draft said "check out" → "lend", per the glossary
- Contradiction: Asha's notes allowed overdue members to borrow; the desk's paper rule
  does not → R-4 added (Asha, 2026-09-30)

The numbered rules matter: stories cite them (F-1/R-2) instead of restating them, so a rule lives in one place.

Writing stories

One /spry:story run can create several stories under the same feature. Each story is one thing a person does, with its acceptance criteria — the checkable statements of what "done" means. They are the most important thing you write in spry, because tests are named after them and QA checks them by hand. They have their own guide: Write acceptance criteria.

A story with more than six criteria is offered a split before the interview goes on.

When the interview drifts

You sayspry does
"You decide" / "whatever's standard"Takes its recommended option and records it as an assumption under Open questions
More detail than was askedWrites it down, and skips the questions you've already answered
"I don't know yet"Records it under Open questions — who answers, by when — and moves on
Starts describing stories while defining a featureNotes them as Later in its reply, not in the document, and offers /spry:story at the end
A new word for somethingAdds a glossary row — or, if it's a second word for an existing concept, uses the glossary's term and adds yours to Don't say

Changing a plan item later

Plans change, and that is fine — git history is the record. Edit the document, re-run the conflict check if its scope moved, and commit. Two things are protected:

  • ready needs a dated conflict check with nothing still marked → open; spry check refuses it otherwise.
  • Changing an acceptance criterion that a test already cites is warned about, and if the same branch changes code too, the merge waits for the story's owner to approve. See Changing criteria after slicing.

done is never written on any item. It is worked out from merged slices and proven criteria — see Status is derived.
