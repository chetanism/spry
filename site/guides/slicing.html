Split a story into slices

A slice is the unit an agent builds and a person reviews: one small change, one pull request. /spry:slice takes a story the team has agreed on and proposes how to cut it, so nobody ends up reviewing a 3,000-line pull request the agent wrote in one go.

What a slice is

Two tests decide whether something is a good slice:

  • One reviewable change. A reviewer can read the whole pull request in one sitting.
  • One visible change. Its demo shows something that was not there before — a screen, a refusal, a printed date.

A slice covers one or more acceptance criteria of one story, and between them a story's slices cover all of its criteria. A slice under a task or a bug covers its Done when or the behaviour it fixes instead. Each slice is a single file, SL-<n>-<slug>.md (the slug is the title in lowercase words joined by dashes), sitting in its parent's folder.

plannedwritten by /spry:slice→ openwork order, branch, draft PR→ closedset in the PR's last commit

A slice can also be dropped. Because closed is set in the pull request's last commit, a closed slice on the main branch always means a merged one.

When to run it

  • The story (or task, or bug) is ready — its owner has said yes to the criteria. spry refuses to slice a draft, because the criteria are what the slices will be built and tested against.
  • If the parent waits on something unfinished (its blocked_by list — the items it waits for), the agent says which, and asks whether to plan anyway.
> /spry:slice S-2

What happens

  1. The agent reads first.

    The story, its feature's rules, the project's coding conventions and decisions, and the code the change will touch.

  2. It proposes the slices in one reply.

    For each: a title, the criteria it covers, and one line on the visible change. They are ordered so each builds on the last, and the agent says which ones need an earlier one — its code, its data, its screen — and which could be built at the same time.

  3. You approve or adjust.

    Merge two, split one, reorder. This is a developer conversation, so expect paths and code names.

  4. The slice files are created.

    One spry.py new slice with a --title per slice, which picks the next IDs and the right folder. Only the Summary, covers and blocked_by are filled in now. Everything else waits for opening the slice.

  5. Checked and committed.

    spry check runs, and the commit is docs(plan): slices for S-2.

What gets written

In the worked example, bug B-1 (Due date a day early on evening receipts) was split into two slices. The second one needs the first, so it says so:

---
id: SL-5
title: Correct due dates on loans already made
state: planned
owner: Ravi
…
covers: []
…
blocked_by: [SL-4]
…
---
# SL-5 · Correct due dates on loans already made

## Work order

### Summary

- Loans made in the evening before the fix get their due date moved one day later.
- A member who was told a book is overdue a day early is no longer shown as overdue.

Because SL-5 is blocked by SL-4, the backlog lists SL-4 under Ready to build and SL-5 under Blocked, naming what it waits on. Two people never pick up a pair that can't be built side by side.

Needs, not just comes after

Put a slice in blocked_by only when it truly needs the earlier one's code, data or screen. A slice that merely comes later in the story's order has no blocker — leaving it free lets someone else build it at the same time.

How big should a slice be?

spry doesn't set a line count. The agent judges against the two tests above, and you correct it. Some signals — rules of thumb, not checked by spry:

Sign (rule of thumb)Usually means
The demo needs three separate things to showToo big — split along the visible changes
Nothing visible changes yetToo small, or it belongs in a task — fold it into the slice that shows it
One slice covers every criterion of a big storyCheck it can still be reviewed in one sitting
A migration plus the screens using itOften two slices: the data change, then the screen

What can go wrong

  • A criterion no slice covers. The backlog lists the story under Needs slicing until every criterion is covered by some slice.
  • A circle of blockers. spry check refuses one, and refuses a blocker that was dropped — it would never finish.
  • The story changes after slicing. That is allowed — git history is the record — but the tool warns when a criterion a test already cites is reworded. See Status is derived.
