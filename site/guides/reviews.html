Reviews with fresh eyes

The agent that wrote the code is the worst one to review it — it shares every assumption it made. /spry:review hands the work to a new agent that carries nothing from the session that wrote it. Solo, it is the second pair of eyes you have no teammate for. On a team, it reads before a teammate does.

What can be reviewed

> /spry:review SL-2      # a slice's pull request
> /spry:review S-3      # a plan item, with or without a PR
> /spry:review 42        # any pull request
> /spry:review           # the current branch's PR
KindKnown byThe question it asks
Slicea branch sl-<n>-…, or SL-nIs this what the work order (the plan written before any code) said, and nothing it said not to do?
Plan (a milestone, epic, feature, story, bug or task)every changed file is under spry/, and none is a sliceDoes it elaborate its parent without extending it?
Otheranything elseDoes the diff do what the title says, and nothing it doesn't mention?

Several targets can be reviewed together; each gets its own new agent, run in parallel.

What "fresh" means

  • A new agent, never the session that wrote the work, and never a fork of it (a copy that carries that session's memory).
  • Its prompt holds only the target and its kind, the review rules, and the shape of the report. Why the work was written as it was is left out on purpose — that reasoning is what's being tested.
  • It reads and comments. It never checks a branch out, edits, pushes, approves (unless told to) or merges. The one exception: on a solo plan item with no PR, it applies the fixes you accept. It reads files straight from the remote branch, so a session mid-slice is left untouched.
  • A second review after fixes gets another new agent, which writes its own findings before reading the earlier ones, then says which still stand.
  • An agent that can't start sub-agents asks you to run /spry:review in a new session.

What it checks

A slice

  1. It reads For the reviewer first — a short section the tool writes at the top of the PR body: the criteria in words, any that changed, what falsify couldn't show, what QA checks by hand. Then the work order, then the diff.
  2. Plan: every file the plan named changed as described; any other file is explained in What changed.
  3. Must not: each rule the work order lists as one this change could break still holds.
  4. Tests: at least one per covered criterion, each citing it, each asserting what the criterion's Then says — not something nearby.
  5. Falsify: the tool broke each safeguard on purpose; every row should read caught (a test noticed), or carry a reason the reviewer accepts. Reviewed during close there are no rows yet, and it says so.
  6. Conventions for the areas the diff touches.
  7. Demo: run if it can run locally — and if not, it says it didn't.

A plan item

The rule everything serves: the parent is elaborated, never extended. It reads the item, its parents, its siblings, the glossary and the decisions that bind it, then looks for:

  • Fidelity — anything the parent didn't ask for, or contradicts;
  • The code, where it's already built — every sentence a tester will act on, checked against what the product actually does;
  • Where a tester will trip — a criterion that can't fail, two behaviours in one, a precondition QA can't set up, a word that differs from the screen;
  • Words missing from the glossary, or on its "don't say" list;
  • Who decided — an open question the drafter answered, or a criterion changed without its owner;
  • an honest conflict check.

Any other PR

Claims match the diff; every changed behaviour has a test; conventions; risk around inputs, permissions, secrets and deleted or migrated data; and a behaviour people see, changed with no slice behind it — reported as a Should, naming the slice, bug or task it should have been.

Findings and the ask

Each finding has a line, a severity — Blocker Should Nit — what's wrong and why, and the replacement text wherever the fix is wording. Every finding is verified before you see it: the reviewer opens the line it rests on. An agent's claim is a lead, not evidence. (A review once reported that the browser blocks a blank email. The input had no required. One look would have caught it.)

Then one question carries the whole review through:

1. What next?
   a. Post, fix every Blocker and Should as found, then merge (recommended)
   b. Post, and fix — stop before the merge
   c. Post only
   d. Neither

a and b are offered only on your own slice or plan PR. a is recommended when every fix is the finding's own suggestion; c when a fix is a choice for the author. The fixes are made by your session — never by the reviewing agent, except on a solo plan item with no PR — and only what was accepted. A fix that turns out to need more (another file, a design choice) is not made; you're asked about it.

How comments are posted

  • One review, one inline comment per finding, anchored on exactly the lines its suggestion replaces.
  • Wording fixes carry a GitHub suggestion, so the author applies them in one click.
  • spry.py review-check checks the review before it's posted: every anchor on a line the diff shows, suggestions closed, none overlapping, none a no-op.
  • On your own PR, only COMMENT. GitHub refuses approve or request-changes there — and solo, every PR is your own.
  • With no PR (a solo plan item committed straight to the main branch), the findings are shown, and the reviewer applies the accepted ones as one commit.

How comments read

Comments go out to the author, in the tone of the document reviewed: a story PR in plain words, a slice PR naming paths. Say what's wrong, why, and recommend one way.

Instead of

  • "AC-2 is not in the feature."

Write

  • "The feature never asks for this. The product does it, though: a member with an overdue book is stopped at the desk. Recommendation: keep it, and add it to the feature first."
