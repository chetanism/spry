Close and merge a slice

When the code is written, /spry:slice-close turns "the agent says it's done" into evidence: a summary written from the diff (the lines the branch changed), a review by a fresh agent, proof that the tests notice the safeguards, and one run of the gate — the project's checks and the affected tests. Then /spry:merge merges — only on your yes.

The close, at a glance

Rebase→ What changed→ Proof→ Follow-ups→ Reviewyou answer its first question→ Falsify→ Gate→ Ready for review
the agent runs ita person decidesthe result

Normally /spry:slice-open runs this for you once the code is built; type it yourself for a slice you opened only, or picked up in a new session. New words — rebase, squash, trailer — are in the glossary.

The order matters. The review comes first and the slow proof last, so falsify and the gate each run once, on the code that merges. A review fix made after the gate would mean a second gate.

> /spry:slice-close
# with no ID, it closes the open slice whose branch you're on

Closing, step by step

  1. Rebase.

    Everything committed, then git fetch; if the main branch moved, rebase onto it — replay the branch's commits on top of the latest main branch. gate --fast passes. The gate later stands for the code that merges, so the rebase comes before it, not after.

  2. What changed.

    The agent compares the diff with the work order's Plan and writes only the differences, and why. If it matches the plan, the section is deleted.

  3. Proof.

    Every criterion the slice covers has a test that cites it by name — or the agent tells QA which ones need a manual check, as a [Test] item for them.

  4. Follow-ups.

    Bugs, tasks and decisions found along the way are created now, with real IDs, and listed.

  5. Review.

    Committed and pushed; the draft PR's body refreshed from the slice file. Then /spry:review: a new agent, with none of this session's reasoning, reads the PR against its work order. You answer its first question, one choice for what happens next: a post its comments, fix every blocker and should, then merge; b post and fix, but stop before the merge; c post only; d neither. Accepted fixes are applied before falsify; on c or d the close goes on to falsify with nothing fixed.

  6. Falsify.

    Each safeguard the slice added is broken on purpose, one at a time, and the tests citing its criteria are run. They should fail. Details below.

  7. Gate.

    spry.py gate: check, fast checks, affected tests. If it fails, fix and run again — it repeats only what the fix could change.

  8. Mark it closed and ready.

    state: closed and closed: today's date, committed with a Slice: SL-n trailer (a labelled line at the end of the commit message), pushed; the PR body refreshed with both parts; the PR marked ready for review. With a GitHub issue, the close summary is posted as a comment on it.

  9. Merge — only through /spry:merge.

    If your answer to the review was a (post, fix, then merge), the close runs it now. Otherwise the PR is ready for it, and a teammate may still review.

Falsify

A test that passes proves little: it would also pass if it tested nothing. Falsify proves the tests notice. The tool drafts a plan from the source lines the branch added — one control per guard, comparison or error — each with a mutation that removes it:

  • a guard made never true;
  • a comparison's boundary flipped (>= ↔ >);
  • a throw or raise deleted.

Never negation: negating a guard also breaks the normal path, so any test "catches" it. That is a false catch.

$ python3 spry/tool/spry.py falsify suggest SL-1
$ python3 spry/tool/spry.py falsify run .spry/falsify/SL-1.json --dry-run
$ python3 spry/tool/spry.py falsify run .spry/falsify/SL-1.json --record SL-1

The run restores every file, even on Ctrl-C, and writes the results into the slice. SL-1 from the worked example — its third control first survived; a test was added and falsify run again, which replaced that row with caught. What changed in the close summary keeps the story:

skippedThe control can't run here (a clock, a network)Write skipped — <reason>; a person accepts it at the merge
The diff decides, not the agent

The agent can add controls, never drop one. At merge time the tool drafts the list again from the diff and blocks if any control has no row. A slice that adds no source line at all — only tests or documents — has nothing to falsify.

The full design is in Falsify.

Merging

> /spry:merge SL-2
# or a PR number; with none, the current branch's PR

Every step runs, every time — each exists because skipping it once went wrong.

  1. Checks are green.

    Red or pending → stop. Nothing on the platform may stop a bad merge, so this step is the only guard.

  2. The slice is ready.

    spry.py merge-check blocks when a control the diff adds has no falsify row, when a row says only survived with no reason, when a criterion was changed together with code without the story owner's approval (criteria_approved_by:), or when the slice isn't closed with a date and a PR number. Softer issues — a survivor with a reason, a criterion with no test — are marked ! and carried to the ask.

  3. The PR body matches the slice file.

    Refreshed if they differ. The file is the source; the body is never edited by hand.

  4. Approval.

    With a team configured, the PR must be approved. Solo projects skip this.

  5. The base hasn't moved under it.

    If the main branch gained commits touching the same files, the green checks are against an old base: rebase, push, start again. It also looks for an ID the branch and the main branch both took.

  6. The ask.

    One line: what merges, and each ! item for you to accept. It merges only on a yes in this conversation, for this PR — or on your earlier fix, then merge answer, if nothing new has come up.

  7. Squash.

    All the branch's commits become one commit on the main branch, with a commit message from spry.py merge-message: the subject, the summary, and Slice:, Parent: and Covers: trailers. A squash keeps nothing else, so the trailers live in the commit.

  8. After the merge.

    The main branch is pulled. If it moved under the PR with code the PR's checks never saw, the agent waits for CI on the main branch. If the progress pages are stale and no CI run will write them, it writes them. Then it reports what is now unblocked.

When CI never ran

A billing lock, used-up minutes or an outage can stop CI from starting at all. A check that never ran is neither green nor red. Then the gate stands in for CI, on the PR's exact head: if it's green, the ask says CI did not run (reason); gate green locally, you accept it, and the squash commit carries a CI: trailer saying so. This is decided fresh for every merge — CI that was down yesterday may be up.

What the commit looks like

For SL-1 in the worked example, merge-message prints:

SL-1 Record a loan (#9)

- A librarian can lend a book from the desk: scan card, scan book, press **Lend**.
- The loan is saved with its due date, a receipt prints, and a book already on loan is refused.

Slice: SL-1
Parent: S-1
Covers: S-1/AC-1, S-1/AC-2, S-1/AC-3
Never

Force-push the main branch, merge with --admin to skip checks, or merge a PR you haven't named.
