Skills

A skill is a command you type into your agent — /spry:story, /spry:slice-close. Each one runs one step of the work by following a process file in your project. This page lists all 25, grouped by when you reach for them.

How to read each entry

Audience is how technical the conversation and the document are, from 1 (no technical knowledge) to 10 (an engineer in this codebase) — see Written for its reader. Arguments are optional unless shown in angle brackets; leave them out and the skill asks or picks the obvious one. In other agents the names differ slightly (spry-slice-open in Cursor, for example) — see Use another agent.

Five skills only run when you type them — the agent never starts them on its own: init, adopt, update, contribute and prelaunch. They set up, change the whole project, or send something out.

Set up

/spry:init

Sets up spry in a project that has little or no code yet. It interviews you — product and the people who use it, team, plan shape, roadmap, constraints, security, performance, external services, stack and tests, and the words you use — then writes everything a project needs.

  • When: once, at the start of a new project. For existing code, use adopt.
  • Arguments: a high-level description of what you are building, or a path to a file holding one.
  • Audience: 3 — until the stack questions, which are for a developer.
  • Writes: spry/spry.config.json, the roadmap and first milestones, knowledge files (glossary, security, performance, constraints, external services), the backlog, coverage and done pages, AGENTS.md, CLAUDE.md, a CI workflow, CODEOWNERS for a team, and spry/README.md last.
  • Stops part-way? Run it again; it resumes from the first topic with no answer.
  • Guide: Set up a new project.

/spry:adopt

Puts spry around a codebase that already exists. It surveys the code first — stack, test commands, main areas, existing documents, external services, domain words — and offers what it found for you to confirm, instead of asking from scratch. No existing file can fail spry's checks, so it blocks nobody.

  • When: once, on a project that already has code.
  • Arguments: the next piece of work, optional — it seeds the roadmap. The plan starts from the next work, not from what is already built.
  • Audience: 5.
  • Writes: everything init writes, plus spry/knowledge/codebase.md. Existing instructions are merged into AGENTS.md; existing decision records move to spry/knowledge/decisions/; existing CI is added to, never replaced; existing tests are untouched.
  • From writ: a project that ran writ is planned from a mapping file writ's agent writes first — Coming from writ.
  • Guide: Adopt an existing codebase.

Plan

The four planning skills share one procedure: find the parent, read everything around it, create a draft, interview into it, run the conflict check, and mark it ready on your yes. Each defines its own level only — never the level below.

/spry:milestone

Defines one milestone with the product owner: why it matters, what "done" looks like in terms a person can check, what is in and out of scope, and constraints. Does not define its epics.

  • When: planning the next big outcome.
  • Arguments: a milestone ID to continue (for example one init drafted), or a title. Empty → it offers the roadmap's Later lines.
  • Audience: 2.
  • Writes: spry/plan/M-n-<slug>/README.md.
  • Guide: Plan the work.

/spry:epic

Defines one epic under a milestone: why, who it is for, done-when, and scope. Does not define its features.

  • Arguments: the parent milestone ID and a title. Without a parent, it lists the milestones and asks.
  • Audience: 2.
  • Writes: E-n-<slug>/README.md inside the milestone's folder.
  • Note: a small project can drop the epic level in its config; features then sit straight under milestones.
  • Guide: Plan the work.

/spry:feature

Defines one feature: a summary, who uses it, how it works step by step, numbered rules (R-1, R-2 …) that stories cite, and what is out of scope. Does not write its stories.

  • Arguments: the parent epic (or milestone, without epics) and a title.
  • Audience: 3.
  • Writes: F-n-<slug>/README.md inside its parent's folder.
  • Guide: Plan the work.

/spry:story

Writes the stories of one feature with the product owner and QA. Each story has acceptance criteria in Given / When / Then form, each one something a person using the product can observe. It asks QA's question as it goes: "how would you check this by hand?"

  • When: a feature is ready to be broken into stories.
  • Arguments: the parent feature and a title. One run can write several stories — it offers the list of titles first.
  • Audience: 3.
  • Writes: S-n-<slug>/README.md per story. A story with more than six criteria is offered a split.
  • Guide: Write acceptance criteria.

/spry:bug

Records a bug against the feature or story it breaks: what happens, what should, how to reproduce it, where, its impact and severity (blocker, major, minor). It reads the open bugs under the same feature first, to catch duplicates.

  • When: someone reports something not working as the plan says.
  • Arguments: the feature or story ID, and what goes wrong.
  • Audience: 4.
  • Writes: bugs/B-n-<slug>/README.md under its parent. A bug that breaks a criterion names it in breaks. Bugs do not count toward their parent's progress.
  • Guide: Bugs and tasks.

/spry:task

Records technical work no story asks for — set-up, upgrades, refactors, infrastructure — under the milestone or epic it serves: why, what changes, how to tell it is done, and the risks. If a user would notice the result, it offers /spry:story instead.

  • Arguments: the milestone or epic ID, and the work.
  • Audience: 7.
  • Writes: tasks/T-n-<slug>/README.md. Tasks do not count toward progress.
  • Guide: Bugs and tasks.

Build

/spry:slice

Splits a ready story, task or bug into planned slices. Each slice is one change a reviewer can read in one sitting, with a demo that shows something that was not there before. It proposes all the slices in one reply — which criteria each covers, and which need an earlier one — and creates them on your approval.

  • When: a story is ready to be built.
  • Arguments: <story, task or bug ID>. Without one, it lists ready items with no slices and asks.
  • Audience: 8.
  • Writes: one SL-n-<slug>.md per slice, in state planned, with only its summary, covers and blocked_by. No branch, no code.
  • Guide: Split a story into slices.

/spry:slice-open

Opens a slice and builds it. It claims the slice, writes the work order (summary, plan per file, must-not rules, tests, demo), runs the conflict check against open slices and the project's rules, creates the branch and a draft pull request, and then builds — asking first only when the plan does something hard to undo or departs from the story.

  • Arguments: a slice ID. Without one, it reads Ready to build on the backlog and offers the first row (or lists four, with slices.pick: ask).
  • Audience: 8 — except the work order's summary, which anyone can read.
  • Writes: the slice file's Work order, the branch sl-n-<slug>, a draft PR whose body comes from the slice file, and — with slices.issue on — a GitHub issue. Then the code and tests.
  • Guide: Build a slice.

/spry:slice-close

Closes a slice whose code is finished. In order: rebase, write What changed from the diff, confirm every covered criterion has a citing test (or name the manual checks QA owes), create follow-ups, get a fresh-eyes review on the draft PR and apply the accepted fixes, falsify the safeguards the slice added, run the gate once, and mark the PR ready. It merges only through /spry:merge — and runs that at its end when you answered post, fix, then merge to the review.

  • Arguments: a slice ID; without one, the open slice on the current branch.
  • Audience: 8.
  • Writes: the slice file's Close summary (what changed, falsify table, follow-ups), state: closed and closed: <date>, the PR body, and a comment on the slice's issue if it has one.
  • Guide: Close and merge a slice.

Review and merge

/spry:review

A review by fresh eyes — a new agent that did not write the work and carries nothing from the session that did. It reviews a slice's PR against its work order, a plan item against its parent, the code and the glossary, or any other PR. Every finding is verified on its line before you see it; on your yes, each is posted as an inline comment, with a suggested change wherever the fix is wording.

  • When: a PR or a newly written plan item is ready for review — solo or on a team.
  • Arguments: PR numbers, slice IDs or plan item IDs; several at once are reviewed in parallel. Without one, the current branch's PR.
  • Audience: 8.
  • Writes: nothing in your branch. It posts comments only on a yes, and only COMMENT on your own PR. On your own PR, one answer can be post, fix, then merge — the session that ran the review does the fixing and merging, never the reviewing agent.
  • Guide: Reviews with fresh eyes.

/spry:merge

Merges a slice's PR safely. Every step, every time: checks green, merge-check passes, PR body current, approval (on a team), base not moved under it, no ID taken twice. Then one ask listing anything a person must accept, a squash merge with the slice's trailers, and a look at the main branch afterwards.

  • Arguments: a PR number or slice ID; without one, the current branch's PR. It never guesses between two.
  • Audience: 8.
  • Writes: the squash commit on the main branch. Afterwards it re-tests only if the main branch gained code the PR's checks never saw, refreshes the progress tables when CI did not, and reports what is unblocked.
  • Never: merges a red or pending PR, merges without a yes for this PR, or uses --admin. When CI never ran at all, the gate on the PR's head stands in — you accept that at the ask, and the commit says so.
  • Guide: Close and merge a slice.

QA and testing

/spry:test-scenarios

Writes the steps QA follows by hand to check each acceptance criterion of a story — what to set up first and who provides it, the exact data, and what you should see at each step. The list is read back and cut with QA before any steps are written.

  • When: once a story is ready, before or while it is built.
  • Arguments: <story ID>; without one, it lists ready stories with no checks file.
  • Audience: 4.
  • Writes: the story's checks.md. An existing one is extended, never rewritten; its check log is never reordered.
  • Guide: Checks for QA.

/spry:test-all

Runs the whole test suite on purpose: spry check first, then each part in order, timed, with local services started only when they are down and stopped only if this run started them. Names failures, slow tests and flaky ones.

  • When: when a person asks — for example after a dependency or configuration change. Never as a routine step of a slice — CI runs the full suite on the main branch.
  • Arguments: a part name, optional.
  • Audience: 8.
  • Writes: nothing. Report only — it never fixes, skips, retries or quarantines a test.
  • Guide: Test beyond the slice.

/spry:explore

Exploratory testing by an agent: a seeded, replayable random walk over a real, isolated instance of the product. It combines actions in orders nobody wrote down, predicts each step's outcome from the area's acceptance criteria before running it, and ends with a report of defects and gaps.

  • Arguments: area, depth (sanity ~15 steps, regular ~50, deep ~150, adversarial ~300) and a seed to replay. It asks for any you leave out.
  • Audience: 8.
  • Writes: nothing in the repository — a transcript in .spry/explore/<seed>/. A defect becomes a bug only on your yes.
  • Needs: the explore section of the config filled in. It never falls back to your development instance.
  • Guide: Test beyond the slice.

/spry:security-audit

Reviews the product, a milestone, an area or a branch for security problems against the project's security rules — access, sign-in and sessions, input, personal data, secrets, dependencies, external services — looking at the code, not only the documents.

  • Arguments: the scope: product, a milestone ID, an area, or a branch.
  • Audience: 8 while working, 6 in the report.
  • Writes: a report in spry/knowledge/audits/. Findings become bugs or tasks you approve — it never fixes anything in passing.
  • Guide: Test beyond the slice.

/spry:prelaunch

A go / no-go review before a release: every story proven, no open blocker bugs, a recent security audit, manual rule checks done, production configuration and secrets, data migrations and backups, alerting, and that spry/ is not in the build.

  • Arguments: the milestone ID or release name.
  • Audience: 8 while working, 6 in the report.
  • Writes: a report with a verdict — go, go with conditions or no-go. It never deploys and never changes production configuration.
  • Guide: Test beyond the slice.

Knowledge

/spry:record

Records what the project learned so the next person — or the next agent session — finds it: a decision and the options rejected, a coding convention the code does not make obvious, how an external service actually behaves, or a security, performance or constraint rule.

  • Arguments: decision, convention or external, and what. It asks when the kind is unclear.
  • Audience: 6–7.
  • Writes: one file under spry/knowledge/, found from its INDEX.md. It searches first and extends an existing entry rather than adding a second.
  • Guide: Record what you learn.

/spry:compact

Brings a file back under its line budget — AGENTS.md first — by moving whole sections to the knowledge, plan or process files that own them, leaving a one-line pointer behind. It moves text; it does not edit it, and no fact is lost.

  • When: spry check reports a file over budget, or AGENTS.md has grown long or repetitive.
  • Arguments: a file, optional; by default every file check reports over budget.
  • Audience: 7.
  • Writes: the moves, on a branch, one commit per destination — shown to you first and applied only on a yes.
  • Guide: Keep spry yours.

Keeping spry current

/spry:process-change

Changes how this project runs spry — a rule, a template, a step — in every file the change touches at once, and records it so a later /spry:update keeps it.

  • When: part of the process does not fit the team.
  • Arguments: the change, in a sentence.
  • Audience: 7.
  • Writes: the process files, templates, config, AGENTS.md or CI it touches, plus a row in spry/knowledge/process-changes.md. It never edits the tool — a tool change is offered to spry with contribute.
  • Guide: Keep spry yours.

/spry:update

Brings the project up to date with what spry has gained since it was set up. It first updates the installed plugin, then offers each changelog entry since the project's baseline, explained in the project's own terms: take it as is, take it adapted, or skip it. Your own process changes are kept.

  • When: whenever you want what is new — it changes nothing until you have answered every ask.
  • Arguments: none.
  • Audience: 7.
  • Writes: the chosen changes to spry/process/, a whole new spry/tool/spry.py, the config's spry and spry_baseline, and one row per entry in process-changes.md.
  • Guide: Keep spry yours.

/spry:contribute

Offers spry something this project built — a process change, a skill, a stack profile. It judges honestly whether another project would use it, strips everything private (product, people, domain words, emails, URLs), and files an issue on spry after you have read it and said yes.

  • Arguments: what to contribute, optional; otherwise it looks for candidates.
  • Audience: 7.
  • Writes: a draft in .spry/ (never committed), the GitHub issue on your yes, and a row in process-changes.md. Never a pull request, a fork, or a push to spry's repository.
  • Guide: Keep spry yours.

Status and tone

/spry:status

Shows how far the project has got — done versus total at every level, open slices and open bugs — and what to pick up next, explained at your tone. Everything comes from the tool's output; it never invents progress.

  • Arguments: an ID for one branch of the plan, or a level such as feature.
  • Audience: yours. At tone 1–4 it is a few plain bullets per milestone; at 5–10, the tree as printed plus what stands out.
  • Writes: nothing. It reads status, and coverage or backlog when you ask what is proven or what to do next.
  • Guide: Generated pages.

/spry:work-report

What one person built between two dates: each story, task and bug they worked on, with two or three lines on their part, and the slices under it by ID and title — then what they are building now. A slice counts for its owner:, the person who built it, and its closed: date, never git. The summaries are written from the slices' close summaries, not from the code.

  • Arguments: <person> [from] [to] — a team member's name or GitHub login, and a range as dates or in words ("last week"). No range → the last 7 days.
  • Audience: yours.
  • Writes: nothing, unless you ask for a file — then .spry/reports/, never committed. It reads spry.py work.
  • Guide: Work as a team.

/spry:tone

Sets how technical the agent's replies are for you, from 1 (no technical knowledge) to 10 (engineer in this codebase), or resets to each document's own audience.

  • Arguments: <1-10 | reset>. Empty → it says your current tone and where it comes from.
  • Writes: .spry/tone — yours alone, never committed.
  • Guide: Written for its reader.
