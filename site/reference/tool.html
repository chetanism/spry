Tool commands

spry.py is one Python file — standard library only, Python 3.10 or newer — copied into every project at spry/tool/spry.py. The skills call it; CI calls it; you can call it too. This page lists every command.

You rarely type these yourself

The skills run the right command at the right moment. This page is for when you want to see what a skill is doing, run a check by hand, or wire spry into CI.

Running it

$ python3 spry/tool/spry.py <command> [options]
$ python3 spry/tool/spry.py --help            # every command
$ python3 spry/tool/spry.py gate --help       # one command's flags
$ python3 spry/tool/spry.py --version
Global optionDoes
--root ROOTThe project root. Default: the nearest folder holding spry/spry.config.json, so it works from any subfolder.
--versionPrints the tool's version.

A few commands — vendor and install — are run from the plugin's copy, because they copy spry into a project. Everything else runs from the project's copy.

Checking

check

The consistency of the plan, the knowledge and the links. This is the command that turns spry's written rules into rules that are actually enforced.

spry check [--base BASE]
  • Always: front-matter, IDs, each item's place in the folder tree, the glossary's banned words, line budgets, links, references to acceptance criteria, QA scenarios, conflict checks present and resolved before ready / open, guide comments and placeholders left in finished documents, blocked_by pointing at a dropped item or forming a circle; a warning at a path over 200 characters, which Windows without long paths cannot open from most folders.
  • --base BASE — the git ref the branch merges into. Adds: a warning when a criterion's text changed under a test, a QA scenario or a check-log row that relied on it; a refusal when the branch changed a generated block; and an ID the branch and the base both took. CI passes it on pull requests.

gate

The one command that says "this code is good to go": spry check, then the fast checks (format, lint, types — cheapest first), then the affected tests. Every fast check runs even if one fails; a failing test step stops the gate. With checks.lock on, the checks and tests wait for any gate or falsify run in another worktree to finish.

spry gate [--force] [--fast] [--full] [--failed]
  • A pass is stamped in .spry/green against a fingerprint of the code. While the code matches, the gate runs check alone — so fixing a document after the tests passed never re-runs the tests.
  • It also runs check alone when the branch changed only documents since its merge base with the main branch.
  • When the branch changed only test files, it runs those files — through the falsify runners — instead of the affected tests, says so, and stamps green marked tests-only. A changed file not named as a test, or one another file mentions, sends it the long way.
  • tests.always runs after the tests whenever the gate runs tests, whatever changed.
  • It says where it is as it goes: first how long its steps usually take together, then each step as it starts (→ affected tests · usually 3m20s) and ends. The usual time is the median of that step's last five green runs in the step log; a step never timed green gets none.
  • With tests.retry set, affected tests that fail on a timeout run once more with no parallelism. A real failure fails both runs.
  • --fast — check and the fast checks only, no tests; stamps nothing. Used for each change while building.
  • A red gate keeps the failing steps’ full output in .spry/gate/last.log, and its last line names the failing test files and that path. On the same code and commands, the next gate does not run again: it shows that failure (--force runs it anyway). A failure that looks like the machine — a timeout, a worker that would not start, a port in use, a service that refused the connection (tests.load_when replaces that list) — runs again. The record is per checkout.
  • --force — run everything even if the code is unchanged, or the last gate failed on this code.
  • --failed — only the test files the last red gate named, through the falsify runners. Stamps nothing. When they all pass it marks the test steps cleared so the full gate runs on the same code; a check that is still red stays red, and a file it could not find keeps it from counting.
  • --full — the affected tests even when the branch changed only test files.

More: The gate and test speed.

step

For a slice built in steps (slices.mode: steps): which step comes next, worked out from the commits already on the branch, and the commit that finishes it.

spry step [--commit] [--ranges [--head REF]] [--squash] [--base BASE] slice
  • With no flag — the next step's title, the criteria it covers and its plan. A new session, or one after a compaction, starts here.
  • --commit — runs gate --fast, then commits everything as SL-n step k: title with the trailer Step: SL-n/k. It refuses when the fast checks are red, when nothing changed, when only documents changed, or when the steps so far are out of order. With slices.steps.tests on it also runs the test files the step added or changed, less slices.steps.tests_skip, and refuses when one fails, naming the file. When every red check has a fix in checks.fast — the formatter's write mode — it runs that on the step's files, names the files it changed, runs the checks again and commits. A lint or type failure still refuses the commit, and then nothing is formatted.
  • --ranges — each step's git diff, and the whole branch's, for the reviewers. Off the slice's branch it reads origin/<branch>, so nothing is checked out; --head REF names another place.
  • --squash — folds fixup! commits (review fixes, falsify's new tests) into their steps before the gate; a rebase that stops is undone.

changed

For CI: prints code=true when any file outside checks.docs changed since --base, else code=false. CI skips the fast checks and tests when it is false; /spry:merge uses it to decide whether the main branch needs re-testing.

spry changed --base BASE

merge-check

Is a closed slice ready to merge? Exits 1 if anything blocks it.

spry merge-check [--base BASE] slice

It blocks (✗) when the slice is not closed or has no closed: date, owner or PR number, when a control the diff adds has no falsify row, when a survivor has no reason, when the branch changed a criterion and code together without criteria_approved_by: the story's owner, when a slice built in steps has a step with no commit, one made twice or out of order, code committed without a Step: trailer, or a fixup not folded in, or when check is not clean. It warns (!) about things a person must accept at the merge — a survivor or skipped control with a reason, a covered criterion no test cites (QA checks it by hand after the merge), one whose latest manual check failed, a steps slice over slices.steps.max_lines or a step over slices.steps.step_lines, or, with slices.design_review on, a work order with no Design review or with a Blocker that was not asked. Lines in checks.generated files are not part of that size; they are printed beside it.

review-check

Would GitHub take this review as it stands? Exits 1 if not.

spry review-check --diff DIFF [--own] payload
  • payload — the review's JSON: commit_id, event, body, comments.
  • --diff DIFF — the PR's diff (gh pr diff <n>), or - for stdin.
  • --own — the reviewer wrote the PR, so only COMMENT is allowed.

It checks every comment is anchored on lines the diff shows, every suggestion is closed, none overlap, none is a no-op.

Progress

status

Done versus total at every level, grouped by parent: milestones, epics, features, stories, slices.

spry status [--level LEVEL] [--all] [id]
  • A plan over 100 lines prints only the levels that fit and says how to go deeper.
  • id — only this item's branch of the plan.
  • --level LEVEL — stop at this level, for example feature.
  • --all — every level, however long.

coverage

Done, in progress and defined for the whole plan and for each milestone, criteria proven, slices, tasks and bugs — and what is built but not proven. Prints the coverage page on any branch.

spry coverage

backlog

What is being built, what to build next, and what stands in the way: In progress, Ready to build, Needs slicing, Blocked and Needs planning, in plan order.

spry backlog [--section NAME]… [--rows N] [--plain]

--section NAME — only that section, named by its first words (ready, blocked); repeat it for more. --rows N — at most N rows of each table. --plain — each link as its text alone. Most of a row is its links' paths: in a large plan the whole backlog runs to tens of thousands of tokens, and /spry:slice-open needs four rows.

done

Finished stories, tasks and bugs, newest first, with the day each closed (from the slices' closed: dates — never from git).

spry done

work

What one person built between two days: their slices closed in the range, under the story, task or bug each builds, newest first — with what else closed there and by whom — then their slices being built now. Closed slices it could not count (no owner, or no closed: date) are named. Read from the slice files alone, never git. /spry:work-report writes its report from this.

spry work --since SINCE [--until UNTIL] [--json] owner
  • owner — a team.members name or GitHub login, or the name in the slices' owner:.
  • --since SINCE, --until UNTIL — the first and last day, YYYY-MM-DD; --until defaults to today.
  • --json — with each file's path, for the skill.

owners

Once, for slices opened before CH-40: fills each open or closed slice's missing owner from its pull request's author — a member's name by their GitHub login, or with no members the author's GitHub name. An owner already there is kept and listed when the author differs.

gh pr list --state all --limit 5000 --json number,author > .spry/prs.json
spry owners --from-prs .spry/prs.json [--replace] [--dry-run]
  • --replace — also change an owner the PR's author contradicts.
  • --dry-run — change nothing; say what would change.

index

Regenerates the marker blocks (children tables, proof tables, coverage, backlog, done) and every INDEX.md. Run by CI on the main branch only.

spry index [--check | --restore BASE]
  • --check — change nothing; exit 1 if anything is stale.
  • --restore BASE — on a branch: put back BASE's copy of every generated block the branch changed.

view

Writes the backlog, coverage and done pages for this working tree to .spry/view/ (gitignored) — fresh pages on a branch without touching the committed ones.

spry view [--since SINCE]

--since SINCE — only when the plan or a test changed since this commit (used by the git hooks).

serve

Browses the plan, knowledge and generated pages in a browser — read-only, on this machine only. Each document is rendered with its generated blocks built for the working tree, beside the plan tree; search is find; the pace page is at /-/pace. Ctrl-C stops it.

spry serve [--port PORT] [--no-open]
  • --port PORT — default: the first free one from 8765.
  • --no-open — do not open a browser.

pace

Where slices' time and tokens went, from the step log that gate, check, falsify run and merge-check write and Claude Code's session logs for this clone. It writes .spry/view/pace.md, which shows:

  • each category's share of the time
  • before and after each dated change — and, under it, the slices of each size by themselves: p25 / median / p75 of the 20 before and of those after (a size needs 10 before), then the bugs filed later against them, per slice
  • flags
  • a row per slice, with its lines changed — and, apart from them, the lines in checks.generated files
  • by size: the medians of active time and spend for slices of each size, each per 100 changed lines as p25 / median / p75, and the bugs filed later
  • tokens per slice: the spend in input-token equivalents, the subagents' share, the spend by phase (subagents in the phase they started in), the share of requests that called one tool, the largest context, and the context when the close started
  • subagents, by what each was started for (build, design review, review, fix, tests, other): how many, their own working time and their spend
  • findings per slice, from the slice file: the design review's Blockers, Shoulds and asks; the close review's Blockers, Shoulds, Nits and fixes (Review); the questions the agent asked; the bullets under Choices taken, where a project keeps that section; and the bugs filed later against the slice — each bug whose introduced_by names it
  • red checks: how often each fast check failed a gate, and the rules its output named — an oxlint or eslint rule, a TS number, a ruff, flake8 or mypy code, a biome rule. Rules are recorded from 0.50.0 on
  • falsify per slice: runs, controls, how many were caught, survived and unreliable, and the seconds a control took
  • reruns per slice: full gates that ran tests, how many ran on code already tested, and the time quiet retries lost
  • gate steps
  • the slowest calls

Never committed.

spry pace [SLICE] [--since YYYY-MM-DD] [--last N] [--compare POINT]
  • SLICE — print one slice in detail instead: each kind of time, each phase, its gates, tokens, subagents, review findings, the bugs filed later against it, red checks, falsify runs, reruns and flags — and where it falls among the other slices of its size.
  • --since, --last N — only slices active since that day, or the last N.
  • --compare POINT — before and after a date, a CH-n taken, or a commit, instead of every change.

Session logs are read once per size and change time. The first run on a long project can take a minute.

Tokens come from Claude Code's session logs. An agent that writes none gets the time report without them.

It measures and never judges. /spry:pace has a fresh agent read the page and propose what to change.

hooks

Installs git hooks, per clone, that refresh .spry/view/ after a checkout or pull that changed the plan or a test.

spry hooks [--remove]

These are git hooks. The Claude Code hooks are a different thing, run by agent-hook.

agent-hook

Answers one Claude Code hook call: the plugin's hooks/hooks.json runs it, with the hook's payload on stdin. It prints the hook's answer as JSON, or nothing when the hook is off, the call is not about it, or there is nothing to say. It always exits 0. You don't run it by hand, except to try a hook out. See Agent hooks.

spry agent-hook <session|link_fields|cited_criteria|check_edit|merge|check_stop> < payload.json

Worktrees and progress

worktree

The worktrees agent sessions build in, side by side. Needs a worktrees block in the config, except prune. Claims live in the main checkout's .spry/worktrees/, so every worktree sees the same. Used by /spry:worktree; see Worktrees.

spry worktree list
spry worktree new [name]
spry worktree claim <name|index>
spry worktree release [name] [--force]
spry worktree home [name]
spry worktree prune [--kept]
  • list — every worktree: its index, branch, claim (and whether it is stale), and the slice its branch builds.
  • new — makes one under worktrees.dir on its home branch at the main branch's head, with the next free index, copies worktrees.share in and runs worktrees.setup there.
  • claim — takes it for this session. Refused while another live session holds it; a claim whose session is gone, or that wrote nothing for worktrees.stale_after hours, is taken and said. The main checkout is never claimed.
  • release — gives back the claim of the worktree it runs in, or the one named; --force drops another session's.
  • home — puts the worktree back on its home branch at the main branch's head; /spry:merge runs it after the squash.
  • prune — removes the scratch trees interrupted falsify runs left, and forgets worktrees deleted by hand; --kept also the trees falsify keeps warm between runs.

say

Adds a line to the progress log by hand, for a milestone inside a long step. The commands that end a stage — step --commit, gate, falsify run, review-check, merge-check, worktree home — write their own.

spry say [--slice SLICE] text [text ...]

watch

A panel per worktree, redrawn every few seconds: its claim, the slice its branch builds — after the ID of the story, task or bug it belongs to — and the step it is on, its last progress lines, and how long since the last — marked quiet past progress.quiet. The top line names who holds the heavy-check lock. With progress.transcripts: "claude-code", each panel also says what the session is doing now, its context, its spend and how long since it was last cleared. Reads only; spends no tokens.

spry watch [-n SECONDS] [--once]

Creating and linking items

new

Creates items from their templates, with the next IDs, in the right folders — one, several, or a batch of mixed types. All are written, or none.

spry new [--parent PARENT] --title TITLE [--title TITLE …] [--owner OWNER] [--dependency DEPENDENCY] type
spry new --batch FILE
  • Item types, with IDs: milestone, epic, feature, story, slice, task, bug, decision.
  • Documents without an ID of their own: checks (a story's QA file; --parent is the story), convention, external (--dependency names the service), audit.
  • Repeat --title for several items of one type under one parent; they are numbered in the order given.
  • --batch reads a JSON list of {"type", "title", "parent", "owner", "key"} from a file, or stdin with -. A parent names an item in the plan or the key of an earlier entry, so a feature and its stories go in one call.
  • With mint: main, the IDs are taken on the main branch in one commit and one push, then merged into the current branch, so two sessions never take one number. Nothing is checked out.
$ python3 spry/tool/spry.py new story --parent F-1 --title "Loan limit" --title "Overdue block" --owner Asha
$ echo '[{"key": "f", "type": "feature", "parent": "E-2", "title": "Renewals"},
        {"type": "story", "parent": "f", "title": "Renew a loan"}]' | python3 spry/tool/spry.py new --batch -

next

The next free ID for a type.

spry next type

claim

Takes a slice before opening it, then cuts its branch sl-<n>-<slug>. With mint: main the claim is made on the main branch and refused when someone already holds it.

spry claim [--owner OWNER] [--no-switch] slice
  • --owner OWNER — who is building it: a team.members name or GitHub login. Left out, the person git says is at this clone. With mint: main it is written on the main branch with the claim.
  • --no-switch — make the branch without switching to it, for a separate worktree.

release

Gives back a claimed slice nobody is building: planned again, branch: cleared. The branch itself is left for its owner to delete.

spry release slice

link

Sets a slice's branch, pr or owner in its front-matter — or, on a plan item, adds the GitHub issue it was asked for in to its issues:.

spry link [--branch BRANCH] [--pr PR] [--owner [OWNER]] slice
spry link --issue ISSUE item

--owner alone is the person git says is at this clone: their team.members name, matched by git's user.name or the start of user.email — or, with no members, user.name. /spry:slice-open runs it, so a slice's owner is who built it.

related

Conflict-check candidates for a document: its parent, siblings, items sharing glossary terms, full-text hits on its key phrases, the files in always_check, decisions that name it — and for a slice, every open slice and the files its plan touches.

spry related file

Pull requests and issues

brief

A slice in one call: the pr-body page (covered criteria in words, falsify gaps, the work order), then the files the branch changed. A session reads it instead of opening the slice, the story and git diff one by one. Every request to the model reads the whole session again, so one call in place of ten saves nine readings of it.

spry brief [--diff] slice

--diff — add the branch's whole diff: what a slice's reviewer starts with. Without it, brief first says when this checkout's session carries more context than slices.fresh_context — the cue to /clear before the close.

pr-body

A slice's pull request body: For the reviewer first (covered criteria in words, criteria changed, falsify gaps, manual checks due), then the work order and close summary. The PR body is always copied from the slice file, never edited by hand.

spry pr-body [--base BASE] slice

--base BASE — the ref the PR merges into, to show criteria the branch changed.

issues

The GitHub issues plan items were asked for in (issues:), each with its stage — accepted, ready, in-progress, done or declined, worked out from the plan — and whether its spry: label shows it. See Requests in GitHub issues.

spry issues [--sync [--dry-run]] [--offline] [--json]
spry issues --legacy [--close]

--sync — on each open issue out of step, set the label, and comment when the stage changed. Creates the labels it needs. Never closes an issue, and leaves a closed one alone. --dry-run says what it would do. --offline — the stages alone, without asking GitHub. --legacy — the issues spry made per slice before 0.41.0 that are still open; --close closes them, each with a comment.

publish

The commits, pushes and pull-request steps around a slice, so the agent never runs them by hand. It commits only files under spry/, and refuses while code is uncommitted.

spry publish [--owner NAME] slice {open,review,ready}
  • open — the slice goes open with its branch and owner; refused, with nothing changed, when check refuses it. The work order is committed as the branch's first commit, pushed, and a draft PR titled SL-n title is opened with the body from pr-body; its number is linked, committed and pushed.
  • review — before the review at close: the close notes committed, the branch pushed (--force-with-lease, after a rebase), the PR body refreshed. The PR stays a draft.
  • ready — at the end of the close: state: closed and today's closed:, the gate (on red the slice goes back to open and nothing is committed), the commit with its Slice: trailer, the push, the PR body, and the PR marked ready.

merge-ready

Everything /spry:merge checks before its ask, in one report: the PR's checks (a run that started no step never ran, and then the gate on the PR's head stands in for CI), merge-check, the PR body (refreshed when it differs from the slice file), approval when there is a team, and whether the main branch moved under the PR's files. Exits 1 if anything blocks the merge. It ends with the ask and the exact merge-finish command to run on a yes.

spry merge-ready [--wait [MINUTES]] [pr | slice]

With no target, the current branch's slice. Run it on the PR's branch.

--wait — when checks are still pending, wait for them on this machine (up to 30 minutes, or MINUTES), then report. Run in the background, it costs the agent one call where polling gh pr checks cost one a look.

merge-finish

On the person's yes: checks CI and merge-check again, squashes with merge-message at the PR's head, deletes the branch, brings this tree to the main branch (a spry worktree goes home), waits for CI there only when the main branch gained code the PR's checks never saw, writes the progress tables when CI left them stale, runs issues --sync, and names what is unblocked.

spry merge-finish [--ci-local REASON] [pr | slice]

--ci-local REASON — as merge-ready printed it, when CI never ran.

merge-message

The squash commit for a slice: subject, summary, and the Slice:, Parent: and Covers: trailers.

spry merge-message [--ci-local REASON] slice

--ci-local REASON — CI never ran, for this reason; the gate stood in for it. Adds a CI: trailer.

Falsify

Proves a slice's tests notice its safeguards. Background: Falsify.

falsify suggest

Drafts a plan from the source lines the branch added: one candidate per line that refuses, stops or decides — a guard, an error line, a clause of a condition, a WHERE — each with a mutation that removes it, expect taken from the slice's covers (or the bug or the task, for a bug's or a task's slice), and files: the tests citing expect that name the control's source file. A line that only builds a value, or that the branch only moved, is left out. A deletion that would not parse is drafted mutation: write one, for a person to fill before the run. With no guard added, it offers up to five lines that compute or store something. With no source line added, there is nothing to falsify.

spry falsify suggest [--base BASE] [--out OUT] slice
  • --base BASE — the branch to diff against (default: main_branch).
  • --out OUT — where to write the plan (default: .spry/falsify/<slice>.json).

falsify run

Removes each control in turn, runs only the tests that should notice, and restores every file — including on an error, Ctrl-C or SIGTERM.

spry falsify run [--dry-run] [--record SLICE] [--replace] [--jobs JOBS] plan
  • --dry-run — validate the plan and list what would run.
  • --record SLICE — write the results into the slice's Falsify table; rows for controls not run stay.
  • --replace — with --record: drop the rows this run did not write.
  • --jobs JOBS — worktrees to run in parallel (default: falsify.parallel; 1 = serial).
$ python3 spry/tool/spry.py falsify suggest SL-2
$ python3 spry/tool/spry.py falsify run .spry/falsify/SL-2.json --dry-run
$ python3 spry/tool/spry.py falsify run .spry/falsify/SL-2.json --record SL-2

Knowledge and search

proc

A process file, or only the sections a skill needs: the file's opening, then each ## section named, with everything under it. A name matches a heading it starts, ignoring case. Skills use it so the agent reads, say, Open and While building of slicing.md — about 120 lines — instead of all 360.

spry proc [--list] file [section ...]

--list — the headings and their sizes. With no section, the whole file.

find

Full-text search over spry/ and AGENTS.md, best sections first. Uses SQLite's full-text search (FTS5), through the standard library's sqlite3, kept in .spry/index.db and refreshed per file; falls back to plain search without FTS5.

spry find [--limit LIMIT] [--rebuild] query [query ...]

--rebuild — rebuild the local index from scratch.

memory-check

Claude Code's memory for this checkout, checked where no judgement is needed. It reads the index against its files (dead lines, files no line names, a name used twice) and the index's size against memory in the config. It flags front-matter, dates that have passed in a clause still to do, and relative days. It reports the plan items, pull requests and issues, commits and paths each memory names, and whether each is closed, merged or gone. It notes text AGENTS.md or spry/knowledge/ already holds, and memories that overlap. Report only; used by /spry:memory-check.

spry memory-check [--dir DIR] [--offline] [--json]

--dir — the memory folder; by default the main checkout's, which every worktree shares. --offline — skip gh; pull requests and issues are looked up in one GraphQL call per hundred numbers otherwise.

scrub

Lists private words still in a file meant to leave the project: the product name, team names and handles, glossary terms, emails and URLs. Used by /spry:contribute.

spry scrub file

Setting up

vendor

Copies process/ and the tool into a project, at spry/process/ and spry/tool/. Run the plugin's copy.

spry vendor [--force] [--root VENDOR_ROOT] [--diff]
  • --diff — change nothing; list what differs from the plugin.
  • --force — overwrite an existing spry/process/.
  • --root — the project to copy into (default: the current folder).

install

Puts the skills where another agent finds them. Run the plugin's copy.

spry install --agent {generic,claude,cursor,gemini} [--root INSTALL_ROOT]
AgentWrites
genericThe skills to spry/skills/, listed in a generated block of AGENTS.md — any agent that reads AGENTS.md can run them.
claudeProject skills in .claude/skills/spry-*, for people not using the plugin.
cursor.cursor/commands/spry-*.md.
gemini.gemini/commands/spry/*.toml, run as /spry:<name>.

codeowners

Writes .github/CODEOWNERS from team.review in the config.

spry codeowners [--check]

--check — change nothing; exit 1 if it is stale.

Testing helpers

tests

Test-suite reports from JUnit XML.

spry tests --slowest [--junit JUNIT] [--limit LIMIT]
  • --slowest — the slowest tests and files.
  • --junit JUNIT — a report file, folder or glob (default: tests.junit).

draw

A replayable choice for an exploratory walk (/spry:explore): the same seed and counter always give the same answer.

spry draw (--seed | --pick | --sample K | --shuffle | --int N) [seed] [counter]
  • --seed — print a fresh seed.
  • --pick — one line from stdin. --sample K — K distinct lines. --shuffle — every line, reordered.
  • --int N — a number from 0 to N−1.
  • counter — the step number; add 1 on every draw.

In CI

The workflow init writes runs the tool in the same order as the gate — cheapest first, and tests only when code changed:

  1. check — with --base origin/<main> on pull requests — then changed, which prints code=true|false.
  2. The fast checks, one step each — only when code is true.
  3. On a pull request: the affected tests. On a push to the main branch: every test. Nightly: every test.
  4. On the main branch: index refreshes the generated pages and commits them with [skip ci].

A change to documents alone runs check and nothing else.
