FAQ

Straight answers to the questions people ask before they try spry. If yours is not here, the design section explains every rule and why it exists.

Getting started

Do I need Claude Code?

No. spry is built as a Claude Code plugin, and that is the smoothest way to run it, but the skills also install for Cursor, Gemini and any agent that reads AGENTS.md (Codex among them):

$ python3 <clone of spry>/plugins/spry/tool/spry.py install --agent generic   # or claude, cursor, gemini

The rules live in process files and the tool, not in the agent, so switching agents mid-slice loses nothing. One limit: reviews by fresh eyes need an agent that can start a second agent; without one, the review asks you to run it in a new session. Use another agent.

Does it work for one person?

Yes. A team is a section of the config, not a separate setup: leave team.members empty and you are solo. Nothing is routed for review, approval is not required to merge, and the fresh-eyes review becomes the second pair of eyes you do not have a teammate for.

I already have a codebase. Do I have to plan it all backwards?

No. /spry:adopt surveys what exists and records it in spry/knowledge/codebase.md; the plan starts from your next piece of work. Existing tests are untouched — only new tests cite criteria — and spry's checks only read spry/ and test names, so no existing file can fail them. Adopt an existing codebase.

Which languages and test runners does it support?

Ready-made stack profiles exist for TypeScript / Node (Vitest or Jest) and Python (pytest). Any other stack works too: setup asks the developer for the commands — format, lint, types, affected tests, all tests, a runner for a list of test files — and records them in the configuration.

Does it need GitHub?

In practice, today, yes. The CI workflow setup writes is GitHub Actions, pull requests and merges go through the gh command, CODEOWNERS is generated for GitHub, and the plan is designed to be read by clicking folders on GitHub. The files themselves are plain Markdown and the tool is plain Python, so another host is possible, but you would adapt the process yourself (/spry:process-change).

Does it work on Windows?

The tool is plain Python 3.10+. Falsify was made to work on Windows from a pilot team's feedback — quoted paths for cmd, process-tree kills on timeout, junctions where symlinks are refused, LF line endings. A plan six folders deep can pass Windows' 260-character path limit: the tool opens such files anyway, and spry check warns at a path over 200 characters so your editor and git keep working too.

Is it ready?

It is early. The tool has a test suite, and the process is being run on pilot projects — most recent changes came from them — but none has run a full milestone through it yet. Expect it to change; /spry:update offers each change rather than forcing it.

Trust

What if my agent ignores a rule?

That is the problem spry is designed around. A rule that matters is in spry check, not only in prose — and check runs in the gate, in CI on every pull request, and inside merge-check. A skipped conflict check, a safeguard no test notices with no reason given, a criterion quietly reworded to fit the code: each one blocks the merge, whatever the agent remembered to do. A criterion with no test is put to you at the merge, as a manual check QA owes. Principles.

How do I know "done" really means done?

Nobody types it. A story is done when its slices are merged and every acceptance criterion is proven — by a test whose name cites it, or by a QA check whose latest result is a pass. A QA fail un-proves a criterion even if a test passes. Status is derived.

Tests pass. Why isn't that enough?

Because a test can pass without testing the thing. Falsify removes each safeguard a slice added — a permission check, a limit, an error branch — and runs the tests that should notice. If they still pass, the safeguard survived, and the slice cannot merge until there is a test or a written reason you accept. Falsify.

Will the agent stop and ask me things all day?

No. A person decides three things: the acceptance criteria, the merge, and anything hard to undo (a database migration, a public API, a new dependency, deleting data). Everything between runs without stopping, because the checks stand in for a person watching. Where a person decides.

Can the agent merge on its own?

No. /spry:merge merges only on a yes given in that conversation, for that pull request, and never a red or pending one. On your own PR, a review's answer can be "post, fix, then merge" — that is the yes, unless the merge finds something the review did not report.

Cost and speed

Is it slow?

The rule is that a slow check runs only when its answer could have changed. While building, the agent runs gate --fast — check, format, lint, types, no tests. The full gate runs the affected tests only, once per slice, at close. A pass is stamped against the code, so editing a document afterwards never re-runs tests. The full suite runs in CI on the main branch and nightly — never as an agent's routine step. The gate and test speed.

What does it cost in tokens?

spry does not publish numbers, and it will vary with your project. What it does to keep the cost down: AGENTS.md — read on every task — has a hard line budget; agents open a process file only when a step names it; knowledge is split into an index plus one file per item, so an agent reads one line per item and opens the one it needs; and spry find searches instead of reading everything. The reviews, interviews and falsify runs are extra work compared with "just write the code" — that work is what you are buying.

Your process

Can I change the process?

Yes — it is yours. /spry:process-change changes a rule, a template or a step in every file it touches at once, and records it so /spry:update keeps it. The one thing never changed locally is the tool; a tool change is offered back with /spry:contribute. Keep spry yours.

We don't use epics. Or milestones are too big.

Levels are set in the config. A small project can drop the epic level; features then sit straight under milestones. ID prefixes are chosen in the setup interview too.

What does a product manager actually do?

Answer interviews. /spry:milestone, epic, feature and story ask a few questions at a time, offer a drafted answer to confirm, and write it down in plain words — audience 2–3, no code or file paths. Then read the plan, backlog and progress on GitHub by clicking folders, with nothing to install — or locally in a browser with spry serve. The one decision only product can make: saying yes to a story's criteria. Plan the work.

And QA?

Writes and runs the manual checks for each story with /spry:test-scenarios, and logs each run. A logged pass proves a criterion; a logged fail un-proves it and becomes a bug. Checks for QA.

Can several people — or several agent sessions — work at once?

Yes. Slices of stories that touch different files can be built side by side, each in its own git worktree and session. With mint: main, IDs and slice claims are taken on the main branch, so two sessions never take one number or start the same slice. Generated pages are written only on the main branch, so branches never conflict over them. Work as a team.

Does it work in a monorepo?

Yes. The TypeScript profile covers Turborepo — filtering checks and tests to changed packages — and falsify runners can run in each test file's nearest package ("cwd": "package"), including pnpm workspaces.

Data and leaving

Where does my data live?

In your repository, as Markdown files under spry/, plus AGENTS.md, CLAUDE.md and a CI workflow. There is no hosted service, database or account; the optional spry serve runs on your machine and only reads those files. A local .spry/ folder — gitignored — holds a search index, your personal tone, the gate's stamp and caches. Nothing leaves your machine except what you push, and /spry:contribute, which files an issue on spry only after you have read it and said yes.

Is there a user interface?

GitHub's own rendering of the files is the main one. For a quicker way around a big plan, python3 spry/tool/spry.py serve opens it in your browser: the plan tree with progress, every document, the backlog and coverage for your working tree, and search. It only reads — plans are changed through the skills, which check them for conflicts. Generated pages.

Will spry end up in my production build?

No. Setup excludes spry/ from deploy builds (.dockerignore or the stack's build config), and the pre-launch review checks it.

Can I stop using it?

Yes. Nothing in your product's code depends on spry. Stop running the skills, and remove spry/, the spry lines in AGENTS.md, and the spry CI workflow when you want them gone — or keep the files as a readable record of what was planned and why. Tests keep working; the S-1/AC-2 in their names is only text.

How is it related to writ?

Inspired by it, not based on it: the same aim, rebuilt around what running writ on real projects taught. A writ project can be adopted. Coming from writ.
