Quick start

Your first hour: set up a project, plan just enough to have one story, then take it through a slice to a merge. Every step is a command you type into your agent; it asks a few questions at a time and writes the answers into files as you go.

Before you start

Install spry (Installation), have the GitHub command-line tool (gh) signed in, and open your agent in the project's folder. The examples below use the Shelf example — a lending desk for a small library. A word you don't know? The glossary has every one.

1. Set up the project

/spry:init

Use /spry:adopt instead if there is code already. The agent starts by asking what you are building, for whom and why now — a paragraph or a pasted document both work. Then it interviews you, in this order:

  1. the product and the people who use it;
  2. the team — names, GitHub handles, who reviews what (or nobody: solo is fine);
  3. the plan's shape — keep epics, or drop them for a small project;
  4. the roadmap — your milestones in order;
  5. constraints, security, performance and outside services you depend on;
  6. the stack and how tests run (this part is for a developer);
  7. the words you use, for the glossary.

It asks at most three things at a time, and offers a drafted answer to confirm or correct rather than an open question. Say "you decide" and it takes its recommendation and notes it as an assumption. Say "I don't know yet" and it records an open question and moves on.

You end up with a spry/ folder, an AGENTS.md, and a CI workflow. It asks before committing. More on setup →

2. Plan one level at a time

Each planning skill defines one level, never the level below. Define just enough to reach one story you can build:

/spry:milestone M-1    # why, done-when, in and out of scope
/spry:epic             # a body of work under the milestone
/spry:feature          # how it works, step by step, and its numbered rules
/spry:story            # stories with acceptance criteria

These are written for product people: plain words, no code. For Shelf, Asha (product) defined M-1 Members can borrow books, then E-1 Lending, then F-1 Lend at the desk with rules like R-1 "a member may have at most 3 books on loan at once".

Before anything goes ready, the agent runs a conflict check — it reads the parent, the siblings, the glossary and your decisions, and resolves or asks about every clash. Then it shows you a summary and asks to mark it ready. Plan the work →

The story is where you decide

A story's acceptance criteria are what "done" means. Each is something a person can see, written as Given / When / Then, numbered AC-1, AC-2…:

ACGivenWhenThen
AC-1a member with 3 books on loanthe librarian scans their library cardthe desk shows "Limit reached: 3 books on loan" and Lend cannot be pressed

The story goes ready only on your yes. Tests will be named after these criteria, and QA will check them by hand. Write acceptance criteria →

3. Split the story into slices

/spry:slice S-2

The agent reads the story, its feature's rules, your conventions and the code it will touch, then proposes slices in one reply: a title for each, which criteria it covers, and the visible change it makes. Each slice is one pull request a reviewer can read in one sitting. It also says which slices need an earlier one and which could be built side by side.

Approve, and each slice becomes a small file, state planned. Split a story into slices →

4. Open and build a slice

/spry:slice-open       # or name one: /spry:slice-open SL-2

With no ID, it lists the slices ready to build and recommends the first. Then, without stopping unless it must:

  1. Claims the slice and creates its branch — and, if your project takes claims on the main branch (mint: main), so nobody else can start it.
  2. Writes the work order — a short summary anyone can read, the plan file by file, the rules it must not break, the tests (each named after a criterion, like "S-2/AC-1 refuses a member with 3 books on loan"), and a copy-paste demo.
  3. Runs the conflict check — against the story, the project's rules and decisions, and open slices touching the same files.
  4. Opens a draft pull request (one marked not yet ready to merge) with the work order as its body.
  5. Builds it, running quick checks after each change — then goes straight on to close it (step 5), unless you asked it to open only.
When it will stop and ask

Only if the plan does something hard to undo — a database migration, a public API change, a new dependency, deleting data — or departs from the story. Otherwise it carries on.

Build a slice →

5. Close it

/spry:slice-close

slice-open does this for you; type /spry:slice-close yourself only for a slice you opened only, or picked up in a new session. Closing is where the slice earns its merge:

  1. Rebase — bring the branch up to date with the latest main branch.
  2. What changed — only where the code differs from the plan, and why.
  3. Proof — every covered criterion has a test naming it, or QA is told which need a manual check.
  4. Follow-ups — bugs, tasks and decisions found along the way are recorded.
  5. Review by a fresh agent that never saw the work being written; you choose which findings to fix.
  6. Falsify — each safeguard the slice added is broken on purpose to prove a test notices.
  7. Gate — the project's checks and the tests the change affects, once, on the code that will merge.
  8. The slice is marked closed and the pull request ready for review.

Close and merge a slice →

6. Merge

/spry:merge

The merge checks that CI is green, the slice is ready, the pull request is approved (on a team), and the main branch has not moved under it. Then it asks you one question: what will merge, plus anything you need to accept — a safeguard no test caught, with its reason; a criterion with no test. Only your yes merges it.

Afterwards it updates your main branch, makes sure the progress pages are fresh, and tells you what the merge unblocked.

Check where you are

At any point:

/spry:status

It shows done versus total at every level, open slices and bugs, and what to pick up next — at your level of technical detail. Not technical? Set it once with /spry:tone 2.
