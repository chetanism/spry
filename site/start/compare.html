spry, Spec Kit and Kiro

All three tools follow the same idea: write down what you want before an agent builds it, and keep that writing as the source of truth. They differ in how far past "write it down" they go, where they run, and what they ask of you. This page was written by spry's authors, so we have tried to say plainly where the other two are better.

GitHub Spec Kit

Spec Kit is the lightest way in. You run specify init, and your agent gains commands that turn an idea into spec.md, plan.md and tasks.md, guided by a constitution of project principles. Optional steps catch problems early: clarify asks about gaps, checklist writes "unit tests for the requirements" that block implement until a person ticks them, and analyze looks for contradictions between spec, plan and tasks. The newer converge step compares the code with all three and adds the tasks that are still missing. Presets, extensions, hooks and workflows let a team shape all of it.

Strengths

  • Works with nearly any agent, and costs nothing.
  • Quick to learn: a few commands, readable Markdown, no new editor.
  • By far the largest community, with a catalogue of extensions to build on.
  • Good tools for finding gaps in a spec before any code is written.

Weaknesses

  • Proof stays with the agent. Tests are not traced back to requirements, and converge is one agent comparing text with code.
  • The process ends at implement. Review, merging and progress across features are up to you.
  • A spec belongs to its branch and is left to age. Keeping specs alive as the product changes is up to the team.
  • Reviewers have noted a lot of Markdown to read for small changes, and an agent that still ignores notes or duplicates existing code.

Amazon Kiro

Kiro builds the same idea into an editor. A spec is three files: requirements written in EARS form (WHEN … THE SYSTEM SHALL …), a design, and tasks. Kiro then runs the tasks, several at once where they don't depend on each other. Around that sit steering files for project conventions, hooks that run on editor events, powers, custom agents, checkpoints and an opt-in memory. Its most distinctive feature turns requirements into property-based tests, each linked to the requirement it checks.

Strengths

  • The most polished experience of the three. Specs, tasks and code sit in one window, and progress shows live.
  • EARS requirements are precise enough to test, and property tests check them over many inputs, not one example.
  • Automation is built in: hooks, parallel tasks, a CLI and a web agent.
  • Backed by AWS, with team plans, SSO and enterprise governance.

Weaknesses

  • Closed source and tied to one vendor. You pay in credits, and the bill grows with use.
  • Plans one feature at a time. There is no roadmap above that, and no roles or ownership in the plan.
  • Property tests are optional, and Kiro's own docs say they are not formal verification. No merge gate holds the work to them.
  • Heavy for small fixes. One reviewer got four user stories and sixteen criteria for a small bug.

spry

spry treats the spec as a whole plan, not a feature: milestones, epics, features and stories, written for non-technical readers, with acceptance criteria a person agrees. Developers split stories into small slices, each with a work order. Then spry makes "done" something the tool works out, not something anyone types: a criterion counts only when a test names it or QA records a pass. Falsify breaks each new safeguard to show a test notices. A fresh agent reviews every slice, and merge-check plus the agent hooks hold the merge to all of it.

Strengths

  • The only one of the three that refuses a merge until each criterion has a test that can fail, or a pass from QA. Criteria are tied to tests by name, falsify checks the tests notice a broken safeguard, and progress is computed. That is strong evidence, not a proof: a test can still check the wrong thing.
  • Covers the whole lifecycle: planning above features, review, merge, QA checks, bugs, tasks, a record of decisions, reports on who built what and where the time went.
  • Made for teams with non-technical members: each document is written for its reader, and the plan is browsable on GitHub with nothing to install.
  • Free and open, with no dependencies beyond Python; you pay only for the agent.

Weaknesses

  • Young. One author, a few pilot projects, no full milestone run through it yet, and it changes weekly.
  • Heavy. Interviews, conflict checks, falsify and review at every slice cost time, and for small work that is too much.
  • Steep to learn: many skills, many rules, a large config.
  • At its best only in Claude Code. Other agents get the skills and checks but not the hooks, and the process assumes GitHub.

They tie overall for different reasons. Spec Kit is easy and open but stops at the code. Kiro is polished and checks requirements best, but it locks you in. spry has the most complete process on paper, but it is the least proven and the hardest to start with.

Which to pick

  • Spec Kit if you want structure in the agent you already use, today, for free, and you will handle review and progress yourself.
  • Kiro if you want one polished tool, your team is happy in an AWS editor, and requirements checked by property tests matter more to you than freedom of tool.
  • spry if you need to know what was built and that it works, with people who don't code following along, and you will accept the overhead and an early tool to get that.
  • None of them for a one-off script or a spike. All three cost more than they give back on small, throwaway work.
