Is spry for you?

spry suits people who want an agent to do most of the building but still want to know — without taking anyone's word for it — what was built, why, and whether it works. Here is who it fits, who it doesn't, and what it asks of you.

It fits if…

  • You already think in milestones, features and stories, or would like to. spry uses the levels agile teams already plan in, so nobody learns a new vocabulary for the plan.
  • You want to review less code, better. Small slices, each checked against a written plan, are easier to trust than one big pull request.
  • People who don't code need to follow along. Product owners, QA and stakeholders read the plan as pages on GitHub, written for them.
  • You have been burned by "it's done" — by an agent, or a status board — and want done to mean proven.
  • You switch agents, sessions or people mid-work. Everything is in files, so any of them picks up where the last one stopped.

Solo or team — the same process

A team is a section in the configuration, not a different setup. With nobody listed, you are solo: nothing is routed for review and the plan can be committed straight to the main branch. Add people with their roles — product, developer, QA — and spry routes plan changes to product, code to developers, and writes a CODEOWNERS file for GitHub to enforce it.

Solo does not mean unreviewed. Every review is done by a fresh agent that did not write the work — the second pair of eyes there is no teammate for. Reviews with fresh eyes →

New code or old

A new project

/spry:init interviews you about the product, team, stack and rules, then writes the plan, knowledge files and CI.

An existing codebase

/spry:adopt surveys the code first and offers what it found for you to confirm. It plans from the next work — what exists is recorded, not planned backwards.

Adopting blocks nobody: the checks only read spry's own folder and test names, so no existing file can fail them. Existing tests are left untouched; only new tests cite criteria.

Your stack, your agent

  • Any language. The tool is one Python file with no dependencies; it calls your own test runner, linter and type checker. There are ready profiles for TypeScript/Node and Python, and a generic one that asks the questions any other stack needs answered.
  • Any agent. spry is a Claude Code plugin, and it also installs for Cursor, Gemini and any agent that reads AGENTS.md — Codex among them. Use another agent →
  • GitHub. The workflow assumes pull requests and GitHub Actions for CI. The plan is browsable because GitHub shows each folder's README.md.

Small projects

The levels are configurable. A small project can drop epics and put features straight under milestones. You also don't plan everything up front: define one milestone, then one epic, then one feature, only as you need them.

What it asks of you

spry is not free. Be honest with yourself about these before you start:

It costsWhat you get back
Interviews. Each milestone, epic, feature and story is a short conversation — a few questions at a time, with drafted answers to confirm.Plans written down once, in plain words, that every later session reads instead of guessing.
Agreeing criteria. A story goes ready only on a person's yes to its acceptance criteria.A definition of done you chose, which tests and QA are named after.
Small slices. You merge more, smaller pull requests.Reviews you can actually do, and a backlog that shows real progress.
Discipline in the files. Templates, one term per concept, a conflict check before anything goes ready. spry check enforces it.A plan that stays consistent as it grows, and agents that don't drift.
Time at close. Review, falsify and the gate run before each merge.Evidence that each slice's tests catch its safeguards breaking.

It may not fit if…

  • You want the agent to just write code, with no plan. spry's value comes from the plan and the proof; without them it is overhead.
  • The work is a one-off script or a spike. Throwaway work does not need acceptance criteria.
  • You are not on git and GitHub. Pull requests, CI and browsable folders are part of how it works.
  • You need a polished, battle-tested product today. spry is young: it is being piloted on real projects, but none has run a full milestone through it yet, and it keeps changing as they teach it things.
