Why spry

A coding agent is fast. The trouble is everything around the code: what to build, how anyone checks it, and how the team knows where things stand. These are the problems people hit when agents join the work — and what spry does about each one.

None of this is the agent's fault. Agents are good at writing code and bad at remembering, at saying "I'm not sure", and at stopping where a person should decide. A process built for people assumed those things came for free. spry puts them back in, as files and checks rather than habits.

The pull request nobody can review

Ask an agent for a feature and you get one: thirty files, three concerns, a migration and a refactor nobody asked for. The reviewer skims, approves, and hopes. The review has become a ritual.

What happens

  • One huge change per feature
  • The reviewer cannot tell what was meant from what was done
  • Scope creep hides inside the diff

What spry does

  • Work is cut into slices: one pull request a reviewer reads in one sitting, showing one visible change
  • Each slice has a written work order — the plan, file by file — before any code
  • The review checks the diff against the work order, so anything extra stands out

"Done" because the agent said so

An agent will tell you, cheerfully, that the feature is complete and all tests pass. Sometimes it is right. A status column someone types into — a ticket moved to Done — has the same problem: it records a claim, not a fact.

What happens

  • Status is typed by whoever last touched it
  • "Done" and "works" drift apart

What spry does

  • Nobody writes "done". The tool derives it
  • A story is done when its slices are merged and every acceptance criterion is proven — by a test named after it, or a QA check that passed
  • A later failed QA check un-proves it, even if the tests pass

In the worked example, the story S-1 Lend a book has its only slice merged — yet it shows not proven, because QA's latest check of one criterion failed in the evening and became bug B-1. That is the point: the page tells the truth without anyone having to remember to update it. Status is derived →

Tests that pass but would not notice the bug

Agents write tests readily. Whether those tests would actually fail if the code broke is another matter — a test that checks the wrong thing passes forever.

What happens

  • Coverage looks high
  • A safeguard can be deleted and every test still passes

What spry does

  • Falsify: before a slice merges, the tool breaks each safeguard the slice added — deletes a check, flips a limit — and runs the tests that should notice
  • A safeguard whose break goes unnoticed ("survived") needs a new test, or a written reason a person accepts
  • The tool decides which safeguards to break, from the diff — the agent can add, never leave one out

Context that lives in a chat

Yesterday's session knew why the due date is stored rather than computed. Today's session does not, and "fixes" it. Long agent sessions also fill up and forget their own beginning.

What happens

  • Decisions vanish when the session ends
  • Switching agent or teammate means starting over

What spry does

  • State lives in files, never in a session. Every answer in an interview is written into the document as it is given
  • Decisions, conventions and how outside services really behave are recorded in small, indexed files an agent searches before it plans
  • A short AGENTS.md holds only what an agent would get wrong without it

Product can't see what's happening

When the work happens in a terminal, the people who own the product are left asking "where are we?" — and the answer is whatever the developer remembers.

What happens

  • The plan is in one tool, the code in another, progress in someone's head
  • Non-technical people need a developer to translate

What spry does

  • The plan is folders on GitHub: milestone → epic → feature → story. Click down; each page explains itself and shows progress
  • Planning pages are written in plain words for their reader — no code, no paths
  • A backlog, a coverage page and a done page are regenerated on every merge

Agents drift — in words and in scope

The product calls it a loan. The agent writes checkout in one place, borrowing in another. A story quietly grows a feature its parent never asked for. Nobody notices until two parts of the product disagree.

What happens

  • Three words for one thing, and bugs where they meet
  • New items that contradict or duplicate old ones

What spry does

  • A glossary with one term per concept and the words not to use — spry check fails on a banned word in the plan and knowledge files
  • A conflict check before anything goes ready: the parent, siblings, decisions and open work are read, and each clash is resolved or put to you

Parallel sessions trip over each other

Two agents, two branches — and both create "story 12", or both start on the same slice, or both edit the same progress table and conflict at every merge.

What happens

  • Duplicate numbers, duplicate work
  • Merge conflicts in files nobody meant to change

What spry does

  • One file per item, so two pieces of work rarely touch the same file
  • Generated pages are written only on the main branch, never on a branch
  • Optionally, IDs and slice claims are taken on the main branch, so two sessions never take one number or one slice

Test runs that eat the afternoon

An agent that runs the whole suite after every edit is slow; one that runs nothing is reckless. Neither is a policy.

What happens

  • Ten-minute suites run for a typo in a README
  • Or tests are skipped "to save time"

What spry does

  • The gate: cheapest checks first (format, lint, types), then only the tests the change affects
  • A pass is stamped against the code — fixing a document afterwards never re-runs the tests
  • The full suite runs in CI on the main branch, nightly, and when you ask

What stays with you

spry does not try to remove people from the loop. It narrows the loop to the three places a person really matters, and makes the agent stop there:

  • The criteria — what "done" means for a story.
  • The merge — the yes that puts code on the main branch.
  • Anything hard to undo — a database migration, a public API change, a new dependency, deleting data.

Everything between runs without stopping, because the checks stand in for a person watching each step. Where a person decides →
