A worked example

Shelf is an invented product: a lending desk for a small community library. It has been taken from roadmap to slice — a slice being one small change, built and merged as one pull request — so you can see what a spry project actually looks like — every file below is real, and passes spry's own checks.

The team and the product

  • Asha (product) writes milestones, epics, features and stories.
  • Ravi (developer) splits stories into slices and builds them.
  • Meera (QA) writes and runs the checks for each story.

Shelf replaces the paper lending register at Riverside Reading Room, which lends about 400 books a week. The first milestone: members can borrow books — lend at the desk, record returns, see what is overdue.

The plan is folders

The plan's hierarchy is the folder tree. On GitHub, opening a folder shows its README.md, so anyone can click down from the roadmap to a story without installing anything:

IDs like M-1, S-2 and SL-4 are simple counters per type, never nested numbers — so moving a story to another feature is just moving its folder.

A feature and its rules

Asha's feature page says how lending works, step by step, then the rules every story under it must follow. Rules are numbered so stories can cite them instead of repeating them:

## Rules

- R-1 A member may have at most 3 books on loan at once.
- R-2 A loan lasts 14 days; the due date is printed on the receipt.
- R-3 A book can be on loan to only one member at a time.
- R-4 A member with an overdue book cannot borrow another until it is returned.

R-4 is there because the conflict check caught something: Asha's notes allowed overdue members to borrow, but the desk's paper rule did not. The check recorded the contradiction, Asha decided, and the rule was added — with the date and her name in the feature's Conflict check section.

A story and its criteria

S-2 Loan limit is a story: one thing a person does, with acceptance criteria a person can check.

ACGivenWhenThen
AC-1a member with 3 books on loanthe librarian scans their library cardthe desk shows "Limit reached: 3 books on loan" and Lend cannot be pressed (F-1/R-1)
AC-2a member with an overdue bookthe librarian scans their library cardthe desk shows "Return overdue book first:" and the overdue book's title, and Lend cannot be pressed (F-1/R-4)
  • Each criterion is one behaviour, observable on the screen — no code, no internals.
  • It cites the feature's rule (F-1/R-1) rather than restating it.
  • The story also says what is not in it, and gives test data: card 1003 is Sam, with 3 books on loan; card 1004 is Lee, with one book overdue.

A slice's work order

Ravi's slice SL-2 Refuse a loan over the limit covers both criteria. Before writing any code, the agent wrote its work order. The summary is for anyone; the rest is for developers:

### Summary
- The desk refuses a loan when the member already has 3 books, or has an overdue one.
- The refusal shows as soon as the library card is scanned, before any book.

### Plan
- src/loans/eligibility.ts — canBorrow(memberId, today); reads loans.due_on (D-1)
- src/loans/lend.ts — call canBorrow before inserting
- src/desk/LendPanel.tsx — show the refusal after the card scan; disable Lend
- src/loans/eligibility.test.ts — unit tests below
- db/seed.ts — members 1003 (3 loans) and 1004 (one overdue)

### Must not
- D-1 — overdue means due_on < today, from the stored date.
- PERF-1 — card scan to screen under 1 s: one query for both checks.

### Tests
- "S-2/AC-1 refuses a member with 3 books on loan"
- "S-2/AC-2 refuses a member with an overdue book"

### Conflict check
- Checked 2026-10-07 against: S-2, S-1, SL-1, D-1, security, performance, open slices (none)
- Overlap: SL-1's lend.ts already returns LendError → AtLimit and Overdue added to it
- Dependency: B-1 changes how "today" is worked out → today is a parameter here
  • Must not links the rules this change could break — a recorded decision (D-1) and a performance rule.
  • Tests are named with the criterion they prove. That name is how spry knows a criterion is proven — a mention in a comment does not count.
  • The conflict check found that the bug fix B-1 changes how "today" is worked out, so this slice takes "today" as a parameter and both fixes line up.

The work order becomes the draft pull request's body. When the slice closes, a close summary is added below it.

Falsify: proving the tests

SL-1 Record a loan is closed. Before it merged, the tool broke each safeguard it added and ran the tests that should notice. In the table, the control is the safeguard in the code, and the mutation is how the tool broke it:

ControlMutationExpectResult
book already on loan → refuseddelete the checkS-1/AC-3caught
due date = today + 14+ 13S-1/AC-2caught
unknown library card → refuseddelete the checkS-1/AC-1caught

The third row is the point. On the first run the unknown-card check could be deleted and every test still passed — the tests looked fine but would not have noticed. Falsify found it, the slice added "S-1/AC-1 refuses an unknown library card", and the re-run caught it. The re-run replaced the row; the close summary keeps the story. How falsify works →

QA's check log

Meera keeps a log of manual checks in the story's checks.md, one row per criterion per run, appended and never edited. Build is the commit she tested:

The latest row for a criterion decides it. A receipt printed in the evening showed the wrong due date, so AC-2 is un-proven even though its test passes. The failure became bug B-1 Due date a day early on evening receipts, and story S-1 now shows not proven — its slice is merged, but it is not done. Checks for QA →

Bugs and tasks are shown with their parent but do not count toward its progress — a feature is done when its stories are, not when its bugs are.

What's written and what's generated

  • Written — by a person, or an agent in an interview: everything outside the marked blocks.
  • Generated — by CI (the automatic checks GitHub runs on every push) on the main branch, or by /spry:merge on the main branch when CI did not run: progress tables, proof tables and index lines, between <!-- spry:… --> markers. Branches never touch them, so they never conflict.

Try it yourself

Clone spry and run the tool against the example:

$ git clone https://github.com/chetanism/spry && cd spry
$ python3 plugins/spry/tool/spry.py --root docs/example status
$ python3 plugins/spry/tool/spry.py --root docs/example backlog
$ python3 plugins/spry/tool/spry.py --root docs/example coverage
$ python3 plugins/spry/tool/spry.py --root docs/example check

For reference, the files themselves are browsable on GitHub: docs/example/spry/README.md — start there and click down.
