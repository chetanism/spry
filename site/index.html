Agent-first development a human team can follow

Your coding agent can write a feature in minutes. spry gives that speed a process your team already understands — plans in plain words, work in small reviewable slices, and progress you can trust because it is proven, never typed.

What spry is

spry is a plugin for Claude Code — usable from Cursor, Gemini, Codex and other agents too — that runs a software project the way an agile team already thinks about it. It is three things working together:

  • Skills — short commands like /spry:story or /spry:slice-close that you type into your agent. Each one walks through one step of the work.
  • Process files — the written rules every agent follows: how to interview you, how to split work, how to review it, how to reply. They are copied into your project, so every agent and every teammate reads the same ones.
  • A small tool — one Python file, no dependencies, that checks the rules and works out progress. It runs in CI (the automatic checks GitHub runs on every change) too, so nothing depends on an agent remembering to do the right thing.

Everything spry writes is a Markdown file in your repository. There is no server, no database, no account to sign up for. Anyone on the team — including people who never open a terminal — can read the plan by clicking through folders on GitHub.

The idea in three lines

Plan in plain words

Milestone → epic → feature → story, one level at a time. Each step is a short interview, and each page is written for the person who will read it.

Build in slices

A written work order before any code, a pull request (the proposed change, shown on GitHub for review) a person can review in one sitting, and tests that are proven to notice when the safeguards break.

Progress is derived

A story is done when its slices are merged and every acceptance criterion is proven by a test or a QA check. Nobody types "done".

How the work is shaped

spry uses the levels most teams already plan in. Each one has a single parent, and each one is written by the person who owns that level of decision:

Milestonean outcome→ Epica body of work→ Featurehow it works, its rules→ Storyacceptance criteria→ Sliceone pull request

Milestones, epics, features and stories are written by product, in plain language, through an interview the agent runs. A slice is where the technical work starts: one small change, one pull request, covering one or more of a story's acceptance criteria. Bugs and technical tasks hang off the same tree. Why people use it

Agents without a process

  • Huge pull requests nobody can review properly
  • "Done" means the agent said so
  • Tests that pass but would not notice the bug
  • Context lives in a chat that is gone tomorrow
  • Product can't see what is happening without asking

With spry

  • Slices a reviewer reads in one sitting
  • "Done" means merged and every criterion proven
  • Safeguards are broken on purpose to prove tests catch them
  • Everything is in files — any agent, any session, picks up where the last left off
  • The plan, backlog and progress are pages anyone can open

Early days

spry is young. The tool is tested, and the process is being piloted on real projects — most recent changes came straight from them — but none has run a full milestone through it yet. Expect it to keep changing; /spry:update brings each change into your project as an offer, never a forced rewrite.
