The plan is a folder tree

In spry the plan is not a database or a board — it is folders in your repository. A milestone is a folder; its epics are folders inside it; and so on down to the story. Open the repository on GitHub and you can read the whole plan by clicking.

Why folders

  • Nothing to install to read it. GitHub shows a folder's README.md when you open the folder. A product owner navigates milestone → epic → feature → story the way they browse any website.
  • The path is the parent. An item's parent is the folder it sits in — there is no parent: field to get wrong. Moving a story to another feature is git mv.
  • Plan and code change together. The plan lives in the same repository as the code (never a nested repository), so a slice's work order and its code land in one pull request.
  • Fewer merge conflicts. One file per item means two people rarely edit the same file.

A project's layout

This is what /spry:init or /spry:adopt sets up. You do not need to remember it — the tool creates every file in the right place — but it helps to know what is where.

AGENTS.md                  # always read by agents; short, with a hard line budget
CLAUDE.md                  # one line: @AGENTS.md
spry/
  spry.config.json         # IDs, levels, team, test commands, budgets
  README.md                # the entry point for people: what's here, where to start
  BACKLOG.md               # generated: what to pick up next
  COVERAGE.md              # generated: done vs defined, criteria proven
  DONE.md                  # generated: what is finished, newest first
  plan/
    README.md              # the roadmap: the milestones
    M-1-<slug>/
      README.md            # the milestone
      E-1-<slug>/
        README.md          # the epic
        F-1-<slug>/
          README.md        # the feature: how it works, its rules
          S-1-<slug>/
            README.md      # the story and its acceptance criteria
            checks.md      # QA's test scenarios and check log
            SL-1-<slug>.md # a slice: work order + close summary
          bugs/B-1-<slug>/README.md
      tasks/T-1-<slug>/README.md   # technical work no story asks for
  knowledge/
    glossary.md            # one term per concept, and the words not to use
    conventions/           # INDEX.md + one file per area of code
    decisions/             # INDEX.md + D-1-<slug>.md …
    external/<service>/    # how a service you depend on really behaves
    security.md  performance.md  constraints.md
  process/                 # spry's rules and templates, copied in
  tool/spry.py             # spry's tool, copied in
.spry/                     # not committed: search index, personal tone, gate stamp, caches, fresh pages (view/)
  • Anything that can have children is a folder — milestone, epic, feature, story, task, bug. A slice has no children, so it is a single file.
  • One directory, spry/, holds it all, and setup excludes it from your deploy build (.dockerignore or the stack's build configuration), so plans never ship to production.
  • A project adopted from writ also has spry/history/: the mapping from old writ IDs to new ones, and writ's slice summaries and requirement details kept as they were written. Coming from writ →

Audience is how technical the document is, from 1 to 10 — see Written for its reader. Tasks and bugs hang off the tree so they are found next to what they serve, but they do not count toward the parent's progress: a feature is not "less done" because someone found a bug in it, and setting up CI does not make a milestone more done.

  • Prefixes and levels are chosen in the setup interview. The ones above are the defaults. A small project can drop epics and put features straight under milestones.
  • Acceptance criteria live only in stories, numbered AC-1, AC-2, … and cited as S-1/AC-1. A feature's rules are numbered R-1… and cited as F-1/R-2; stories cite rules instead of restating them.

IDs are flat counters

Every type has its own counter: S-1, S-2, S-3, wherever those stories sit. IDs are never hierarchical like M2.E3.F1.

Why: a hierarchical ID is wrong the moment work moves. Move a feature to another epic and every ID under it changes, along with every test name and link that cited them.

Two sessions, one number

With several people or agent sessions working at once, two of them can each create "the next story" and both pick S-7. The mint setting decides how spry handles that:

mintHow an ID is takenBest for
local defaultThe next free number in your working tree. Two branches can take the same number; check --base names the clash before merge, and the later branch renames.Solo work, or a main branch that accepts no direct commits
mainThe main branch on the remote is the counter and the push is the lock: new takes the number there, pushes it, and merges that commit into your branch. Two sessions can never get the same number. It works in a temporary worktree holding only spry/, with git hooks off and your git config untouched.Several sessions or people creating items in parallel

Why merge it in, rather than write the same file on the branch? Because the branch then fills that file in, and git would see two different additions of one path — a conflict at every merge — unless the file is already in the merge base. Merging the main branch in puts it there. The cost is that the branch's base moves mid-slice, which is the smaller problem. Why is local the default? So nothing pushes to your main branch until your project says it may. Work as a team →

Front-matter

Each item file starts with a small block of fields, its front-matter. It uses a restricted format — only key: value and key: [a, b] — so the tool can read it with nothing but Python's standard library.

---
id: SL-2
title: Refuse a loan over the limit
state: open
owner: Ravi
audience: 8
covers: [AC-1, AC-2]
branch: sl-2-refuse-over-limit
pr: 14
blocked_by: []
related: [SL-1]
---
Every item
id, title, state, owner, audience, blocked_by, related. No parent — the folder says it.
state for plan items
draft → ready, or dropped. "Done" is never written — it is worked out (Status is derived).
state for slices
planned → open → closed, or dropped. A closed slice also carries closed: <date>.
Slices add
covers (the story's criteria it builds), branch, pr — and issue, when the project turns on a GitHub issue per slice.
blocked_by
What must finish first. An item waits on what it, and everything above it, names here. Filled by the conflict check (a Dependency finding) and by /spry:slice when one slice needs another's code.
related
A pointer to something nearby. It never affects progress.

Blockers must be able to finish

spry check refuses two kinds of blocked_by:

  • A dropped blocker — it will never finish, so the item would wait forever.
  • A circle — A waits on B, B waits on A. This includes subtle ones: a slice that names its own story waits on something that is only done when the slice is.

The issue option

With slices.issue on, opening a slice creates a GitHub issue from its work order — for people outside the repository who follow issues rather than files. The issue body is frozen and says so; the slice file keeps changing, and the difference is the record. The close summary is posted as a comment, and the merge commit's Closes #n closes it. check refuses an open slice without its issue.

A slice has two parts

Work order — at open, before code

  • Summary anyone can read
  • Covers — which criteria
  • Plan — one line per file
  • Must not — rules this could break
  • Tests — named after criteria
  • Demo — copy-paste to see it
  • Conflict check

Close summary — at close

  • What changed — only where the code differs from the plan, and why
  • Falsify — each safeguard, broken on purpose, and whether a test caught it
  • Follow-ups — bugs, tasks, decisions found

The file is the source; the pull request body is copied from it — the work order at open, both parts at close — and never edited by hand. That way the review, the record and the PR can never disagree. The work order is never rewritten to match the code afterwards; the close summary says what differed.

Nobody maintains a map

The tool builds the relationship map — the hierarchy, what blocks what, what is related — from the folders and front-matter. There is no diagram, spreadsheet or register to keep in step by hand.
