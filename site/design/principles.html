Principles

Every rule in spry comes from a handful of principles. If you know these, you can predict how spry behaves in a situation this site never mentions — and decide whether that behaviour suits your team.

The eight principles

One parent per item

The plan is a strict tree: milestone → epic → feature → story → slice. Each link is one-to-many, and nothing in the plan belongs to two parents.

Why: writ, the process spry grew out of, let one piece of work claim several requirements at once. Working out "is this requirement done?" then meant following a web of claims, and the answer drifted. With one parent, "done" rolls up by simple counting, and moving a piece of work is moving one folder. Trade-off: work that really serves two stories has to be split, or linked as related — a pointer that does not count toward progress.

Status is derived, never typed

People write intent: what should be built and how to tell it works. Nobody writes "done". The tool works it out from facts — the slice is merged, the criterion has a test that names it, or a passing QA check.

Why: a status someone types is a status someone forgets to update, or updates optimistically. An agent is the most optimistic typist there is. Status is derived →

Written for its reader

Every kind of document declares an audience level from 1 (no technical knowledge) to 10 (an engineer in this codebase). Planning documents are written in plain words; slices are technical. The same level governs how the agent talks to you while it works on that document.

Why: product owners stop reading plans full of file paths, and developers waste time on prose. Writing each page for the person who reads it keeps both in the loop. Written for its reader →

Incremental

No big requirements document up front. You plan one milestone, then one epic, then one feature — as the work needs it.

Why: writ started every project with a full business requirements document. It went stale as soon as the first slice taught the team something. spry plans a level when you are about to need it, so what is written is still true when it is built.

Checked or not written

A rule that matters is enforced by spry check — the tool's validator — rather than left as a sentence an agent may or may not follow.

Why: an agent follows written rules most of the time. "Most of the time" is the problem: the one time it doesn't is the time nobody is watching. Rules that can be checked are checked, in the agent's session and again in CI.

Small files, indexed

Anything that grows — conventions, decisions, notes about an external service — becomes an INDEX.md with one line per item, plus one file per item.

Why: an agent reading a 900-line file to find one rule burns its context and still misses things. An index lets it read one line per item and open only the item it needs. Knowledge and size →

Agent-neutral

The logic lives in templates, process files and the tool. Skills are thin pointers to them. State lives in files, never in a chat session.

Why: sessions end, context windows fill, and teams use different agents. Because everything is in files, you can switch agent — or hand the slice to a colleague — halfway through and lose nothing.

Same for one person or ten

A team is a section of the configuration file, not a different way of working. Solo, nothing is routed for review; add members and roles, and review routing and code owners follow.

Why: most projects start with one person and grow. Changing process when the second person joins is when things break.

"team": {
  "members": [{"name": "Asha", "github": "asha", "roles": ["product"]}],
  "review": {"spry/plan/**": ["product"], "src/**": ["developer"]}
}
  • Empty members means solo: nothing is routed for review.
  • GitHub's CODEOWNERS file is generated from review, so plan changes go to product and code changes to developers.
  • Skills read the roles to decide who an item goes to. Work as a team →

How the pieces fit

spry has three parts. Knowing where each lives explains why your project behaves the same whichever agent you use, and why CI can check things without any agent at all.

PartWhat it isWhere it lives
SkillsShort entry points you type, like /spry:story. Each names the process file to follow.The plugin (or, for other agents, copied into your project)
Process filesThe rules every agent follows: how to interview, slice, review, merge, reply. Plus a template for every document type.Copied into your project at spry/process/
The toolspry.py — one Python file, standard library only, Python 3.10+. Checks the rules, works out progress, writes generated pages, runs falsify.Copied into your project at spry/tool/spry.py

Why the process and tool are copied into your project

This is called vendoring: the process files and the tool are copied into your repository, not read from the plugin each time.

  • Any agent reads the same rules. A teammate on Cursor and one on Claude Code follow identical text, because it is in the repository they both cloned.
  • CI runs without an agent. GitHub Actions runs python3 spry/tool/spry.py check with nothing installed but Python.
  • Your project can change its own process. /spry:process-change edits your copy and records why, so /spry:update keeps your change when it brings in spry's newer ones. The tool itself is never edited locally — it is replaced whole on update, and a change your project needs in it is offered back to spry with /spry:contribute.

The trade-off: your copy can fall behind. /spry:update exists for that, and offers each change one by one. Keep spry yours →

How it is installed

  • Claude Code: add the marketplace, install the plugin, and the skills appear as /spry:<name>.
  • Any other agent: spry.py install --agent generic writes the skills to spry/skills/ and lists them in a generated block of AGENTS.md, which most agents (Codex among them) read. --agent claude writes project skills for people not using the plugin, cursor writes Cursor commands, and gemini writes Gemini commands. The four skills that need the plugin itself — init, adopt, update, contribute — point at the folder install ran from.

The spry repository itself

For reference, spry's own repository holds the marketplace listing, the spry plugin (skills, process files, templates, the tool, and per-stack setup profiles for TypeScript/Node, Python and a generic fallback), the tool's tests, and the worked example under docs/example/. A second plugin, spry-web, for design-system and other "how to do X" skills, is planned for later.
