Agent hooks

spry's rules live in spry check, merge-check and CI, which every agent runs. But they run late: at close, at the merge, after the push. A Claude Code hook runs at the moment the agent acts, so it can say the same thing sooner, while the mistake is one edit old. spry ships six, and you turn each one on or off by itself.

Why they exist

On the pilot projects, some rules held only while the agent remembered them:

  • Nothing but the agent's memory made merge-check run before a merge.
  • A slice's pull-request number was set with sed, around the link command that checks it.
  • The agent looked for the config at the repository root three times.
  • Problems in documents surfaced only at close: one slice ran the full gate three times, about 22 minutes.
  • A criterion that tests already cited was edited, and nobody saw it until the merge checks.

Each hook below answers one of these.

The six hooks

KeyWhen it runsWhat it does
sessionA session starts, resumes, is cleared or compactedTells the agent where the config and the tool are, which slice this branch builds, your tone, and which hooks are on.
link_fieldsAn edit of a slice file, or a sed -i / perl -i that names oneRefuses a change to branch, pr, issue or owner, and names the link command that sets it. The rest of the file stays editable.
cited_criteriaAn edit of a storyWhen a criterion that a test cites changes or is dropped, asks you first. The story's owner decides a criterion. If code changes on the same branch, the slice still needs their approval before merge-check passes.
check_editAfter an edit of a document check readsChecks that one file: front-matter, budget, leftover placeholders, links, banned words. Any errors go straight back to the agent.
mergegh pr merge, from the slice's branchRuns merge-check for the slice whose pull request or branch it names, and refuses the merge if anything blocks it. It does not look at CI: /spry:merge still checks that first. Run from another branch, it says nothing, because the files there hold another copy of the slice.
check_stopThe agent is about to finishIf documents changed (uncommitted, or on the branch), runs check. On errors the agent goes back once to fix them or say why they stay. The same documents are not checked twice, whether they passed or not.

Turning them on

Each hook has a key under hooks in spry/spry.config.json. New projects start with all six on; setup names each and asks which to turn off. A missing key is off, so a project set up before 0.34.0 sees nothing until /spry:update offers them.

"hooks": {
  "session": true, "link_fields": true, "cited_criteria": true,
  "check_edit": true, "merge": true, "check_stop": false
}

To turn every hook off for one session, start Claude Code with SPRY_HOOKS=off in its environment.

What they cost

  • Nothing for calls they are not about. Each hook is filtered by tool and by a rule such as Bash(gh pr merge *) or Edit(**/spry/plan/**). A test run or an edit of code starts no process. The session-start and stop hooks can't be filtered that way, so once the plugin is installed they start Python in every repository (a fraction of a second), and leave at once outside a spry project.
  • Little for the rest. check_edit reads one file and the glossary, not the plan. link_fields and cited_criteria read the file being edited. merge and check_stop load the plan, but they run what you would run at that point anyway. On a slow disk (one pilot has a virus scanner that adds about 11 ms to every file open), that matters.
  • They never stand in the way by accident. If a hook fails, times out or finds no Python, the call goes through. A hook only says something sooner: the rule itself stays in the checks, which CI and every other agent still run.
Claude Code with the plugin

The hooks come with the Claude Code plugin and need Claude Code 2.1.295 or later. Cursor, Gemini and other agents don't run them. Nothing is lost there: those agents run the same checks, just later. A project installed with install --agent claude instead of the plugin can copy the entries from the plugin's hooks/hooks.json into its own .claude/settings.json, with spry/tool/spry.py as the tool.

The project's rules, not the plugin's

The plugin's copy of the tool answers each hook. If your project's copy, the one vendored into spry/tool/, is a different version, your copy answers instead. So a hook follows the rules your project took, even when the plugin is newer.

Adding your own hooks

spry's six cover spry's own rules. Your project may want more: run the formatter after an edit, refuse a push to the main branch, remind the agent of a rule it keeps breaking. Those belong to your project, not to spry.

  1. Write it in your project's .claude/settings.json, which is committed, so everyone gets it. Use the same shape as spry's hooks/hooks.json: an event, a matcher for the tool, an if rule so it only runs when it can matter, and the command. 
    {
  "hooks": {
    "PostToolUse": [{
      "matcher": "Edit|Write",
      "hooks": [{
        "type": "command",
        "if": "Edit(**/*.ts)",
        "command": "pnpm exec prettier --write \"$(jq -r .tool_input.file_path)\"",
        "timeout": 30
      }]
    }]
  }
}
  2. Keep it cheap and quiet. A hook reads the call as JSON on stdin. It exits 0 with nothing to say, or prints a JSON answer: refuse a call, ask you, or send the agent back. Don't load more than the call needs. If the check matters for every agent, put it in CI or check too: the hook only says it sooner.
  3. Record it with /spry:process-change, so /spry:update keeps it and the next person knows why it is there.
  4. If every spry project would want it, offer it to spry with /spry:contribute. It becomes a seventh key under hooks.

Claude Code's hooks reference lists every event, the payload each one gets, and the answers it takes.
