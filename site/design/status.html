Status is derived

Nobody in spry marks anything "done". The tool works it out from facts that are hard to fake: the slice is merged, and every acceptance criterion has a test or a QA check that proves it. When you read "done" in spry, it means something.

Why not just a status field?

A typed status is an opinion. People forget to update it, update it too early, or update it for the part that works and not the part that doesn't. An agent is worse: asked whether it finished, it will say yes. And when a story is "done" but nobody can say which test proves it, the next change can quietly break it with nobody noticing.

So spry asks for two kinds of evidence instead — one about the code, one about the behaviour — and counts.

The rules, level by level

LevelDone when
Slicestate: closed. /spry:slice-close sets it in the pull request's last commit, so on the main branch "closed" means merged.
Acceptance criterionProven: a test whose name contains S-1/AC-1, or a pass as the latest row for it in the story's checks.md.
StoryAll its slices are done and every criterion is proven.
Feature, epic, milestoneAll counted children are done. Dropped ones are left out; bugs and tasks never count.
Built is not the same as done

A story can have every slice merged and still not be done, because a criterion is unproven. In the worked example, S-1 Lend a book has its only slice merged, but QA's latest check of AC-2 failed — so S-1 shows "not proven". That is the point: built and working are different claims.

What counts as proof

A test, by its name

A test proves a criterion when the criterion's ID is in the string that names the test — its title, its docstring, a parametrize id:

it("S-2/AC-1 refuses a member with 3 books on loan", () => { … })
  • A comment or code doesn't count. // covers S-2/AC-1 above a test proves nothing, and check warns about it. Why: a comment survives the test being deleted, renamed or rewritten to test something else. A test's name is what the runner reports.
  • A skipped test doesn't count. A line that skips the test or leaves it for later (it.skip, test.todo, xit, @pytest.mark.skip) proves nothing.

Why a name and not a mapping file? Because there is nothing to keep in sync. Rename the test and the proof goes with it; delete it and the proof disappears, visibly.

A QA check

Some criteria are checked by a person — a printed receipt, a layout on a real device. QA logs each run as a row in the story's checks.md: date, criterion, build, who, pass or fail. Checks for QA →

A later fail un-proves it — test or not

When the latest check-log row for a criterion is fail, the criterion is unproven even if a passing test cites it. Why: a person saw it broken. A green test that disagrees with what someone saw is a test that tests the wrong thing.

A plan longer than 100 lines prints only the levels that fit and says how to go deeper: status <ID> for one branch of the tree, --level to choose the depth, or --all for everything. /spry:status explains the same thing at your tone and says what to pick up next. The same numbers also appear on the generated pages.

Changing a story after work has started

Stories change. spry allows it — git history is the record — but it watches for one specific danger: the quiet way to "pass" is to weaken the criterion to fit the code.

  • A warning when a branch edits the text of a criterion that a test already cites, or that its story's checks.md scenarios or check-log rows relied on and the branch left as they were. (check --base, which CI runs on every pull request, compares against the main branch.)
  • A block when a branch changes a criterion and code together: merge-check refuses to merge until the slice carries criteria_approved_by: the story's owner. Only their yes, in their words, puts that line in — never the agent's judgement.

The trade-off is one extra question when a criterion really did need to change. In exchange, the criteria stay what product agreed to.

Criteria are never renumbered

A criterion's number is permanent. Dropping one strikes it through (~~AC-2~~) rather than deleting it, so AC-3 always means the same thing in every test name, check row and conversation.
