Falsify

A passing test tells you the code works today. It doesn't tell you the test would notice if the code broke. Falsify answers that: for each safeguard a slice adds, it removes the safeguard on purpose, runs the tests, and expects one to fail.

The problem it solves

Agents write a lot of tests, quickly, and many of them pass for the wrong reason: they check that a function returns something, or test the happy path next to the rule rather than the rule. A suite like that is green whether the safeguard is there or not. You only find out when the bug ships.

Falsify is a targeted form of what testers call mutation testing: make a small, deliberate change to the code (a mutation) and see whether the tests catch it. spry does it only for the lines that matter — the safeguards the slice added — so it takes minutes, not hours.

From the worked example

SL-1 Record a loan added three safeguards. Falsify deleted the "unknown library card" check, and every test still passed — no test noticed. The slice added "S-1/AC-1 refuses an unknown library card", ran falsify again, and the check was caught. The re-run replaced that row, so the table keeps only the result; the close summary says what happened.

How it runs

  1. The plan is drafted from the diff, not by hand.

    falsify suggest reads the source lines the branch added and lists each control — a guard, a validation, an authorisation check, an error branch — with a mutation that removes it. Each plan entry names the line with find and its replacement with with — writ's form. A person can edit the plan before it runs.

  2. Each control names what should catch it.

    expect names acceptance criteria (S-1/AC-2) — or, for a bug's or a task's slice, the bug or the task (B-4, T-7), since neither has criteria. Tests are found by those IDs in their names. Or it names a test file by its path, for a guard a test already covers — a task's set-up or refactor is often guarded by tests older than the task.

  3. Only those tests run, with the runner's fail-fast flag — one failure is enough.
  4. The result is recorded in the slice file's Falsify table, with --record.

Which mutations

  • A guard made never true — if (loans >= 3) becomes a condition that never fires.
  • A comparison's boundary flipped — >= ↔ >. Never == ↔ !=, and never inside a generic's <…>, which isn't a comparison at all.
  • A throw, raise or error return deleted.

Why not negate the guard?

Negating if (overLimit) to if (!overLimit) also breaks the normal path — now every member is refused. Any test at all "catches" that, including ones that know nothing about the limit. It is a false catch: it says the safeguard is tested when it may not be. Making the guard never true removes only the safeguard.

When there is no guard to remove

  • The slice changes a value — a key, a digest, a calculation — and adds no guard: falsify offers up to five lines that compute or store something, each deleted. Keep the ones a test must notice. merge-check never requires these.
  • The slice adds no source line at all — only tests or documents: there is nothing to falsify, and merge-check accepts an empty table.

The diff decides, not the agent

The one thing an agent must not be able to do is leave out the control it suspects would survive. So:

  • merge-check runs suggest again at merge time and blocks when a control it lists has no row in the table.
  • The agent can add controls, never drop one. A control that cannot run — it needs a real clock, a network — is recorded skipped — <reason>, for a person to accept.
  • Rows are matched by a key, a hash of the file and the line found (<!-- f:… --> in each row). So renaming a control in plain words, to help the reader, never forces a re-run.

Results

ResultMeansThen
caughtA test failed with the safeguard removed — the runner's report says soNothing — this is the goal
survivedEvery test still passedAdd a test and run again — or write why no test should catch it. A bare survived blocks the merge.
unreliableThe tests were red, or timed out, before anything was changed — or the run broke before any test failedFix the baseline, or what broke the run, first
skippedThe control can't be run hereA written reason, accepted by a person at merge
  • caught only when a test failed. A non-zero exit says only that something failed: a database not made yet, a port in use, pnpm refusing to run. falsify reads the runner's own summary (1 failed, 1 failing, --- FAIL:…); without one, the control is unreliable, noted failed, but no test did. Why: a false caught hides a missing test, and one turned up in ten parallel runs of a pilot's plan. A runner none of the built-in summaries fit gets its own failed pattern. The limit: jest counts a test failed when its beforeAll throws, and node --test a file that throws as it loads, so there a slot that is not ready still looks like a failed test — falsify.setup readies the slot before any test runs.
  • survived only when every group of its tests ran. One group red or timed out makes it unreliable — never a survivor that might have been caught.
  • A reason on a survivor or a skip (survived — logged only; no rule depends on it) is a ! in merge-check, which a person accepts in the merge's one ask.
  • Re-running only the survivors is fine: --record replaces their rows and keeps the rest. A control whose line has changed since has a new key; run the whole plan with --replace to drop its old row.

Making it fast

  • Only the citing test files run, through a per-runner command with a {files} placeholder.
  • Files that name the control's source file run first; the rest run only if those miss it. A control cited by more than 20 files is flagged wide: at the run — list the files that matter to cap it.
  • The baseline runs once for all the files together, not once per control.
  • Parallel in git worktrees (falsify.parallel: false, true or a number; or --jobs N). Each worker gets its own detached copy of the code outside your repository, so your working tree is never written to. Installed dependencies (node_modules, .venv, venv, plus falsify.share) are linked in, not reinstalled — except a pnpm package's own node_modules, whose links are copied, so a workspace sibling resolves to the worktree's mutated copy rather than the untouched one.
  • The baseline runs in a worktree too, so anything a worktree is missing shows up as unreliable — never as every control looking caught.
  • It falls back to serial when tracked files have uncommitted changes or a cited test file isn't committed. A runner marked "parallel": false (integration tests on a shared database, fixed ports) runs its controls one at a time.
  • Worktrees are kept between runs (falsify.keep_worktrees) and reset at the start of each — checked out at HEAD, every untracked and ignored file removed. Why: a virus scanner reads every file of a fresh worktree on its first run: 16 seconds against 3 for the same test file on a pilot's Mac.
  • pnpm's dependency check is off in a worktree: pnpm 11 judges the borrowed node_modules stale and would try to reinstall before every run.
  • Each slot can have its own database. Every command sees SPRY_FALSIFY_SLOT (1, 2, …) and SPRY_FALSIFY_SLOTS; falsify.setup, if set, runs once in each slot before the baseline — create and migrate that slot's database — so integration tests can run in parallel without a runner of your own. A setup that fails stops the run.

Safety

  • It refuses a mutation that changes nothing, a file with uncommitted changes, and an expect no test cites, or a path that is not a test file.
  • It always restores the code — after an error, Ctrl-C or a kill signal too — and checks the files are exactly as committed afterwards.
  • A runner that times out is stopped with its whole process group, so no stray test process keeps running.
  • It works on Windows: paths are quoted for cmd, taskkill /T stops a timed-out run, a directory junction stands in when a symlink is refused, pnpm projects run serially, and files are written with Unix line endings.
  • Every write gets a fresh, increasing file timestamp. Why: this bug was found while building falsify. Two mutations of the same size written in the same second let build caches that check only size and timestamp — Python's .pyc files — run the previous mutation's code. That produced a false caught.

Where it fits in a slice

At close, falsify runs after the review and before the gate:

Reviewand its fixes→ Falsifytests added for survivors→ Gateonce, on the code that merges

Why that order: a review fix changes code falsify would have proved, and a test added for a survivor changes code a gate already passed. In this order each runs once. Falsify runs its own baseline, so it doesn't need a gate first. Close and merge →

Is it worth it?

The cost is a few minutes per slice, mostly unattended. The trade-off is honest: falsify proves the tests notice the safeguards this slice added. It does not prove your whole suite is good, and it can't run a control that needs a real clock or network — those are written down and accepted by a person rather than silently passed.
