Coming from writ

spry is inspired by writ, not based on it. Both aim at agent-first development a human team can follow. spry was rebuilt around what running writ on two real projects taught — and if your project runs writ today, it has a planned way across.

Kept, changed, dropped

What
KeptSkills run the project; the slice loop; a work order before code; the demo; falsify; decisions; chat rules; process-change; security-audit; prelaunch; test-scenarios; test-all; update; contribute; adopt. Renamed: manual-test → explore, context-compact → compact, requirement-review → review.
ChangedAn up-front business requirements document → milestones planned one at a time. Registers → item folders. The ledger → status derived from merges and proof. CLAUDE.md → AGENTS.md.
DroppedMany-to-many claims between work and requirements; requirement-verify; coverage-review; change-request; velocity; the code graph; maintenance and cleanup.

Why those changes

  • The requirements document went stale. Written up front, it stopped matching the product as soon as the first slices taught the team something. spry plans a level when it is needed. Incremental →
  • Many-to-many claims made "done" a puzzle. One slice could claim several requirements, and one requirement several slices. One parent per item makes "done" a count.
  • A hand-kept ledger and queue drifted. They were edited by hand after every slice. spry derives both. Status is derived → · Generated pages →
  • Comments counted as proof. writ accepted a requirement ID in a comment near a test. spry accepts only the test's name. What counts as proof →

Still to come from writ's list: product-docs, product-guide, and a separate spry-web plugin.

Adopting a writ project

/spry:adopt recognises a writ project by a folder — usually canon/ — holding BRD.md, ID-REGISTRY.md and a slice queue. It works in two halves, so nothing is investigated twice:

writ's agentcleans up, writes to-spry.md→ You approve it"Status: approved"→ /spry:adoptbuilds the plan from it→ You review the PRthen retire canon/
an agent runs ita person decides

Before anything is written

  • The mapping file must exist and be approved: canon/to-spry.md, whose first line reads Status: approved <date> by <name>. Without it, adopt stops and tells you to run the pre-work.
  • No work in flight. A slice in progress in writ, or an open pull request for one, has no home in spry — finish it or park it first.
  • On a branch, spry-adopt: one commit per step, one pull request at the end.

The mapping file

writ's own agent writes it, in writ's terms. It assigns no spry IDs — adopt numbers things as it creates them. Its sections:

  1. Tree — milestones, epics, features and stories as titles with one line of purpose, in plain words, every link one-to-many. A story is one thing a person does; most writ requirements become a criterion of one.
  2. Identifiers — every traceable writ ID and what it becomes: a criterion (ac), a story, a feature rule, knowledge, a milestone exit, or drop — and whether it is done.
  3. Work not built — writ's queue rows not yet built, and the story each goes to.
  4. Documents — every document and where its content goes in spry. History holds only records of what happened; current content moves into the plan or knowledge.
  5. Local process changes — what the project added to writ, why, and whether it is still useful.
  6. Open questions.
  7. Requirement details — writ's detail files, case by case. A file with several jobs becomes a feature: its summary, personas, fence and open questions go to the feature; each May not of a persona, and each blank-field outcome that is not a refusal, becomes a criterion; unsettled reconciliation rows become bugs or open questions and stay out of the Built under writ slice. Stories from a file nobody reviewed stay draft.
  8. Test scenarios — split into stories' checks.md files.

What adopt does with it

  1. Survey and interview as for any adoption, with answers drafted from writ's documents. The roadmap topic has no questions — it shows the approved tree.
  2. Builds the plan top-down, which is where the new IDs come from. Each criterion keeps its requirement's meaning in plain words. Nothing is cut to fit a budget: a story that would run over is split, and only steps, fields and data move to checks.md.
  3. Writes the trail, spry/history/writ.md: every old ID and what it became (S-12/AC-3, F-2/R-1, D-41, dropped, …), added as each item is made.
  4. Records built work. Each story writ built gets one closed slice, Built under writ, linking writ's slice summaries, which are kept unchanged in spry/history/writ/slices/. writ's requirement details are kept the same way in spry/history/writ/requirements/. check skips history; find lists it last.
  5. Rewrites test citations from the trail, by script, in test files only — and moves an ID cited only in a comment into the test's name, since spry only counts names. Then runs the full suite once: only names changed, so it must stay green.
  6. Moves knowledge and instructions: decision records to knowledge/decisions/, CLAUDE.md into AGENTS.md under the admission test, writ's local process changes into process-changes.md.
  7. Asks to remove writ's machinery — its skills, CI workflows and scripts — in one ask.
  8. Verifies by script that every ID and case landed somewhere, then has a fresh agent compare each original with the pages it became and list anything lost or changed. Every gap is fixed before the pull request.
  9. Retires canon/ in the last commit — only after you have compared spry status with writ's last ledger. The trail, the kept summaries and git history keep everything.
Adopted with an older spry?

Projects adopted before the slice summaries were kept, or before current documents were moved out of history, have a recovery procedure that restores them from git history on one branch. Run /spry:update and it is offered.
