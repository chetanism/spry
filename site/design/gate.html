The gate and test speed

Agents make a lot of small changes. If every change ran your whole test suite, a slice would take all day; if none did, broken code would reach review. spry's rule: a slow check runs only when its answer could have changed — and the cheapest checks run first, so a slow one is never thrown away by a lint error.

Three speeds of checking

CommandRunsWhen
gate --fastspry check → fast checks (format, lint, types, cheapest first). No tests, and it stamps nothing.After each change while building, and for review fixes at close
gatespry check → fast checks → affected tests, stopping at the first failureOnce per slice, at close — or whenever a test's answer is what you need
Full suiteEvery testCI on the main branch and nightly; /spry:test-all on request. Never by the agent as a routine step.

Affected tests are the ones your change could affect, using the test runner's own mechanism — vitest --changed, turbo filters, pytest-testmon and so on. The setup interview captures your stack, and the stack profile turns on parallel test execution by default.

The stamp

When gate passes, it writes a stamp in .spry/green with a fingerprint of the code: every file outside checks.docs (by default spry/** and **/*.md). While the fingerprint still matches, the gate runs check alone.

Why: after the tests pass you still write the close summary, fix a typo in the work order, set the slice to closed. None of that can change a test result, so none of it re-runs the tests. The habit this teaches the agent: fix lint before tests run, and write documents after the gate, never the reverse.

A branch that changed only documents

The gate also runs check alone when the branch — working tree included — changed only documents since it forked from origin/<main>, stamp or no stamp. A rebase onto other people's code, or a fresh worktree, then doesn't re-run tests on code the branch never touched. When the gate is unsure, it runs them.

Timeouts on a busy machine

With tests.retry set, affected tests that fail on a timeout (tests.retry_when, by default matching "timed out", "timeout" or "ETIMEDOUT") run once more, quietly, with no parallelism. A machine under load is not a red gate; a real failure fails both runs. So the agent never re-runs the gate to get past a timeout.

CI follows the same order

  1. spry check — which also prints changed --base: code=true when anything outside checks.docs changed.
  2. Fast checks — only when code=true.
  3. Tests — only when code=true.

A pull request that changes only the plan runs in seconds. A slice pushes twice at close — once for the review, once at the end — because every push runs CI again.

After a merge: run nothing, usually

When a slice merges, did the main branch move under it? changed --base <PR head> compares what the PR's checks saw with the main branch now:

  • code=false — the only commits the main branch gained were documents. Its code is exactly what the PR's checks passed. Run nothing.
  • code=true — it gained code the PR never saw, and a PR green against its base can be red where it landed. Wait for CI on the main branch, which runs the full suite there — never run it again locally. No CI on push, or CI that cannot run → run the full suite once and say why.

Why not run everything, always?

Because on a real project the full suite takes minutes or more, and an agent working on a slice would run it dozens of times. That is slow, and it teaches people to stop waiting for checks. spry moves the full suite to where it belongs — CI on the main branch and nightly — and keeps each check in a slice tied to what that check can actually tell you.

The trade-off: an affected-only run trusts the runner's idea of "affected". After a change to dependencies or to build or test configuration, where that can't be trusted, run the full suite on purpose with /spry:test-all. Test beyond the slice →

Finding the slow tests

  • spry tests --slowest reads JUnit XML and names the slowest tests.
  • /spry:test-all runs the whole suite part by part (tests.parts: unit, integration, …), timing each, starting the local services only when they are down and stopping only what it started. It reports; it never fixes.

Fewer conflicts, too

Speed is also not fighting git. One file per item (the plan tree) and no generated files on branches (generated pages) mean parallel slices rarely touch the same file.
