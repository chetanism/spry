Where a person decides

An agent that asks permission at every step wastes your day; one that never asks eventually does something you can't take back. spry draws the line in one place: a person decides three things, and the agent works through everything else without stopping.

The three decisions

1 · The criteria

A story goes ready only on a person's yes. Its acceptance criteria are what "done" means, so the agent never decides them.

2 · The merge

/spry:merge asks once, listing everything a person must accept: a test that didn't catch its safeguard, a skipped check, a changed criterion, CI that didn't run.

3 · Anything hard to undo

A database migration, a public API or event shape, a new dependency, deleting data or files, or breaking a project's Must not rule.

Why the agent doesn't stop in between

Because checks stand in for a person watching each step — and checks do not get tired or skim:

  • The gate — spry's check, the fast checks (format, lint, types) and the affected tests, run at close on the code that merges. The gate →
  • Falsify — every safeguard the change adds is broken on purpose, to prove a test notices. Falsify →
  • Citations only in test names — so a criterion is proven by something the runner actually reports. Status is derived →
  • merge-check — blocks a merge when anything above is missing.
  • A fresh-eyes review — a new agent that didn't write the code reads it against its work order. Reviews →

So opening, building, testing and closing a slice run as one piece of work. You are asked when your answer changes the outcome, not to confirm that the agent is still alive.

Asking only to open

If you would rather read the work order before any code is written, say so when you run /spry:slice-open — it will stop after opening. The default is to keep going.

How the merge's one ask works

Everything a person must accept is gathered into a single question at merge time, rather than scattered through the slice. Items marked ! by merge-check are listed there:

  • a safeguard that survived falsify (no test noticed it removed), with its written reason;
  • a safeguard that was skipped (it needs a clock, a network), with its reason;
  • a criterion with no test — QA will check it by hand;
  • a criterion changed under its tests or QA scenarios;
  • CI that did not run, with the local gate standing in.

When you reviewed the PR and chose fix, then merge, that answer already covers everything the review named; only something new is asked again. Close and merge →

Settled decisions

These are the design questions that were argued over and settled, with the reasoning. They are why spry behaves as it does in the cases where a reasonable person might expect something else.

2026-10-08 — the three decisions

A person decides the criteria, the merge, and anything hard to undo. Everything between runs without stopping, because the checks stand in for a person. Slices of stories that touch different files run side by side, each in its own git worktree.

2026-10-08 — generated tables, slice size, story edits

  • Generated blocks (progress tables, indexes) are written by CI on the main branch only — never on a branch, so they never conflict. Generated pages →
  • Slice size is judged by the agent against a written rule — one sitting to review, one visible change — not a line count.
  • Editing a story after slicing has started is allowed, with a warning when a cited criterion changes.
  • Falsify was built serial first, then parallel.

2026-10-08 — adopt is built alongside init

Putting spry around existing code mattered as much as starting fresh, so /spry:adopt was built with /spry:init, not after a pilot.

2026-10-08 — "Work order" and "Close summary"

A slice file's two parts have these names, and the pull request body is copied from the file by the skills rather than written separately.

2026-10-08 — compact is its own skill; explore is not "manual test"

  • /spry:compact is separate from /spry:process-change: files grow from slices, records and interviews, so the trigger is a line budget, not a change of process.
  • writ's manual-test is called explore here, so it is not confused with the manual checks in checks.md.
  • writ's history-churn survey script is not ported; adopt reads the code itself.

2026-10-09 — the backlog order is derived

  • The backlog is in plan order, worked out — no priority field and no hand-kept queue, which writ's slice queue needed constant re-editing for.
  • A slice branch counts as "in progress", read from git (CI fetches the branches), not from GitHub's API.
  • Fresh pages for a branch live in .spry/view/, never in the tracked file. Marking the tracked file skip-worktree was tried and rejected: git then refuses a pull as soon as CI updates that file.

2026-10-10 — parallel sessions

  • A new ID taken on the main branch reaches your branch by merging the main branch in, not by writing an identical copy. Your branch fills the file in next, and git would see two different additions of one path — a conflict at every merge — unless the merge base holds it. The base moving mid-slice is the smaller cost.
  • A claim is branch: on a planned slice, not state: open: check refuses an open slice without its work order and conflict check, which the main branch cannot have yet.
  • mint defaults to local, so nothing pushes to the main branch until a project says it may.

IDs and parallel sessions →

2026-10-31 — the agent's memory changes only on your answer

  • The tool settles what needs no judgement; the agent reads the rest. A dead index line or a merged pull request is a fact; whether "queued" still means queued is not. Either half alone misses what the other catches.
  • Nothing changes before you answer. The memory is yours and sits outside the repository, where no review or history would catch a wrong delete.
  • Obvious changes come in one question, the agent applying them recommended; each tricky one alone, you editing it recommended.
