Generated pages

Nobody keeps a status board up to date in spry. The tool writes the tables people read — progress in every plan folder, what to pick up next, what is built but unproven, what is finished — from the plan itself.

Marker blocks

A generated table lives between two markers in an otherwise hand-written page:

## Stories

<!-- spry:children -->
| Story | State | Progress |
|---|---|---|
| [S-1 Lend a book](…) | ready | not proven · 1 of 1 slices · 2 of 3 criteria proven |
| [S-2 Loan limit](…) | ready | in progress · 0 of 1 slices · 0 of 2 criteria proven |
<!-- /spry:children -->
  • Everything outside the markers is written by a person, or by an agent in an interview. Everything between them is generated.
  • Each item's README.md has a spry:children block: its children, with links and done/total. Stories also get a spry:proof block — each criterion and what proves it.
  • INDEX.md files in the knowledge folder are generated the same way, from each item's title and summary.

The three project pages

Backlog — what to pick up next

spry/BACKLOG.md, also printed by spry backlog. Its tables, in order:

TableHolds
In progressSlices that are open, or claimed, or have a branch named sl-<n>-…. Leave these to their owner.
Ready to buildPlanned slices with nothing unfinished in their way. The first row is next — /spry:slice-open with no ID offers it.
Needs slicingReady items with no slice, or with criteria no slice covers.
BlockedItems waiting on unfinished work, naming each blocker, where it stands on this page, and who owns it.
Needs planningDrafts to finish, and items with no children yet.
  • Plan order, never typed. By top-level item; inside one, bugs first, then tasks, then stories, in tree order; slices by ID. There is no priority field and no hand-kept queue. Why: writ's hand-kept slice queue needed re-editing every time anything moved. To change the order, change the plan.
  • Every row has a Part of column — everything above it, top level first — so it reads the same however many levels your project uses.
  • In-progress and ready rows have Unblocks — what waits on the slice, or on something it is part of. Between two ready rows, the one that frees more is worth noticing.
  • Every row has a Type: story, task or bug — for a slice, what it builds; above those, the level (feature, …). Every table numbers its rows from 1.
  • With slices.pick: ask, slice-open lists the first four ready rows and recommends none — for teams where outside facts (a design not settled, another team's date) decide.

Coverage — built versus proven

spry/COVERAGE.md, also printed by spry coverage on any branch. It shows, at each level, how much is done, how much is in progress — not done, but some slice under it is open or closed — and how much is defined; then criteria proven, slices, tasks and bugs. Each milestone not yet done gets the same table for just its own work, so you can see how far each one has got; a done milestone is one line. And the list that matters most: stories whose slices are all closed but whose criteria are still unproven, plus unproven criteria cited only in a comment or code — where someone thought they had a test and doesn't.

Done — what is finished

spry/DONE.md, also printed by spry done: every finished story, task and bug, newest first, with what it is part of and the date it closed — the latest closed: date of the slices it counts.

Why the date is in the slice file, not read from git: CI's checkout is shallow, so it can't see old history, and the same files must give the same page in every clone. slice-close writes closed: beside state: closed; merge-check blocks without it, and check refuses one that isn't a date. A slice closed before this existed has no date, so its item shows — and sorts last, in plan order.

Only the main branch gets them

Generated blocks are written only on the main branch — by CI, running spry index with [skip ci], or by /spry:merge when CI left them stale. Branches never touch them.

Why: if every branch regenerated the progress tables, every pair of branches would conflict on them. Kept to the main branch, they never conflict. spry check ignores what is inside the blocks, so a stale table never fails a check.

  • check --base refuses a branch that changed a generated block — unless it matches the base now, or where the branch forked.
  • index --restore <base> puts the base's copy back.
  • /spry:merge never leaves the tables stale: if no CI run is going to update them, it runs index and pushes the refresh itself, retrying if someone merged meanwhile.

Fresh pages on a branch

The committed pages show the main branch as of CI's last run. To see your branch's own state:

  • spry backlog, spry coverage, spry done print them for the working tree.
  • spry view writes every page for the working tree to .spry/view/, which is never committed.
  • spry hooks (opt-in, once per clone) installs git hooks that run view after a checkout or pull that changed the plan or a test, and say so.

Why not regenerate the tracked file and hide the change from git? That was tried with skip-worktree, and rejected: git then refuses to pull as soon as CI updates the file.

Browse in a browser

GitHub renders every page, and needs nothing installed. On a plan of a thousand items, though, clicking folder by folder to follow a story to its slices, blockers and proof gets slow. For that, optionally:

$ python3 spry/tool/spry.py serve   # opens http://127.0.0.1:8765/
  • The plan tree beside every page, each item with a mark for where it stands and its done/total; the branch you are on opens itself.
  • Every document rendered at its own path, so its links work as on GitHub. Its generated blocks are built for your working tree, so the backlog and coverage pages are your branch's, not the main branch's.
  • An item's front-matter as badges: where it stands, its owner, its pull request and issue, and what it covers, waits on and relates to, each a link.
  • Search, the same as spry find.
  • Pace, at /-/pace: where your slices' time went, the same page spry pace writes.

It is read-only. Edits go through the skills, which run the conflict check and spry check — a second way to write would skip both. It answers only on 127.0.0.1, never on the network, and never serves hidden folders like .git or .env. The files stay the only source: no database holds a document.

On a big plan, reading every file takes seconds, so a page answers from the plan as last read while a fresh read runs in the background. A change to the tree or the progress tables shows once that read ends — at once on a small plan, a few seconds later on a big one. The document you open is always read fresh.
