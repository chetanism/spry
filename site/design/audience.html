Written for its reader

A plan only helps if the people who need it actually read it. spry sets how technical each document is — and how the agent talks to you while working on it — by who the reader is.

Audience levels

Every document type carries an audience number from 1 to 10. It governs the document and the agent's chat while a skill works on that document.

LevelReaderWhat's allowed
1–3product, QA, stakeholdersPlain words; what a person sees and does. No file paths, code, commands or internals. An ID always appears with its title: "S-2 Loan limit", never just "S-2".
4–6QA, support, designersNames screens, fields, data and error messages — but no internals.
7–10developersPaths as file:line, types, commands, internals. IDs alone are fine.

The defaults follow who writes each kind of item: milestones and epics are 2, features and stories 3, bugs 4, tasks 7, slices 8. One exception: a slice's Summary is written so anyone on the team can read it.

Your own tone

/spry:tone <1-10> sets a personal override, stored in .spry/ on your machine and never committed. A product owner can set 3 and get plain-language replies even while the agent is working on a slice; a developer can set 9 and get paths while a story is being written. The agent uses, in order: your override, then the audience of the document in hand, then 5.

Why: product owners stop reading plans full of file paths, and when they stop reading, they stop catching the wrong assumption in time. Meanwhile developers want the path, not a paraphrase of it. One tone for everyone serves nobody.

The shape of every reply

Tone sets the vocabulary; the chat rules set the shape, which is the same at every level. They exist so you can scan an agent's reply in seconds and know what it did and what it needs from you.

  • Bullets, not prose. No preamble, no recap, no closing summary, no restated question.
  • Grouped under only the headings the reply needs, in this order: BLOCKED (what stops progress, and on whom) · DONE (what the agent did) · NEXT (what you should do) · FYI (facts, nothing to do) · ASK (questions for you — last, so you have the findings before the choice).
  • Every bullet starts with a tag: past tense for what the agent did — [Added] [Changed] [Fixed] [Ran] [Found]; to-do verbs for what you should do — [Review] [Decide] [Run] [Approve] [Test]; [Note] for a fact.
  • One fact per bullet. Never quote back a diff or a file just written.

Asks you can answer in two characters

  • Asks are numbered from 1 in each reply; options are lettered a, b, c.
  • One line per option, saying why it is or isn't the better choice.
  • Exactly one option is marked (recommended) — except where your configuration says the choice is yours alone (slices.pick: ask).
  • The question carries its own context, so 2b is a complete answer and you never have to open a file to reply.

Writing rules for every document

The same discipline applies to the documents themselves. Rules marked checked are enforced by spry check.

  • Start from the document's template and keep its section order.
  • Bullets, one fact per line. A table where rows share columns. No prose paragraphs.
  • No guide comments or placeholders left in a finished document — no <!-- guide: … -->, no <placeholder>. checked
  • An empty optional section is deleted, not filled with "None" or "TBD".
  • Absolute dates — 2026-10-08, never "today" or "next week". A plan is read months later.
  • No hedging — "should probably", "might want to". State the rule, or ask.
  • An ID with its title on first mention in any document at audience 5 or below — "S-2 Loan limit", then "S-2".
  • Never restate another document — link it. A restatement is a second copy that will drift.
  • Front-matter uses only key: value and key: [a, b]. checked
  • Line budgets per document type. checked Knowledge and size →

One term per concept

The glossary rule: spry/knowledge/glossary.md holds each term, what it means, and the words not to use for it. spry check fails on a banned word anywhere in spry/ — except in code, in the glossary itself, and in conflict-check sections, which quote words in order to correct them. checked

TermMeansDon't say
Membera person who may borrow books from the librarypatron, borrower
Lenda librarian gives a book to a member, recorded as a loancheck out, issue a book
Overduea loan still open after its due datelate, past due

From the Shelf example's glossary.

Why: when a story says "borrower", the feature says "member" and the code says patron, everyone has to wonder whether these are three things or one. Agents are especially prone to it — they vary words for style. A new concept gets a glossary row in the same change that introduces it; a second word for an existing concept is added to Don't say, and the agent tells you once which word it used instead.
